    十五、流水线数据通路设计¶

    （一）流水线寄存器¶

    1. 必要性¶

    流水线各阶段之间需要寄存器来保存前一个周期产生的信息，供下一个周期使用。

    2. 四个流水线寄存器¶

    寄存器 存储内容 作用
    IF/ID 取指的指令、PC+4 为译码阶段提供指令
    ID/EX 操作数、立即数、控制信号、目标寄存器、PC+4 为执行阶段提供数据
    EX/MEM ALU结果、写数据、控制信号 为访存阶段提供数据
    MEM/WB 内存读取数据/ALU结果、控制信号 为写回阶段提供数据

    二、流水线控制¶

    （一）简化的流水线控制架构¶

    核心原理： - 控制信号由指令的opcode字段产生 - 与单周期实现类似，但控制信号需要随流水线传递

    控制信号 控制哪个部件 作用

    ALUOp ID EX ✅ 需要传到ID/EX
    MemRead/MemWrite ID MEM ✅ 需要传到ID/EX，再传到EX/MEM
    MemtoReg ID WB ✅ 需要一路传到MEM/WB
    RegWrite ID WB ✅ 需要一路传到MEM/WB

    传递规则：

    控制信号的生命周期：
ID阶段产生 → ID/EX保存 → EX/MEM保存 → MEM/WB保存

    减少硬件开销 不需要每个阶段都重新解码，只解码一次然后传递

    转发单元需要比较"当前指令要用到的寄存器"和"前面指令要写入的寄存器"是否冲突，所以输入包括：

    输入信号 来源 含义
    ID/EX.RegisterRs1 ID/EX 流水线寄存器 当前指令的源操作数 1 的寄存器编号
    ID/EX.RegisterRs2 ID/EX 流水线寄存器 当前指令的源操作数 2 的寄存器编号
    EX/MEM.RegisterRd EX/MEM 流水线寄存器 上一条指令的目标寄存器编号
    EX/MEM.RegWrite EX/MEM 控制信号 上一条指令是否写回寄存器
    MEM/WB.RegisterRd MEM/WB 流水线寄存器 上上条指令的目标寄存器编号
    MEM/WB.RegWrite MEM/WB 控制信号 上上条指令是否写回寄存器

    简单说：转发单元接收 当前指令的两个源寄存器号，以及 前面两条指令的目标寄存器号和写使能信号。

    Forwarding unit 的输出¶

    输出是两个 2 位的控制信号，分别控制 ALU 输入端的两个多路选择器（Mux）：

    输出信号 控制对象 含义
    ForwardA（2位） ALU 上面的 Mux 选择 ALU 第一个操作数的来源
    ForwardB（2位） ALU 下面的 Mux 选择 ALU 第二个操作数的来源

    Mux 的选择逻辑（ForwardA / ForwardB）¶

    信号值 选择来源 场景
    00 寄存器堆读出的值 正常情况，无数据冒险
    10 EX/MEM 流水线寄存器（ALU result） 上一条指令的结果刚算出来，直接前递
    01 MEM/WB 流水线寄存器（Write Data） 上上条指令的结果，从 MEM/WB 前递

    一句话总结¶

    > 转发单元输入"当前指令要读谁"和"前面指令要写谁"，判断是否有 RAW（写后读）冲突；输出两个 Mux 控制信号，让 ALU 直接使用前面指令的运算结果，而不必等到写回寄存器堆。¶

    七、Load-Use 冒险¶

    （一）什么是 Load-Use 冒险¶

    为什么 Load-Use 冒险不能用转发解决？

    普通的数据冒险（如 sub 后跟 and）可以用转发解决，因为： - sub 在 EX 阶段就计算出了结果 - 可以在同一个周期内转发给下一条指令的 EX 阶段

    但 Load 指令不一样：

    1

4
5

ld x2,20(x1)  [IF] → [ID] → [EX] →[MEM] → [WB]
                              ↑ 计算地址
                                    ↑ 数据从这里才能读取！
and x4,x2,x5         [IF] → [ID] → [EX] → ...
                                   ↑ 这里就需要x2，但数据还在内存中！

    问题本质： - Load 指令要到 MEM 阶段 才能从内存读取数据 - 下一条指令的 EX 阶段 就需要这个数据 - 即使转发，也需要"未来"的数据（不可能实现）

    十二、动态分支预测详解¶

    （一）为什么需要动态预测？¶

    核心问题：在更深的流水线和超标量处理器中，分支惩罚更严重。

    处理器类型 流水线深度 分支惩罚
    简单流水线 5级 冲刷1-3条指令
    深度流水线 10-20级 冲刷10+条指令
    超标量处理器 多发射 每周期多条指令，惩罚翻倍

    动态预测的核心思想：根据分支的历史行为来预测未来行为。

    分支历史表（Branch History Table）：

    特性 说明
    存储结构 小型缓存/表
    索引方式 用分支指令地址作为索引
    存储内容 taken（跳转）或 not taken（不跳转）

    工作流程：

    操作
    1.用分支指令地址查表，获取历史预测
    2.根据预测从目标地址或顺序地址取指
    3.冲刷流水线，翻转预测值

    打个比方：

    想象你在猜一个人明天会不会带伞： - 静态预测：不管三七二十一，总是猜"会带"或"不会带" - 动态预测：看他过去一周带伞的记录，发现他晴天不带、雨天带，然后预测

    （二）1位预测器的缺点¶

    问题场景：嵌套循环

    当前预测 实际行为 下次预测

    （三）2位预测器¶

    核心改进：只有连续两次预测错误才改变预测。

    状态机解释：

    图中有4个状态，分为两列：

    左列（预测 taken） 右列（预测 not taken）
    强 taken（深灰蓝色） 弱 taken（深灰色）

    弱 not taken not taken 变成弱 taken 变成强 not taken
    强 not taken not taken 变成弱 not taken 保持强 not taken

    （四）计算分支目标地址¶

    问题：即使有了预测器，仍然需要计算目标地址，会有1个周期的惩罚。

    解决方案：Branch Target Buffer（分支目标缓冲）

    特性 说明
    存储内容 目标地址的缓存
    索引方式 用PC（程序计数器）索引
    查找时机 指令取指时

    工作流程：

    1
2
3
    1. 用当前PC查分支目标缓冲
2. 如果命中，且该指令是分支指令，预测taken
3. 直接从缓存的目标地址取指，无需计算

    效果：

    情况 周期惩罚

    有分支目标缓冲，未命中 1周期

    十三、异常和中断¶

    （一）什么是异常和中断¶

    定义：需要改变控制流的"意外"事件。

    异常 vs 中断：

    类型 来源 例子
    异常（Exception） CPU内部产生 未定义操作码、系统调用、除零错误
    中断（Interrupt） 外部I/O控制器产生 键盘输入、定时器中断、网络数据到达

    为什么要处理？

    • 用户按了Ctrl+C → 需要终止程序
    • 程序访问非法地址 → 需要报错
    • 定时器到期 → 需要切换进程

    挑战：在不牺牲性能的情况下处理它们。

    3. 跳转到处理程序 转移控制权 默认地址：0x1C090000

    （五）流水线中的异常¶

    （四）双发射中的冒险¶

    核心问题：一个周期两条指令 → 同一时刻竞争资源 + 依赖关系翻倍

    1. 包内冒险¶

    问题：同一个发射包里的两条指令有依赖

    1
2
3
4
5
    发射包：
┌─────────────────┬─────────────────┐
│  add x1, x2, x3 │  sub x4, x1, x5 │  ← x1 有依赖！
└─────────────────┴─────────────────┘
        槽1                槽2

    解决：编译器保证包内无依赖，或者拆成两个包

    2. 包间冒险¶

    问题：当前包依赖上一个包的结果

    1
2
    周期1：add x1, x2, x3  │  nop
周期2：sub x4, x1, x5  │  ld x6, 0(x4)  ← x1、x4 都依赖上周期

    解决：转发机制仍然有效，但需要更复杂的检测逻辑

    3. Load-Use 冒险更严重¶

    问题：Load 指令要到 MEM 阶段才能读到数据

    1
2
3
4
5
6
7

周期1：nop           │  ld x1, 0(x10)
周期2：nop           │  nop           ← 强制等一周期
周期3：add x2, x1, x3 │  ...

    代价：双发射下 Load-Use 冒险浪费的是2个发射槽（相当于浪费2条指令的吞吐量）

    4. 双发射冒险总结¶

    冒险类型 原因 解决方案 代价
    包内数据冒险 同包指令有依赖 编译器调度避免 无（编译期解决）
    包间数据冒险 跨包依赖 转发机制 无（硬件解决）
    Load-Use冒险 数据还没读到 插入气泡 浪费2个槽
    结构冒险 两个ALU冲突 复制硬件资源 硬件成本

    问题：乱序执行时，如何保证异常的正确处理？

    时序： - div 先执行（没有依赖） - ld 后执行（需要访存） - 但 ld 在程序顺序上更早

    不精确异常的问题： - 如果 div 先触发异常，处理程序会认为 div 是第一条出错的指令 - 但实际上 ld 可能也会出错，且 ld 更早

    ROB 保证精确异常：

    1
2
3
4
5
6
7
8
9
    执行顺序：div → ld → add
异常检测：div 先检测到除零错误

ROB 中的处理：
1. div 的异常标记写入ROB
2. 不立即触发异常
3. 等待 div 成为 ROB 头部
4. 提交时检查到异常，触发异常处理
5. 此时所有之前的指令都已提交

    关键：异常只在提交阶段触发，保证精确性。

    6. 预约站 vs ROB 的分工¶
    组件 职责 数据流向
    预约站 缓冲指令，等待操作数 寄存器/ROB → 预约站
    ROB 缓存结果，保证顺序提交 功能单元 → ROB → 寄存器

    类比： - 预约站 = 餐厅的"等位区"，顾客（指令）等待食材（操作数） - ROB = 餐厅的"取餐区"，菜品（结果）按顺序给顾客

    内存停顿的计算：

    \[CPI_{内存} = \text{Miss次数/指令} \times \text{Miss惩罚}\]

    10. Cache Miss 与流水线设计的权衡¶
    设计选择 对Cache Miss的影响 代价
    增大Cache 降低Miss率 面积、功耗

    常见面试题¶

    Q1: 为什么Load-Use冒险不能只用转发解决？

    A: 因为Load指令要到MEM阶段才能从内存读到数据，而需要使用该数据的指令在EX阶段就需要它。即使转发，也需要"未来"的数据，物理上不可能。

    Q2: 2位预测器为什么比1位预测器好？

    A: 对于嵌套循环，1位预测器每次循环结束和下次循环开始都会预测错误。2位预测器需要连续两次错误才改变预测，避免了这个问题。

    Q3: 异常处理和分支预测错误有什么共同点？

    A: 都需要： 1. 冲刷流水线 2. 保存当前状态（PC、原因） 3. 跳转到新地址 4. 可以复用大部分硬件

    Q4: 为什么说流水线提高了吞吐量但不减少延迟？

    A: - 吞吐量：每周期完成的指令数增加（理想情况1条/周期） - 延迟：单条指令从开始到完成的时间不变（5个周期） - 流水线是"并行处理多条指令"，不是"加速单条指令"

    Q5: 什么是精确异常？为什么重要？

    A: - 精确异常：异常发生时，之前的指令都已完成，之后的指令都未执行 - 重要性：简化异常处理程序的逻辑，保证程序语义正确 - 实现难度：乱序执行、多发射等优化使得精确异常难以维护
