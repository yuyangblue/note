    第九章 虚拟内存系统（VM Systems）¶

    依据：CMU 15-213 第 18 讲课件（18-vm-systems.pptx，中译版已交付桌面课件目录）+ 《深入理解计算机系统》原书第 3 版第 9.6–9.7 节。

    上一篇《第 9 章 虚拟内存概念》讲了"虚拟内存是什么、地址翻译由哪些部件组成（MMU / TLB / 页表）"。本篇用一个小参数系统把整条地址翻译流水线完整走一遍，再看真实 Core i7 + Linux 是怎么落地的。

    1. 一个简化的内存系统示例¶

    为了把"虚拟地址 → 物理地址 → 缓存字节"整条流水线走通，课件先造了一个参数很小的假想机器，方便手算。

    1.1 地址划分¶

    参数：

    • 虚拟地址 14 位，物理地址 12 位；
    • 页大小 \(P = 64\) 字节，即 \(\log_2 P = 6\)；
    • 所以 VPN（虚拟页号）= 14 − 6 = 8 位，VPO = 6 位；
    • PPN（物理页号）= 12 − 6 = 6 位，PPO = 6 位。

    这套小系统里 TLB、页表、L1 缓存都很小，便于手动追踪每一步命中还是不命中。

    1.2 TLB¶

    TLB 是 MMU 内部的小缓存，缓存 VPN → PPN 的映射。这个示例机器的 TLB：

    • 16 项、4 路组相联；
    • TLB 索引 TLBI 用 VPN 的低 \(\log_2(16/4) = 2\) 位；
    • TLB 标记 TLBT 用 VPN 的剩下 6 位。

    TLB 每一项里都有一个有效位，以及缓存的 PPN。MMU 拿 VPN 的低位去索引 TLB 组，再比较 TLBT 标记位，命中就直接拿到 PPN；不命中则要去内存里查真正的页表。

    1.3 页表¶

    这个示例系统只有一级页表，共 256 项（对应 8 位 VPN）。每项：

    • 有效位；
    • PPN（6 位）；
    • 一些保护位（R/W、U/S 等）。

    注意课件里只列出了前 16 项，其余省略。有效位为 0 的项对应"还没分配的虚拟页"，一旦访问就会触发缺页。

    1.4 L1 缓存¶

    • 16 组、每组 1 行（直接映射）、块大小 4 字节；
    • 物理地址索引；
    • 块内偏移 CO 占 2 位（\(\log_2 4\)）；
    • 缓存索引 CI 占 4 位（\(\log_2 16\)）；
    • 缓存标记 CT 占剩下的 6 位。

    注意这个小例子里缓存标记 CT 恰好等于 PPN（都是 6 位），老师课上特意强调这只是巧合——如果缓存组数再多一点，CI 位数就会"溢出"到 PPN 那几位，CT 自然就和 PPN 对不上了。两者没有必然联系。

    1.5 一次完整的地址访问流程¶

    给定一个虚拟地址，硬件按下面的顺序跑：

    1. 拆虚拟地址：VPN = 虚拟地址右移 6 位；VPO = 低 6 位。
    2. 查 TLB：用 TLBI 选组，比较 TLBT。
    3. 命中 → 直接拿到 PPN；
    4. 不命中 → 用 VPN 查内存里的页表，把得到的 PPN 填回 TLB。
    5. 拼物理地址：PA = PPN ‖ PPO（PPO 直接复用 VPO，因为页内偏移在翻译前后不变）。
    6. 查缓存：用 CI 选行，比较 CT 标记。命中就返回这 4 字节里想要的那一字节；不命中就去主存取一块回来。

    课件用三个例子（虚拟地址 \(0x03D4\)、\(0x0020\)、\(0x0020\) 的不同情形）手算了 VPN/TLBI/TLBT/TLB 命中、PPN、物理地址、CI/CT/缓存命中、最终取出的字节，是教材配套练习题的标准考法。

    1.6 手算示例 #1：虚拟地址 \(0x03D4\)¶

    已知条件（见前面 TLB、页表、缓存三张表）：

    • TLB 共 16 项、4 路组相联，TLBI 取 VPN 低 2 位；
    • 页表共 256 项，前 16 项里 VPN=0x0F 对应的 PTE 是有效位 1、PPN=0x0D；
    • L1 缓存 16 行、块大小 4 字节、直接映射，缓存第 1 行恰好有效、标记 CT=0x35、那一行存的字节是 0x36。

    第一步：拆虚拟地址。

    \(0x03D4 = 0000\,0011\,1101\,0100_2\)（16 位写全，实际只有低 14 位有效）。

    • VPO = 低 6 位 = 010100 = \(0x14\)；
    • VPN = 高 8 位 = 00001111 = \(0x0F\)。

    第二步：拆 VPN，查 TLB。

    • TLBI = VPN 低 2 位 = 11 = \(0x3\)，所以查 TLB 第 3 组；
    • TLBT = VPN 高 6 位 = 000011 = \(0x03\)。

    在 TLB 第 3 组的 4 个项里找标记位等于 \(0x03\) 的那一项 → 命中（Y），不缺页。直接拿到 PPN = \(0x0D\)。

    第三步：拼物理地址。

    PPO 直接复用 VPO（因为 64 字节内的偏移在翻译前后不变）：

    \[ \text{PA} = \text{PPN} \ll 6 \mid \text{PPO} = 0x0D \ll 6 \mid 0x14 = 0x340 \mid 0x14 = 0x354 \]

    第四步：拆物理地址，查缓存。

    PA = \(0x354\)，12 位：

    • CO = 低 2 位 = 00 = \(0\)（块内字节偏移）；
    • CI = 接下来 4 位 = 0101 = \(5\)（选缓存第 5 组）；
    • CT = 高 6 位 = 001101 = \(0x0D\)。

    查缓存第 5 组：有效、标记正好是 \(0x0D\) → 命中。这一行 4 字节里第 CO=0 个字节就是要取的数，结果是 \(0x36\)。

    整条链路：VA \(0x03D4\) → TLB 命中 → PA \(0x354\) → 缓存命中 → 字节 \(0x36\)。

    1.7 手算示例 #2：虚拟地址 \(0x0020\)（TLB miss + 缓存 miss）¶

    老师课上接着算了第二个例子，专门演示"两步都不命中"的情况。

    已知 TLB 第 0 组里有一项 tag=0 但有效位为 0；页表 VPN=0 的 PTE 有效位=1、PPN=\(0x28\)；缓存第 8 组里那行的 tag 是 \(0x24\)。

    第一步：拆虚拟地址。

    \(0x0020 = 0000\,0000\,0010\,0000_2\)：

    • VPO = 低 6 位 = 100000 = \(0x20\)；
    • VPN = 高 8 位 = \(0x00\)。

    第二步：查 TLB。

    • TLBI = VPN 低 2 位 = 00 = \(0\)，查 TLB 第 0 组；
    • TLBT = VPN 高 6 位 = \(0x00\)。

    第 0 组里找 tag=0：tag=3 不匹配、tag=9 不匹配、有一个 tag=0 但有效位为 0 → TLB miss（tag 撞了但有效位是 0，不算命中）。必须出芯片走内存查页表。

    第三步：查页表，拼物理地址。

    页表第 0 项有效，PPN = \(0x28\)：

    \[ \text{PA} = 0x28 \ll 6 \mid 0x20 = 0xA00 \mid 0x20 = 0xA20 \]

    第四步：查缓存。

    PA = \(0xA20\)：

    • CO = 低 2 位 = \(0\)；
    • CI = 接下来 4 位 = 1000 = \(8\)（查缓存第 8 组）；
    • CT = 高 6 位 = \(0x28\)。

    第 8 组里那行 tag 是 \(0x24\)，不等于 \(0x28\) → 缓存 miss。这次必须从主存取块。

    整条链路：VA \(0x0020\) → TLB miss（走页表拿到 PPN \(0x28\)）→ PA \(0xA20\) → 缓存 miss（走主存）。这个例子展示了最坏情况——两级缓存都不命中。

    2. 真实案例：Intel Core i7 / Linux¶

    小例子走完了，看真实 CPU。

    2.1 硬件层级¶

    Core i7 的内存层级比小例子复杂得多：

    • L1 数据 TLB：64 项、4 路（缓存 VPN→PPN）；
    • L1 指令 TLB：128 项、4 路；
    • L1 数据缓存：32 KB、8 路；
    • L1 指令缓存：32 KB、8 路；
    • L2 统一缓存：256 KB、8 路；
    • L3 统一缓存：8 MB、16 路，所有核心共享；
    • 主存 DRAM。

    地址空间是 48 位虚拟地址、4 KB 页，所以 VPO = 12 位，VPN = 36 位。

    老师课上给了各级缓存的典型访问延迟，帮建立直觉：L1 大约 4 个周期、L2 大约 10 个周期、L3 大约 30–50 个周期（已经要穿过片上互连到共享缓存），主存则是几百个周期。L1 指令 TLB（128 项）比数据 TLB（64 项）大，老师猜测原因是"取指失败的惩罚更大"——I-TLB miss 会让整个取指流卡住，而 D-TLB miss 至少还能继续预取后面的指令。

    为什么还要有 L2 TLB？如果只做一个巨大的 L1 TLB，你不知道程序是数据页访问多还是指令页访问多——把晶体管全堆在 D-TLB 上，遇到指令密集的程序就会容量缺失；反过来也一样。加一层 L2 TLB 相当于"对冲赌注"：L1 miss 的代价不大（L2 只要十几周期），但换来了对两种工作负载都不偏科。

    2.2 端到端地址转换¶

    虚拟地址进来后，MMU 先查 L1 TLB；TLB 不命中就用 36 位 VPN 去走四级页表。每级 VPN 切 9 位，CR3 寄存器指向一级页表的物理基地址。

    2.3 四级页表¶

    • 虚拟地址 48 位 = VPN1(9) ‖ VPN2(9) ‖ VPN3(9) ‖ VPN4(9) ‖ VPO(12)；
    • CR3 指向 L4 页表（最外层）；
    • VPN1 索引 L4 PTE，拿到 L3 页表物理地址；
    • VPN2 索引 L3 PTE，拿到 L2 页表地址；
    • VPN3 索引 L2 PTE，拿到 L1 页表地址；
    • VPN4 索引 L1 PTE，拿到最终 PPN；
    • 拼上 VPO 得到物理地址。

    第 1~3 级 PTE 指向的是"下一级页表"（物理地址是一个页表的基地址），第 4 级 PTE 指向的才是真正的物理页。

    每级 PTE 的关键位：

    • P：存在位，0 表示这一级页表或这个页不在物理内存；
    • R/W：读写权限；
    • U/S：用户态/内核态；
    • A：访问位（被 TLB/缓存走过时硬件置 1，OS 用它做页面置换）；
    • D：脏位（写过才置 1，OS 决定换出时要不要写回磁盘）；
    • G：全局位（标记"所有进程都共享的页"，切换进程时 TLB 不用刷掉它）；
    • XD（eXecute Disable）：执行禁止位，硬件上禁止这条物理页被当指令执行。这是现代系统防栈溢出攻击的关键——栈页的 PTE 把 XD 置 1，攻击者即使把 shellcode 拷到栈上跳过去跑，CPU 也会直接拒绝执行。

    四级页表每级覆盖的范围可以心算一下：每级 9 位索引，即 \(2^9 = 512\) 项，每项管一个 \(4\text{ KB}\) 的页，所以最里一级（L1）覆盖 \(512 \times 4\text{ KB} = 2\text{ MB}\)；往外一级再乘 \(512\)，L2 覆盖 \(1\text{ GB}\)，L3 覆盖 \(512\text{ GB}\)，最外层 L4 覆盖整个 \(256\text{ TB}\) 虚拟地址空间。实际进程几乎不会用满整个地址空间，所以最外层页表项里大部分都是"不存在"，OS 完全不为它分配下一级页表——大多数程序只需初始化第一级（L4）的少数几项，这就是多级页表省内存的本质。

    CR3 是 CPU 里一个特殊寄存器，存当前进程一级页表的物理基地址。进程切换时 OS 做的一件关键事就是把 CR3 换成新进程的页表基地址——CR3 一切，整个虚拟地址空间就换了，这也是为什么两个进程的指针虽然长得一样（比如都是 0x40000000），但实际指向完全不同的物理内存：它们用的是不同的页表。

    2.4 一个巧妙的加速：虚拟索引、物理标记¶

    L1 缓存用 CI 选行。理论上应该先把虚拟地址翻译成物理地址，再用 CI 查缓存——但这样缓存查找就排在 MMU 后面，慢。

    Core i7 的设计让 CI 这几位正好落在 VPO 范围内。VPO 在地址翻译前后是不变的，所以：

    • 地址翻译（查 TLB、查页表）和缓存索引（用 CI 选行）可以并行开始；
    • 翻译完成、PPN 拿到之后，只用它去做 CT 标记比较；
    • 这就是"虚拟索引、物理标记"（VIPT, Virtually Indexed, Physically Tagged）。

    代价是：缓存大小被精心限制过——如果缓存行多到 CI 越过 VPO 边界，就要等翻译完才能索引，VIPT 就失效了。

    这里的 CI+CO 位数之和正好等于 VPO 位数，不是小例子里那种巧合，而是硬件设计的硬约束。Core i7 的 L1 数据缓存正好是 64 字节块（CO=6 位）、8 路（CI=6 位），CI+CO=12，正好等于 4 KB 页对应的 VPO 位数。这也是 L1 缓存做不大的根本原因——组数一旦增加，CI 位数就要往上顶，一旦超过 12 位就会撞到 VPN 部分，硬件就没法再用虚拟地址索引了。所以你看到现代 CPU 的 L1 数据缓存基本都是 32 KB 左右，不是不想做更大，是 VIPT 的物理上限卡在这里。

    3. Linux 进程的虚拟地址空间¶

    3.1 一个进程看到的内存布局¶

    从低地址到高地址：

    • 程序代码 .text（只读）；
    • 已初始化数据 .data；
    • 未初始化数据 .bss；
    • 运行时堆（由 malloc 通过 brk 向上扩张）；
    • 内存映射区域（共享库、mmap 映射的文件）；
    • 用户栈（高地址，向下增长，%rsp 指向栈顶）；
    • 最上面是内核虚拟内存（用户态不可访问）。

    堆和栈之间留了大片空洞，需要时再扩张。

    3.2 Linux 用 vm_area_struct 描述区域¶

    Linux 不给每个页都建一个描述结构，而是把连续、性质相同的一段虚拟地址叫一个区域（area），用一个 vm_area_struct 描述：

    • vm_start、vm_end：这段区域的起止地址；
    • vm_prot：权限（读/写/执行）；
    • vm_next：串成链表；
    • 跟 task_struct → mm_struct → mmap 挂在一起。

    一个进程的若干个 vm_area_struct 串成链表，分别对应代码段、数据段、堆、共享库映射、栈……课件里为了好懂画的是链表，实际 Linux 为了在区域数量很多时还能快速按地址查找，把它们组织成一棵红黑树——按虚拟地址排序，故障地址一进来就能对数时间定位到所属区域，而不是线性扫完整条链表。

    3.3 缺页异常处理¶

    当 CPU 触发缺页，内核拿到故障虚拟地址 CR2 寄存器里的值，做三件事判断：

    1. 查这个地址属于哪个 vm_area_struct：用红黑树对数时间定位。如果地址不属于任何区域（野指针、栈越界）→ 直接给进程发 SIGSEGV 段错误，进程崩掉。
    2. 查权限：地址属于某段，但这次访问权限不对（比如往只读的 .text 写、用户态访问内核页）→ 同样发 SIGSEGV。
    3. 地址合法、权限也对，但 PTE 存在位为 0（页还没分配，或者被换出到磁盘）：分配一个物理页，从文件/匿名对象填好内容，建 PTE，返回用户态让那条指令重新执行。

    三种情况里前两种都是"程序有 bug"，最后一种才是"正常按需分配"。但 Linux 对前两种都只发同一个 SIGSEGV，进程从外部看不出到底是哪一种。

    4. 内存映射（Memory Mapping）¶

    4.1 基本思想¶

    内存映射：把一段虚拟内存区域和一个磁盘对象"绑定"起来，让这段虚拟页的初始内容来自那个对象。这样做的好处是——物理页按需才分配（第一次访问才缺页），而且多个进程可以映射同一个对象，自动共享物理内存。

    可以绑定的对象有两类：

    • 普通文件：虚拟页的内容直接来自文件的某一段（比如可执行文件的 .text 段对应程序代码）；
    • 匿名文件：没有磁盘后端，第一次缺页时内核分配一个全零物理页（栈、堆、.bss 都是这种）。匿名文件本质上是内核的一个诡计——它假装磁盘上有一个"全零文件"，第一次访问时缺页处理程序直接拿一个全零物理页填上，让所有"需要从零开始的内存段"都走同一套缺页路径，不需要给 .bss 在磁盘上真存一份全零数据。

    4.2 共享对象¶

    两个进程把同一个共享对象映射进自己的虚拟地址空间，它们的某些虚拟页指向同一个物理页。两边任何一个进程写这个物理页，另一个进程都能看到——这就是共享库、进程间共享内存的底层机制。两个进程里这个对象的虚拟地址可以不同，重要的是物理页被 PTE 共享。

    4.3 私有对象与写时复制（COW）¶

    共享对象是"写了大家都看得到"，但有些场景需要"两个进程一开始共享同一份物理页，一旦某一个写，就立刻复制出一份私有副本"。这就是写时复制（Copy-On-Write, COW）。

    做法：

    1. 父进程和子进程的 PTE 都指向同一个物理页，但 PTE 被标记为只读、区域标记为"私有 COW"；
    2. 一开始没有真正复制物理页，两个进程共享同一份；
    3. 任何一个进程尝试写这个页，会触发保护异常；
    4. 内核在异常处理里：分配一个新物理页，把旧页内容拷过去，把触发写的那个进程的 PTE 改指向新页，并改成可读写；
    5. 异常处理返回，指令重新执行，这次写就落到私有副本上。

    关键点：拷贝尽可能延后。fork 创建子进程时不需要立刻复制整个地址空间，所有页都先以 COW 方式共享，真正写时才复制——这就是 fork 这么快的原因。

    4.4 用 VM 的视角重看 fork 和 execve¶

    • fork()：内核为新进程复制 mm_struct、所有 vm_area_struct、所有页表，但不复制物理页——所有 PTE 都设成只读 + COW。父子共享物理页，谁写谁触发复制。
    • execve(filename)：它不创建新进程，而是在当前进程里扔掉原来的 vm_area_struct 和页表，按新程序重建：代码段和已初始化数据段映射到可执行文件，.bss 和栈映射到匿名全零页，然后把 CPU 栈切到新程序的入口。注意 execve 也不把整个程序拷贝进内存——它只是建好虚拟地址映射，哪一页第一次访问才缺页从文件读进来，这叫按需加载。

    共享库 libc.so 的代码段是 MAP_SHARED，所有进程共享同一份物理页；但 libc 里有些数据段（比如随机数生成器的内部状态）是每个进程独立的，那部分就用 MAP_PRIVATE + COW：一开始物理页共享，谁要写就复制一份。同一份 .so 文件里不同段可以用不同映射标志，这就是为什么一个库能同时支持共享代码和私有状态。

    4.5 用户态 mmap API¶

    1
    void *mmap(void *start, int len, int prot, int flags, int fd, int offset);
    • start：建议映射到的虚拟地址（内核通常忽略，自己选）；
    • len：映射多长；
    • prot：权限（PROT_READ / PROT_WRITE / PROT_EXEC）；
    • flags：MAP_PRIVATE（私有 COW）还是 MAP_SHARED（共享）、MAP_ANONYMOUS（匿名、无文件）；
    • fd、offset：映射哪个文件、从文件哪个偏移开始。

    munmap 把一段映射拆掉。教材给了一个用 mmap 把整个文件读进内存再写出去的例子：传统 read/write 流程是"磁盘 → 内核页缓存 → 用户缓冲区 → 内核 → 网卡"，中间用户缓冲区是一次多余的拷贝；用 mmap 把文件映射进虚拟地址空间后，直接对映射区 write 到 stdout，数据从内核页缓存走到网卡，省了一次内核→用户→内核的来回。

    5. 小结¶

    虚拟内存不是抽象概念，它是一条硬件流水线：虚拟地址 → TLB → 多级页表 → 物理地址 → 缓存，每一步都有自己的小缓存和命中规则。Linux 用 vm_area_struct 把一个进程的虚拟地址空间描述成若干区域，缺页时按区域查权限、按需分配物理页。内存映射把虚拟页和磁盘对象绑定；共享对象多进程共享物理页，COW 让 fork 可以"先共享、写时才复制"。
