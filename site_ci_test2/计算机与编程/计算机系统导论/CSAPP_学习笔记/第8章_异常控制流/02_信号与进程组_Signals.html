    1. 外壳（Shell）与进程层次（15 讲热身）¶

    1.1 Linux 进程层次结构¶

    Linux 系统启动后，进程按"祖孙"关系组成一棵树：

    • [0] 号进程：系统启动时最先运行的进程（调度进程，PID=0，是所有进程的祖先）。0 号进程是最基础的进程，整个操作系统最先启动的就是它。
    • init 进程（PID 1）：由 0 号创建，是所有其他进程的"老祖宗"；永不终止，负责收养孤儿进程（见第 8 章进程部分"回收子进程"）。
    • 从 init 繁衍出两类进程：
    • 守护进程（daemon）：后台常驻、提供服务的进程，如 httpd（Web 服务器）。
    • 登录外壳（login shell）：用户登录后启动的命令解释器。
    • 外壳再创建子进程、孙进程——你每敲一条命令，shell 就 fork 一个子进程去执行它（详见 1.2）。

    守护进程名字的规律：很多守护进程名字以字母 d 结尾（daemon 的 d）：httpd（HTTP 服务）、sshd（远程登录服务）等。Windows 上叫"服务"（Service），Unix 上叫"守护进程/精灵进程"。你输网址时最前面那个 http:// 里的 HTTP 就是"超文本传输协议"（HyperText Transfer Protocol）：超文本 = 不只文字，还能传图片、音频、视频的"高级文本"；:// 表示协议分隔符。

    另外，ps/top 命令可以查看进程；pstree 命令可以把进程树画出来（课件 p4 也提示了）。

    外壳（shell）：一种应用程序，代表用户运行其他程序——它本身不是内核，而是一个普通进程，靠 fork + execve + waitpid 实现"读命令 → 执行命令"的循环。

    char buf[MAXLINE];   /* 存放修改后的命令行 */

            }
        }

            if (waitpid(pid, &status, 0) < 0)

    • builtin_command 判断是不是内置命令（本示例 shell 只有 quit；真实 shell 还有 pwd、jobs、fg 等）。

    直观理解：shell 命令的"分身"逻辑。你在 shell 里敲的任何命令（ls、clear……），其实都是 shell fork 一个子进程再去 exec 那个程序执行的，shell 自己只负责等你执行完（前台）或记下 PID（后台）。这就是"父进程接单、子进程干活"的模型，和服务器模型完全一致。

    前台 vs 后台：前台程序占着终端，你不能再敲命令，Ctrl-C 可以直接终止它；后台程序（命令末尾加 &）不占终端，你想终止它只能 kill 发信号。后台程序的输出如果不想要，可以重定向到黑洞 /dev/null。

    前台和后台在 shell 代码里的差别其实只有一行——前台作业父进程会 waitpid 等它结束，后台作业直接打印 PID 就继续下一轮读命令。没有别的本质区别。但这一行区别就埋下了后面 SIGCHLD 的伏笔：前台作业父进程已经 wait 回收了，后台作业没人收尸，只能靠后面要讲的 SIGCHLD 信号通知 shell 来补回收。

    1.3 简单外壳示例的问题：后台作业变成僵尸¶

    注：此处课件 p7 为纯文字页，内容直接列在下面，不插图。

    我们的示例 shell 能正确等待并回收前台作业，但后台作业呢？

    • 后台作业终止时会变成僵尸进程；
    • 永远不会被回收，因为 shell（通常）不会终止；
    • 会造成资源泄漏，可能耗尽内核内存（进程表项、PID）。

    ECF 来救场！ 解决办法：异常控制流——当后台进程完成时，内核会中断常规处理来提醒 shell。在 Unix 中，这种提醒机制称为信号（signal）。这正是本讲的主角。

    2. 信号基础（8.5.1）¶

    2.1 什么是信号¶

    信号（signal）：一条小消息，用于通知进程系统中发生了某类事件。

    • 类似异常和中断：异常是硬件 → 内核的通知，信号是内核（或进程）→ 进程的通知，都是"控制流突变"。
    • 由内核发送（有时应另一个进程的请求）。
    • 信号类型由小整数 ID（1–30）标识；信号中只包含它的 ID 和"已到达"这一事实，不携带数据。

    直观理解：信号就是个小整数标签。信号本质上就是一个 1–30 的小整数。操作系统里很多东西都用整数表示：进程 ID 是整数、文件描述符是整数、信号也是整数。信号很"轻"——它不像消息队列那样能传内容，它只告诉你"某种事件发生了"，具体怎么办由你（或默认动作）决定。

    2.2 常用信号表¶

    信号编号 → 名称 → 默认动作 → 对应事件（课件 p10 表格）：

    编号 名称 默认动作 对应事件

    代码里为什么写 SIGINT 而不是数字（直观理解）：SIGINT 是一个宏（符号常量），在头文件 <signal.h> 里定义为 #define SIGINT 2——它本质就是整数 2，只是给这个数字起了个能读的名字。写 signal(SIGINT, handler) 和写 signal(2, handler) 完全等价。用名字的好处：① 可读——一看就知道是"键盘中断（Ctrl-C）"，而不是神秘的数字 2；② 可移植——不同 Unix 系统上同一个信号名的编号可能不同（例如 SIGUSR1 在有的系统是 10、有的可能是 30），但名字永远一样，代码不用改。信号名的规律：SIG + 事件缩写，如 INT=interrupt（Ctrl-C）、KILL=kill、SEGV=segmentation violation（段违规）、ALRM=alarm（定时器到）、CHLD=child（子进程）、TERM=terminate（请终止）、STOP/CONT=停止/继续。

    两个"你管不了"的信号：SIGKILL（9） 和 SIGSTOP（19） 是两个不能被忽略、不能被捕获的信号：SIGKILL 是"你必须死"，SIGSTOP 是"你必须停"。为什么？如果程序能把所有信号都忽略，那它就连内核都管不了、无法无天了——操作系统必须保留"最后手段"来掌控任何进程。

    SIGTERM（15）vs SIGKILL（9）：SIGTERM 是"礼貌地请你去死"，程序可以捕获它、做点清理再退出（很多服务器用这个做优雅停机）；SIGKILL 是"强行弄死"，程序没有任何机会反抗。默认动作都是终止，区别在于能不能被捕获/忽略。

    SIGCHLD（17）：子进程终止或停止时，内核自动给父进程发这个信号。父进程如果忽略它，子进程就没人收尸 → 变成僵尸进程。这正是上一讲"僵尸进程"和本讲信号的衔接点。

    停止 ≠ 终止：SIGTSTP/SIGSTOP 是"暂停"（挂起），进程还在内存里，可以靠 SIGCONT 继续跑；SIGINT/SIGTERM/SIGKILL 是"终止"，进程结束。Ctrl-C 是终止，Ctrl-Z 是挂起——两个键完全不同。

    3. 发送信号（8.5.2）¶

    3.1 发送信号的概念¶

    发送（递送）信号：内核通过更新目标进程上下文中的某些状态，向目标进程发送信号。

    内核因以下两种原因之一发送信号：

    1. 内核检测到系统事件：如除零（SIGFPE）、子进程终止（SIGCHLD）、非法内存引用（SIGSEGV）。
    2. 另一进程调用了 kill 系统调用，显式请求内核向目标进程发送信号。

    直观理解：kill 不是"杀死"，是"发信号"。kill 这个名字有误导性——它其实是"请内核帮我给某进程发一个信号"。发 9 号（SIGKILL）才会"杀死"，发别的号（如 2 号 SIGINT）可能只是通知。信号都是内核发的，kill 只是"告诉内核去发"。

    同样地，signal() 这个名字也有误导——它并不"发"任何信号，只是"登记一下：以后收到 signum 时改成这个动作"。这两个 API 都是早期 Unix 随手起的名，跟实际行为对不上，别被字面意思骗了。

    3.2 进程组（发送信号的目标）¶

    进程组（process group）：每个进程恰好属于一个进程组，进程组用一个进程组 ID（PGID）标识。

    • 图中 Shell 自身：pid=10、pgid=10（默认进程组 ID = 进程 ID）。
    • 前台作业（pid=20，pgid=20）下有两个子进程 pid=21、pid=22，它们的 pgid 都是 20——父子一起算"前台进程组 20"。
    • 后台作业 #1（pgid=32）、后台作业 #2（pgid=40）各自成组。

    直观理解：进程有两个"号"。每个进程既有进程 ID（PID，自己是谁），又有进程组 ID（PGID，属于哪一组）。默认进程组 ID 等于创建它的父进程的进程组 ID。为什么要有"组"？因为想一次给一群进程发信号——比如你把一个作业跑在前台，它 fork 了一堆子进程，按一次 Ctrl-C 希望整组都死，而不是只死父进程。

    进程组里到底装哪些进程？（不是只有"一个父 + 它的直接子进程"）

    组的规则是继承 + 按作业划分，而不是"严格的一父多子"：

    • 管道命令同组（兄弟关系）：执行 ls | grep foo | sort 时，shell 把整条管道命令算一个作业，为它建一个进程组——三个程序是兄弟（都是 shell 的子进程），但 PGID 相同。所以进程组装的是一"条命令"的所有进程，父子、兄弟都行。
    • 祖孙三代同组（继承）：子进程 fork 出孙进程，孙默认继承同一 PGID。./forks 17 里父进程 fork 一个子进程，整组就父+子两个；若子进程再 fork，三个都在组里。
    • 一个父进程可以同时有多个组的子进程：shell 每执行一条命令就新建一个作业/进程组（前台一个组、后台每个作业各一个组），所以 shell 的子进程分散在不同组里。
    • 组长（leader）：进程组 ID 通常等于组内第一个进程（组长）的 PID。组长可以退出，组还在（剩下成员继续同组）。
    • setpgid 能"换组"：进程不是永远锁死在继承来的组里，setpgid(pid, pgid) 可以把它挪到别的组（shell 建作业、脱离终端控制都靠它）。

    一句话总结：进程组 ≈ 一次作业（一条命令行）。默认大家跟着组长走，组长是作业里最先出生的进程。

    3.4 从键盘发送信号（Ctrl-C 与 Ctrl-Z）¶

    键入 ctrl-c（或 ctrl-z）会使内核向前台进程组中的每个作业发送信号：

    • ctrl-c → SIGINT：默认动作是终止每个进程。

    4. 接收信号（8.5.3）¶

    4.1 接收信号的含义与三种反应¶

    接收信号：当内核强制目标进程以某种方式对信号的递送作出反应时，目标进程就"接收"了信号。

    可能的反应方式：

    1. 忽略信号（不做任何事）。
    2. 终止进程（可选择转储 core——保存崩溃现场便于调试）。
    3. 捕获信号：通过执行称为信号处理程序（signal handler）的用户级函数来处理。

    直观理解：三大反应的"人生选择"。收到信号你有三条路：①不理它（忽略）；②去死（终止，Windows 程序崩溃时问你"要不要把现场发给微软"就是在转储 core，方便调试定位 bug）；③接住它，跑自己的处理函数（捕获）。第三种就像硬件异常处理：主程序正跑着，信号一来，CPU 跳到处理程序，执行完再跳回主程序继续。

    • 进程忽略该信号。

    /* sigint.c */
void sigint_handler(int sig) /* SIGINT 处理程序 */
{

    /* 等待信号的接收 */
    pause();
    return 0;
}

    这个程序在干嘛（直观理解）：这是一个"信号劫持"演示——程序把自己比作一颗炸弹，用 signal(SIGINT, sigint_handler) 把 Ctrl-C 的默认动作（终止）换成了自己的处理程序，于是按 Ctrl-C 不但杀不死它，还会触发它"嘲讽"你三句话，最后自己退出。

    1. signal(SIGINT, sigint_handler)：安装处理程序——告诉内核"SIGINT 来了别默认终止，去调用我的函数"；
    2. pause()：挂起等待信号——进程睡过去，直到收到任意信号才醒来；
    3. 你按 Ctrl-C：内核向前台进程组发 SIGINT → 进程收到 → 不再终止，而是跳去执行 sigint_handler；
    4. 处理程序打印"你以为用 ctrl-c 就能停掉炸弹吗？" → 睡 2 秒 → "好吧..." → 睡 1 秒 → "好的。:-)" → exit(0) 主动结束。

    注意两点：① 处理程序最后 exit(0) 是它自己主动结束进程（"嘲讽完自己投降"）——如果只是 return，控制权会交回 main，pause() 返回 -1（errno=EINTR）后 main 继续 return 0，程序照样退出，只是少了"由处理程序决定命运"的效果；② 处理程序里用了 printf/fflush/exit，它们都不是异步信号安全函数（G1 准则，见 6.3 节）——printf 依赖的缓冲区和内部锁可能正被主程序占用，信号一来就被打断，数据可能错乱。正式的安全写法是 6.4 的 sigintsafe.c：用 Sio_puts + _exit。

    EINTR 是什么、为什么会出现：pause() 返回 -1 时 errno 被设为 EINTR（Interrupted system call）。这不是错误，而是"被信号打断"的标准返回方式。早期 Unix 上凡是慢系统调用（slow syscall）——即调用后会阻塞等待外部事件的系统调用，如 read 等磁盘数据、accept 等连接、pause 等信号——只要在阻塞期间被信号打断，内核就直接让它返回 -1 并置 errno=EINTR，不会自动重试。所以用户代码里写 read(...) 时必须自己判断 errno == EINTR 然后循环重试，否则一次 Ctrl-C 就让 read 莫名其妙地"失败"了。现代 sigaction 带 SA_RESTART 标志后会自动重启这类慢系统调用，这也是 csapp.c 里的 Signal 包装默认带 SA_RESTART 的原因。

    pause() 具体怎么挂起（直观理解）：pause() 让调用进程进入睡眠（sleeping）状态——内核把进程从"运行队列"挪到"等待队列"，CPU 不再给它分配时间片，进程不消耗 CPU。它一直睡到"有信号被递送且被接收（处理）"：

    1. 信号到达，内核唤醒进程；
    2. 如果该信号装了处理程序，进程先执行处理程序（此时进程是"运行"状态，跑的是你的 handler 代码）；
    3. 处理程序返回后，pause() 返回 -1 并置 errno = EINTR（"被信号中断"）——这是它的正常返回值，不是错误；
    4. main 继续往下执行 return 0，程序结束。

    所以 sigint.c 里 pause() 的作用是制造一个"等着被打断"的睡眠点：不装处理程序时，Ctrl-C 一发 SIGINT 进程直接死；装了处理程序后，Ctrl-C 打断 pause 的睡眠，把控制权交给 handler——"捕获"的完整闭环就是这么走通的。

    为什么说 pause 有竞态风险（8.2 节细讲）：如果信号在 pause() 之前就到达了，进程会一直睡下去——信号已经"错过"，pause 不会重放。具体时间窗口是：主程序刚检查完 while (!pid) 发现 pid 还是 0、正准备调用 pause() 的那一瞬间，SIGCHLD 恰好到达并被处理程序跑完（pid 已经被设成非 0），然后主程序才进入 pause()——此时信号已经处理完了，pause() 永远等不到下一个信号，进程就死锁在那里。这就是"检查标志"和"挂起"两步之间不是原子操作的经典竞态。显式等待信号要用 sigsuspend（原子地"换掩码 + 挂起"），见 8.2 节。

    信号处理程序作为并发流：处理程序是一个独立的逻辑流（不是进程），与主程序并发运行。

    看图理解：进程 A 的 main 正在跑用户代码 → 信号被递送给 A → 上下文切换，A 进入内核代码 → 信号被 A 接收 → A 执行用户代码（处理程序） → 处理程序返回 → 回到内核代码 → 再回到用户代码（main）继续。处理程序这段"插队"执行的用户代码，就是与 main 并发的一条逻辑流。

    教材原图解读（进程A 两栏 + 进程B）：这张图里"进程A"出现了两次，并不是两个进程——左边一栏是进程 A 的主程序流（while(1); 死循环，main 的正常执行），中间一栏是进程 A 的 handler 处理程序流。两条流同属进程 A：同一个 PID、同一个地址空间，handler 只是信号到达时在进程 A 内部"插队"执行的一段代码。右侧"进程B"才是另一个独立的进程：不同的 PID、不同的地址空间、跑着不同的程序，和 A 唯一的联系是共用同一个 CPU。

    下方虚线上的竖线是进程切换点（上下文切换）：时间轴上可以看到，进程 A 的主循环跑一会儿 → 内核切换进 handler（还在 A 内）→ handler 返回 → 继续 A 的主循环 → 内核切到进程 B 跑一会儿 → 再切回 A…… A 的主程序、A 的 handler、B 这三条流在同一个核上交替执行，宏观上"并发"。

    一句话区别：图里左边两个"进程A"是同一条进程的两条逻辑流（主程序 vs 处理程序），共享进程的资源（内存、PID）；右边的"进程B"是另一条进程，与 A 互不共享。处理程序不是进程，这是理解信号并发模型的关键。

    嵌套信号处理程序：处理程序可能被其他处理程序中断。

    流程：主程序捕获信号 s → 控制传递给处理程序 S → S 执行中又捕获信号 t → 控制传递给处理程序 T → T 返回 S → S 返回主程序 → 主程序恢复执行。处理程序可以像函数调用一样被更高优先级的事件再次打断。

    5. 阻塞与解除阻塞信号（8.5.4）¶

    5.1 待处理信号与阻塞信号（两个关键概念）¶

    • 待处理（pending）：信号已发送但尚未被接收，称为待处理。
    • 阻塞（blocked）：进程可以阻塞某些信号的接收——阻塞的信号可以被递送（到达进程），但在解除阻塞之前不会被接收。

    重要性质：信号不会排队！

    • 任何特定类型的待处理信号最多只能有一个。
    • 如果进程已有类型 k 的待处理信号，之后发送给该进程的类型 k 信号都会被丢弃。
    • 待处理信号最多被接收一次。

    直观理解：同一个信号来几次都只算一次。信号在进程里是用一个位（bit） 表示的：这一位是 1 表示"有这个信号待处理"，是 0 表示"没有"。来了两个同类型的信号，位还是 1——不计数。所以你不能用"发了几次信号"来计数事件（比如数子进程死了几个），信号只告诉你"发生过"，不告诉你"几次"。

    5.2 待处理/阻塞位向量¶

    内核在每个进程的上下文中维护两个位向量：

    • pending：表示待处理信号的集合。当类型 k 的信号被递送时，内核在 pending 中置位 k；当类型 k 的信号被接收时，内核清除 pending 中的位 k。
    • blocked：表示被阻塞信号的集合。可以用 sigprocmask 函数设置和清除，也称为信号掩码（signal mask）。

    直观理解：mask 就是"掩码/开关"。"掩码"这个词类比子网掩码：IP 地址和子网掩码做按位与，就能算出网络号（哪些位是网络部分、哪些是主机部分）。信号掩码同理——它是一串开关位，把某一位设 1，这个信号就被"盖住"（挡住），不让它进来。所以 pending & ~blocked 就是"来了的"与"没被挡住的"做与运算，得到"该处理的了"。

    5.3 隐式阻塞与显式阻塞¶

    隐式阻塞机制：内核阻塞当前正在处理的信号类型的所有待处理信号。例如：SIGINT 处理程序不会被另一个 SIGINT 中断（同一个信号不会无限嵌套打断自己）。

    • sigset_t mask, prev_mask;：两个集合——mask 是"要操作的信号集合"，prev_mask 用来保存调用前的旧掩码；
    • Sigemptyset(&mask);：先把 mask 清空（空集合，一个信号都不含）；
    • Sigaddset(&mask, SIGINT);：往 mask 里加入 SIGINT（2 号）→ 此时 mask = {SIGINT}；
    • Sigprocmask(SIG_BLOCK, &mask, &prev_mask);：把 mask 里的信号（SIGINT）加入进程的阻塞集合；同时第三个参数是"输出参数"，把加入之前完整的旧掩码写进 prev_mask；
    • 中间那段注释区域就是临界区：期间 SIGINT 到达只能置 pending 位、不会被接收，无法打断这里的代码；
    • Sigprocmask(SIG_SETMASK, &prev_mask, NULL);：用保存的 prev_mask 整体替换阻塞集合，精确还原成调用前的样子。

    为什么恢复用 SIG_SETMASK + prev_mask，而不是 SIG_UNBLOCK + mask？ 因为 SIG_UNBLOCK 只是把 SIGINT 从阻塞集合里删掉——如果调用前 SIGINT 本来就已被阻塞（例如嵌套阻塞），SIG_UNBLOCK 会"多解开一层"，破坏原状态。SIG_SETMASK 用 prev_mask 整体替换，"进来什么样，出去就什么样"，保证临时阻塞一定成对还原。

    直观理解：阻塞 ≠ 丢弃。阻塞的信号还是会被递送（到达进程），只是暂时"压着不处理"，等解除阻塞后，内核会在返回用户态时把它作为待处理信号处理。阻塞是"先欠着"，忽略是"不要了"，丢弃是"来了但位已置 1 就没了"——三者要分清。

    6. 编写安全信号处理程序（8.5.5）¶

    6.1 为什么处理程序危险¶

    处理程序与主程序并发执行，并共享相同的全局数据结构——共享数据结构可能被破坏。本学期后面（第 12 章并发）会深入讨论并发问题；现在先给出几条避免麻烦的准则。

    6.2 编写安全处理程序的准则（G0–G5）¶

    准则 内容 解释
    G0 让处理程序尽可能简单 例如只设置一个全局标志然后返回
    G1 处理程序中只调用异步信号安全函数 printf、sprintf、malloc、exit 都是不安全的！
    G2 进入和退出时保存并恢复 errno 以免其他处理程序覆盖你的 errno 值
    G3 通过临时阻塞所有信号来保护对共享数据结构的访问 防止可能的破坏
    G4 将全局变量声明为 volatile 防止编译器把它们存到寄存器中（处理程序可能修改它）
    G5 将全局标志声明为 volatile sig_atomic_t flag 只被读取或写入（如 flag = 1，不要 flag++）；这样声明的标志不需要像其他全局变量那样被保护

    6.3 异步信号安全¶

    异步信号安全（async-signal-safe）：如果一个函数是可重入的（例如所有变量都存储在栈帧上，见 CS:APP3e 12.7.2），或不会被信号中断，那么它就是异步信号安全的。

    什么样的函数状态"不在栈帧上"（即不可重入）：栈帧是每次调用独有的"草稿纸"——返回地址、参数、局部变量都写在自己的帧里，调用 1 的帧和调用 2 的帧是两块不同的内存；凡是整个进程只存一份、所有调用共享的状态，都不在栈帧上：

    • 全局变量 / 静态变量（.data 段已初始化、.bss 段未初始化）：进程里只有一份。经典例子 strtok——它内部用 static 指针记住"上次解析到哪"，主程序调用一半被打断、处理程序再调一次，两次操作同一个指针，状态就乱了。
    • 堆内存（malloc/free）：堆是共享的数据结构，malloc 内部还要维护空闲链表等元数据，两条控制流并发操作同一份堆元数据会写坏。
    • 库函数内部状态：printf 的 stdout 缓冲区 + 内部锁、errno、环境变量表等——全在栈帧之外，全进程一份。

    所以"所有变量都存储在栈帧上"翻译成人话就是：这个函数不碰任何进程共享的可变状态，每次调用完全独立。栈区在进程地址空间高地址、向下增长；.data/.bss 在低地址数据段，堆在其上方——栈帧是"每次调用私有"，全局/静态/堆是"整个进程共享一份"。

    • POSIX 保证 117 个函数是异步信号安全的（来源：man 7 signal）。
    • 列表中的常用函数：_exit, write, wait, waitpid, sleep, kill
    • 不在列表中的常用函数：printf, sprintf, malloc, exit
    • 不幸的事实：write 是唯一异步信号安全的输出函数（所以处理程序里不能随便 printf！）

    为什么 printf/exit 不安全（直观理解）：处理程序和主程序是同一个进程里两条并发的控制流，共享同一份内存（缓冲区、全局状态）。printf 内部做两件事：① 往标准输出的缓冲区写数据（可能还没刷到终端）；② 用内部锁保护缓冲区，防止并发写坏。

    危险场景：主程序正在执行 printf 中途——缓冲区写了一半、锁还没释放——信号恰好到达，处理程序也调用 printf。两条控制流同时操作同一个缓冲区和同一把锁，结果可能是：

    • 输出交错/错乱（两句话的碎片混在一起）；
    • 缓冲区状态不一致（写了一半的指针、长度计数）；
    • 如果锁不可重入，处理程序里的 printf 会死锁——主程序拿着锁被信号打断，处理程序等锁永远等不到。

    write 为什么安全：它是直接系统调用，一次把整块数据交给内核，不经过用户态缓冲区、不持有用户态锁，原子性由内核保证。Sio_puts 内部就是用 write 实现的，所以处理程序里输出要用它。

    exit 为什么不安全：exit 是库函数，会做一堆清理——刷新所有 stdio 缓冲区、运行 atexit 注册的清理函数、释放资源——这些都不是异步信号安全的；_exit 是直接系统调用，立即终止进程、不做任何清理。所以处理程序里要用 _exit。

    cout 也安全吗？不安全，和 printf 同类甚至更危险：① cout 默认与 C 的 stdio 同步（ios_base::sync_with_stdio 默认开启），底层还是走 stdout/stdio 缓冲区——printf 的问题它全有；② operator<< 是一连串成员函数调用，中间可能持有 iostream 内部锁，还维护一堆格式化状态（width/precision/flags）和异常状态，被信号打断更容易坏；③ 重载的 << 可能触发堆分配与临时对象构造/析构（涉及 malloc、锁），这些全都不在 POSIX 117 个异步信号安全函数列表里。结论：处理程序里输出只能用 write（或基于它的 Sio_puts）；C++ 里同样直接 write(1, buf, len)，别用 cout。

    7.2 无竞态的修正版（procmask2.c）¶

    思路：父进程在 fork 之前就阻塞 SIGCHLD，把"fork → addjob"做成不可被打断的整体；子进程 exec 前恢复；父进程 addjob 完再恢复。这样 SIGCHLD 处理程序不可能在 addjob 之前跑。

    /* procmask2.c —— 无竞态的修正版 shell */
int main(int argc, char **argv)
{
    int pid;
    sigset_t mask_all, mask_one, prev_one;
    Sigfillset(&mask_all);
    Sigemptyset(&mask_one);
    Sigaddset(&mask_one, SIGCHLD);
    Signal(SIGCHLD, handler);
    initjobs(); /* 初始化作业列表 */
    while (1) {
        Sigprocmask(SIG_BLOCK, &mask_one, &prev_one); /* 阻塞 SIGCHLD */
        if ((pid = Fork()) == 0) { /* 子进程 */
            Sigprocmask(SIG_SETMASK, &prev_one, NULL); /* 解除对 SIGCHLD 的阻塞 */
            Execve("/bin/date", argv, NULL);
        }
        Sigprocmask(SIG_BLOCK, &mask_all, NULL); /* 父进程 */
        addjob(pid); /* 把子进程加入作业列表 */
        Sigprocmask(SIG_SETMASK, &prev_one, NULL); /* 解除对 SIGCHLD 的阻塞 */
    }
    exit(0);
}

    为什么这样就安全了：SIGCHLD 在 fork 前就被阻塞，所以子进程退出触发的 SIGCHLD 只能待处理着，处理程序不会立刻跑；父进程 addjob 完成后才解除阻塞，此时 SIGCHLD 处理程序再跑 deletejob，作业一定已经在列表里了。"先加后删"的顺序被强制保证。

    9. 非本地跳转（8.6）¶

    9.1 setjmp / longjmp 是什么¶

    非本地跳转（nonlocal jump）：C 语言提供的一种强大（但危险）的用户级机制，用于把控制转移到任意位置——一种受控的、打破过程调用/返回纪律的方式。对错误恢复和信号处理很有用。

    1
2
3
    #include <setjmp.h>
int setjmp(jmp_buf j);    // 必须在 longjmp 之前调用；只调用一次，但返回一次或多次
void longjmp(jmp_buf j, int i);  // 在 setjmp 之后调用；只调用一次，但从不返回
    • setjmp：为后续的 longjmp 标识一个返回点。实现：把当前寄存器上下文、栈指针和 PC 值存储在 jmp_buf j 中，记住"你在哪"。直接调用时返回 0。
    • longjmp：再次从跳转缓冲 j 记住的 setjmp 处"返回"……这次返回 i 而不是 0。实现：从 j 恢复寄存器上下文（栈指针、基址指针、PC），把返回值设为 i，跳转到 j 中存储的 PC 位置。

    直观理解：setjmp 是"做记号"，longjmp 是"空投回记号处"。本来函数调用必须一层层返回（A→B→C 只能 C→B→A），longjmp 可以从深嵌套的函数直接飞回最初的调用者，中间的函数栈帧全都不管了。代价是危险——跳回的地方的局部变量可能已经失效。

    执行逻辑：main 先 setjmp（返回 0）→ foo() → foo 里 error1 为 0 继续 → bar() → bar 里 error2 为 1 → longjmp(buf, 2) → 直接飞回 main 的 setjmp 处，这次返回 2 → switch 命中 case 2，打印"在 foo 中检测到 error2 条件"。

    为什么用 switch：setjmp 第一次返回 0（继续正常流程），longjmp 之后"第二次返回"非 0 值（1、2……对应不同的错误），用 switch 区分"正常"和"哪种错误"。这就是 C 语言版的 try/catch——C++/Java 的异常机制底层就是类似的机制（第 8 章开头提过）。

    10. 本节重点¶

    本节重点： - 信号 = 小整数消息（1–30），由内核发送，不含数据；类似异常/中断，是内核与应用程序之间的 ECF。 - 常用信号：SIGINT(2) Ctrl-C 终止、SIGKILL(9) 不可忽略终止、SIGSEGV(11) 段违规、SIGALRM(14) 定时器、SIGCHLD(17) 子进程停止/终止、SIGTSTP(20) Ctrl-Z 挂起、SIGTERM(15) 可捕获终止、SIGSTOP(19) 不可忽略停止。 - 两个不可忽略信号：SIGKILL（必须死）、SIGSTOP（必须停）——保证内核永远能掌控进程。 - 发送信号：内核检测事件自动发 / kill 系统调用（命令或函数）请求发；kill -9 -PGID 发给整个进程组（负号=组）；Ctrl-C/Ctrl-Z 发给前台进程组。 - 接收信号三种反应：忽略 / 终止（可转储 core）/ 捕获执行处理程序。 - pending/blocked 位向量：pnb = pending & ~blocked；信号不排队，同类待处理信号最多一个、最多接收一次 → 不能用来计数。 - 阻塞：隐式（内核阻塞当前处理类型）+ 显式（sigprocmask + sigemptyset/sigaddset）；阻塞 ≠ 丢弃。 - 安全处理程序五准则 G0–G5：简单、只用异步信号安全函数（write 是唯一安全输出！）、保存恢复 errno、阻塞保护共享数据、volatile / volatile sig_atomic_t。 - 正确回收：SIGCHLD 处理程序里用 while ((pid = wait(NULL)) > 0) 循环回收所有已终止子进程，errno == ECHILD 结束。 - 同步竞态：fork 前先阻塞 SIGCHLD，addjob 后再解除（procmask2）；显式等待信号用 sigsuspend（原子换掩码+挂起），不要用 pause/sleep 轮询。 - 非本地跳转：setjmp/longjmp 打破调用/返回纪律；只能跳回"已调用未完成"的环境（栈纪律）；信号处理中用 sigsetjmp/siglongjmp（restart.c 自我重启）。 - 僵尸进程联系：后台作业不回收 → SIGCHLD 被忽略 → 僵尸；正确做法是捕获 SIGCHLD 并在处理程序里 wait 循环回收。
