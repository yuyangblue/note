## 7.6 swap.o 的符号表

```c
extern int buf[];

int *bufp0 = &buf[0];
static int *bufp1;

static void incr() {
    static int count = 0;
    count++;
}

void swap() {
    int temp;
    incr();
    bufp1 = &buf[1];
    temp = *bufp0;
    *bufp0 = *bufp1;
    *bufp1 = temp;
}
```

判定规则：函数和已初始化全局变量进 .symtab；static 符号是本地的；未初始化全局变量是弱符号（common/.bss）；函数内局部变量在栈上，不进符号表。

| 符号 | swap.o.symtab 表目？ | 符号类型 | 定义符号的模块 | 节 |
| --- | --- | --- | --- | --- |
| buf | yes | 外部 | main.o | .bss |
| bufp0 | yes | 全局 | swap.o | .data |
| bufp1 | yes | 本地 | swap.o | .bss |
| swap | yes | 全局 | swap.o | .text |
| temp | no | ——（栈上局部变量，不进符号表） | —— | —— |
| incr | yes | 本地 | swap.o | .text |
| count | yes | 本地 | swap.o | .data |

逐行解释：

- `buf`：`extern int buf[]` 只是声明引用，真正定义在 main.o（全局数组，.bss）。
- `bufp0`：已初始化的全局指针（初值 `&buf[0]`），在 .data。
- `bufp1`：`static` 未初始化全局指针 → 本地符号，在 .bss。
- `swap`：全局函数 → .text。
- `temp`：swap 函数内的局部变量 → 在栈上，链接器看不见。
- `incr`：`static` 函数 → 本地符号，在 .text。
- `count`：函数内 `static int count=0` → 本地符号，已初始化，在 .data。

## 7.8 多重符号定义时链接器怎么解析

规则回顾：

1. 不允许强符号（函数、已初始化全局变量）多重定义 → 报错 ERROR；
2. 强符号 vs 弱符号（未初始化全局变量）→ 选强符号；
3. 多个弱符号 → 任选一个 → UNKNOWN。

### A. main 的冲突

- Module 1：`int main() {}`——函数 main，全局强符号。
- Module 2：`static int main=1;`——static 变量，本地符号，对其他模块不可见。

(a) REF(main, 1) → DEF(**main.1**)（模块 1 自己定义的函数）
(b) REF(main, 2) → DEF(**main.2**)（模块 2 的 static 变量，本地符号只在本模块内解析）

### B. 两个未初始化的 x

- Module 1：`int x;`——未初始化，弱符号。
- Module 2：`double x;`——未初始化，弱符号。

(a) REF(x, 1) → **UNKNOWN**
(b) REF(x, 2) → **UNKNOWN**

两个都是弱符号，链接器任选一个，无法预测选哪个。

### C. 两个已初始化的 x

- Module 1：`int x=1;`——已初始化，强符号。
- Module 2：`double x=1.0;`——已初始化，强符号。

(a) REF(x, 1) → **ERROR**
(b) REF(x, 2) → **ERROR**

两个强符号同名，违反规则 1，链接时多重定义错误。

## 7.9 为什么 `char main;` 能打印出 0x55

```c
/* foo6.c */
void p2(void);
int main() {
    p2();
    return 0;
}

/* bar6.c */
#include <stdio.h>
char main;
void p2() {
    printf("0x%x\n", main);
}
```

**解释**：

- foo6.c 的 `int main()` 定义了函数 main（强符号，在 .text）；bar6.c 的 `char main;` 定义了一个叫 main 的全局变量（未初始化，弱符号，在 .bss）。
- 按规则 2（强符号优先），bar6.c 里所有对 main 的引用都被链接到了 foo6.c 的**函数 main**——而不是 bar6.c 自己那个 char 变量。
- 所以 p2() 里 `printf("0x%x\n", main)` 打印的不是变量值，而是 **main() 函数的加载地址**。
- x86-64 Linux 的 PIE 可执行文件代码段通常从 `0x555555554000` 附近开始加载（用户态代码段的典型基址），所以地址高位是 `0x55`，打印出来就是 `0x55...`。
- bar6.c 那个 `char main` 虽然在 .bss 占了 1 字节，但从未被真正访问过——所有 main 引用都解析到函数上了。

## 7.10 静态库的最小命令行

规则：链接器从左到右扫描；某个位置出现未解析符号时，只能到它**后面**的库里找。所以"引用者在前，被引用者在后"；循环依赖要把库重复列一遍。

A. `p.o → libx.a`

```
gcc p.o libx.a
```

B. `p.o → libx.a → liby.a` 且 `liby.a → libx.a`（循环）

```
gcc p.o libx.a liby.a libx.a
```

解析过程：p.o 的未解析符号由 libx.a 解决；libx.a 带来的新未解析符号由 liby.a 解决；liby.a 又带回对 libx.a 的未解析符号——libx.a 已经扫过了，所以要把 libx.a 在末尾再列一遍。

C. `p.o → libx.a → liby.a → libz.a` 且 `liby.a → libx.a → libz.a`

```
gcc p.o libx.a liby.a libz.a libx.a
```

解析过程：p.o → libx.a → liby.a → libz.a 一路解析，最后 liby.a 对 libx.a 的循环引用需要再扫一遍 libx.a 才补全。

## 7.15 binutils 工具实操

### A. libc.a 和 libm.a 各含多少目标文件

```bash
ar -t /usr/lib/x86_64-linux-gnu/libc.a | wc -l
```

本机实测：**libc.a 有 2211 个成员**。

`libm.a` 在现代发行版里已经不是真归档，而是一个 linker script（指向 `libm-2.39.a`），所以 `ar -t libm.a` 报 "file format not recognized"。要看真实成员数得用：

```bash
ar -t /usr/lib/x86_64-linux-gnu/libm-2.39.a | wc -l
```

### B. `gcc -O2` 与 `gcc -O2 -g` 产生的代码不同吗

**可执行机器码完全相同**（优化级别都是 -O2，生成的指令序列一模一样）。

`-g` 只是额外在目标文件里塞了一堆调试信息段：`.debug_aranges`、`.debug_info`、`.debug_abbrev`、`.debug_line`、`.debug_str`、`.debug_line_str`、`.debug_loclists`、`.debug_rnglists` 等，不影响指令本身。用 `readelf -S` 能看到这些 `.debug_*` 段。

### C. GCC 驱动程序使用的动态链接器

```bash
gcc -v hello.c -o hello 2>&1 | grep -E "ld-linux|collect2"
```

本机实测链接命令里写死的是：

```
-dynamic-linker /lib64/ld-linux-x86-64.so.2
```

即默认动态链接器是 **`ld-linux-x86-64.so.2`**（x86-64 Linux），默认 C 库是 **`libc.so.6`（glibc）**。
