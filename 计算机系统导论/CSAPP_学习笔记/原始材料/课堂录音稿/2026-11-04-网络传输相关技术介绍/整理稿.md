## 一、传输介质：线、光纤、无线电、微波

整个网络在硬件这一层，就是拿各种线把机器连起来。网线里最常见的是**双绞线**，此外还有**光纤**；无线那一侧是无线电加一块 WiFi 芯片。

还有一种是**微波**：两个波对着照，就能传数据。但微波有个问题——中间不能有阻挡。原因是它的波长很短，衍射能力差，只能沿直线走，跟光差不多。长波可以绕过障碍、传得很远（以前的广播就是长波，能覆盖很大范围），短波则只覆盖小区域。所以微波只能在山头架一个、另一个山头架一个，两边对视才能通信。

像星链那类设备，射频部分仍然要大致对准，但它有一定绕射余量：在屋里从装 WiFi 的地方走到另一个房间，信号也能过去。

### 光纤靠的是全反射

光纤容量大，原理就是**全反射**。光从一端进去，在纤芯与包层的界面上不断全反射前进，损耗极小。物理里讲的"全反射"就是这个：入射角大于临界角时，光不再折射出去，而是全部反射回介质内部。不同角度可以承载不同的波，接收端再把它们解出来。

### 电线曾经是个候选方案

设计全国网络的时候，确实考虑过**用电力线传网络信号**。理由很实际：每家每户都有电线，至少都有电灯，如果能在电力线上传数据，基础设施几乎不用改动。

后来发现不行。一是电力线上还有别的信号，容易互相干扰；二是衰减——电信号传一段距离就弱下去。举个量化的说法：发出去时高电平代表 1，传过去电压掉下来，掉到低电平的门限，1 就变成 0 了。所以每隔一段距离就得加一个**中继器**把信号重新整形放大。一公里一个中继器，成本和维护都不划算。

光纤就没有这个问题：它可以传很远，只在必要的位置加放大设备即可。跨国海底光缆尤其需要这个特性——海底放中继器要供电，维护极其困难。

（注：课堂提到武汉在光纤产业上的地位，以及烽火通信等企业，属于背景信息，这里从略。）

### 带宽需求把光纤推到了机房和家里

以前一个机房里，服务器之间用电线连就够了，带宽 1G 量级。现在不够了：一台机器之间可能要 10G、100G 甚至更高。

原因是大模型。大模型是分布式部署的，一个模型要多个主机组成集群共同训练或共同推理，主机之间的通信量非常大。普通电缆撑不住，必须用光纤。

所以光纤从主干网一路往下推：**光纤入户**已经很普遍，再往下还有"光纤入室"的说法——房间到房间都用光纤。不过一般家庭三百兆、五百兆的带宽就够用了，入户这一步基本到顶。

## 二、网卡适配器：为什么要"适配"

所有数据都要通过**网卡**（网络适配器）才能连到网络上。

为什么叫适配器？因为设备内部的总线架构和网络那套统一的硬件接口并不一样。CPU 一侧是内存总线、I/O 总线，外面是网线、光纤、无线电，两边电气特性和协议都不同，中间必须有一层把一边的信号翻译成另一边——这就是"适配"。

所以介质不同，网卡也不同：连双绞线要一张网卡，连光纤要带光模块的网卡，连 WiFi 要无线网卡。它们统称**网络适配器**。

---

## 三、协议：约定俗成的规则

再往上一层是**协议**。协议就是我们约定俗成的规则：你发数据、收数据按这套规则来，我也按这套规则来，两台主机才能通信。

打个比方，你和一个老乡说家乡话，彼此能懂；全国推广普通话，是因为大家用同一套约定。协议就是网络世界的普通话。

---

## 四、客户端与服务器：是进程，不是机器

**客户端（client）** 和**服务器（server）** 本质上是两个**进程**，我们只是给它们贴了标签：主动发起请求的那个叫客户端，等着响应、提供服务的那个叫服务器。

从写程序的角度看，我们做的正是上面这一层——客户端程序和服务器程序。数据怎么从我这台机器走到那台机器，是另一批人做的事（做网络规划、做路由的那批人）。我们要做的只有一件事：知道对方的地址，把数据交出去。

---

## 五、数据在网络里怎么走：路由器与路由表

数据可能经过很多路由器。这个网络非常复杂，怎么从一端走到另一端，本质是一个路径规划问题。

现在的做法比较成熟：靠**路由表**查表转发。像古代的驿站——你到一个驿站，看牌子写着"去北京，下一站该到哪个驿站"，一站一站接力过去。每个路由器都告诉你"要去这个目的地，下一步该往哪个口走"。

新加入一个节点会有麻烦：它刚接上去时，别的路由表里还没有它，不知道往哪转。一般做法是定时向邻居**泛洪**（flooding），把"我在这里"的消息广播出去，各个路由器收到后更新自己的表。

（注：课堂说这套机制"跟域名服务器的更新是一个道理"，指的是层次化的信息分发；严格说路由收敛与 DNS 缓存不是同一机制，笔记里没有沿用这个类比。）

## 六、IP 地址与域名

要到某台主机，得先知道它的地址。这就是 **IP 地址**，TCP/IP 协议族里的核心标识，32 位。32 位的叫 **IPv4**，128 位的叫 **IPv6**。

32 位不好记，所以分成四组、每组转成十进制，用点隔开，例如 `128.2.203.17`。这就是**点分十进制**。好记一些，但仍然不好记——现在能记住的多半是 `202.114.6.42` 这种，武汉大学的域名服务器地址，因为配电脑时要填它。别的地址基本记不住。

所以要给地址起名字，这就是**域名**：把一个 IP 地址和一个名字绑定。访问域名就等于访问那个 IP。跟电话簿一样——记电话号码难，记人名容易，查一下就行。

（注：课堂提到早期 3721 的中文域名服务，让没学过英文的人输入中文访问网站，现已淡出。属于历史背景，从略。）

有了 IP，一个进程就能通过互联网和另一个进程通信。这个地址是必需的——寄包裹没有地址，东西就不知道送哪去。

## 七、IPv4 与 IPv6；公网地址与私有地址

IPv4 是 $2^{32}$，约 43 亿个。当时以为够用：世界上能有多少台联网设备？

后来设备越来越多。一个人至少三四个——手机、平板、笔记本，家里还有台式机。$2^{32}$ 远远不够，于是设计了 IPv6，128 位，号称"地球上每一粒沙子都能分到一个地址"。

但实际使用中，**并不是每台主机都需要一个公网 IP**。内网里可以用私有地址，比如 `192.168.1.3`。你家的 `192.168.1.3` 和我家的 `192.168.1.3` 完全不冲突，因为各自在自己的网络里，出去时经过一个公网路由器（网关）做转换。

这就像一个目录下的两个同名文件，只要不在同一个目录里就不冲突。

也正因为有子网和私有地址，$2^{32}$ 才撑到了今天。IPv4 现在仍在运行；IPv6 当年在高校做试点推广，所以教育网里 IPv6 覆盖比较早、比较多。目前大部分场景讲的还是 IPv4。

## 八、字节序与 `struct in_addr`

IP 地址在编程里要有标准的结构。教科书式的定义是：

```c
struct in_addr {
    uint32_t s_addr;   /* 32 位无符号整数 */
};
```

这个结构常被吐槽为"设计得最失败的一种定义"：只有一个成员，封装成结构体毫无必要，直接用 `uint32_t` 就行。但它用得实在太广，改不动了，所以一直保留。

地址是 32 位、四个字节，就牵出**字节序**问题。同一个整数，不同架构往内存里放的方向相反：有的把高位放低地址（大端），有的把低位放低地址（小端）。不统一就没法通信。

所以协议规定了**网络字节序**，取大端。发送整数之前必须转换，接收整数之后必须转回来：

- `htons` / `htonl`：host → network，分别处理 16 位与 32 位；
- `ntohs` / `ntohl`：network → host。

这两个函数会按本机架构自动决定要不要交换：本机本来就是大端，它们什么也不做；本机是小端，它们做字节翻转。所以调用方不需要判断自己是什么架构，一律调用即可。

只有整数需要这一步。**字符没有字节序问题**——它就是一个字节，按顺序排列。

## 九、域名系统：分级、查找与缓存

域名服务最早在美国出现。最上层是**一级域名**，它本身没有名字，类似文件系统的根目录 `/`。常见的一级域名按机构类型分：

| 一级域名 | 含义 |
|---|---|
| `.com` | company，公司 |
| `.net` | 网络机构 |
| `.edu` | 教育机构 |
| `.gov` | 政府机构 |
| `.mil` | 军队 |
| `.cn`、`.de`、`.jp` | 国家与地区 |

往下是机构，再往下是院系、专业，一层层分下去——和目录结构一样。所以它叫**域名系统**（Domain Name System）。DNS 既是"域名系统"也是"域名服务器"（Domain Name Server），缩写相同。

### 找一个域名怎么找

假设新注册了 `abc.cn`，这个域名在下层服务器里可能还没有记录。查找过程是自下而上：

先在本地找，找不到就去所属区域的域名服务器（比如武汉大学的域名中心）找；还没有，就往上到教育网（`.edu.cn`）的服务器；再往上到顶级域名服务器。注册一定是在上层完成的，所以**往上找最终一定能找到**。

找到之后，这条"域名 → IP"的对应关系会被**缓存**在沿途的服务器上，下次再查就快了。所以第一次访问某个新域名会慢一些，之后明显变快。

本质上 DNS 就是一个数据库，存的是"域名 → IP"的映射，能查到就能拿到 IP，再通过 IP 协议访问那台主机。

### 用命令行查

`nslookup` 可以查某个域名对应的 IP。`hostname` 查本机名字——局域网里主机名可能重复，公网上则要唯一。

### 为什么建议用域名而不是 IP 连服务

一个域名对应一个 IP，但**一个 IP 可以对应多个域名**。

更重要的是：IP 会变。服务器换了机房、换了运营商，IP 段就变了；但域名不用动，只要改一下域名与 IP 的映射。所以需要长期有效的连接，一律用域名。

反过来讲，`hosts` 文件就是本地的"域名 → IP"表。有些软件破解就是让你改这个文件，把域名指向 `127.0.0.1`（本机），于是程序连不上验证服务器，验证就失效了。

## 十、端口：找到主机之后，还要找到进程

网络通信是**进程到进程**的。IP 只能找到主机，主机上还有多个进程，得再定位到具体是哪一个。这个标识就是**端口（port）**，一个 16 位整数，范围 0–65535。

（注：转写原文这里是"32 个整数""只有 32 个整数"，口误；端口是 16 位，取值个数为 $2^{16} = 65536$。）

所以一个**套接字（socket）**的完整描述是 `IP:端口`。IP 指主机，端口指主机上的某个服务。

### 端口号的分段

小于 1024 的是**知名端口**，留给约定俗成的服务，需要特权才能绑定：

| 端口 | 服务 |
|---|---|
| 80 | HTTP |
| 25 | SMTP（发邮件） |
| 22 | SSH（安全远程登录） |
| 23 | Telnet（远程登录，明文，不安全） |
| 21 / 20 | FTP 控制 / FTP 数据 |
| 7 | Echo（回显） |

这些映射登记在 `/etc/services` 里，可以直接看。同一个端口号可以同时出现在 TCP 和 UDP 两栏，说明两种传输层协议各自独立编号。

自己开发网络程序，用大于 1024 的端口即可，注意别和已有服务撞号。

**客户端端口不用管**，让内核分配；**服务器端口必须显式指定且固定**，否则客户端不知道往哪连。

打饭的类比：IP 是哪个食堂，端口是食堂里的哪个窗口，窗口后面是不同的菜。

## 十一、连接的性质：点对点、广播、单工与全双工

一条连接首先要能**点对点**：从这台主机到那台主机，能找到它。

与之相对的是**广播**：往这个网络里一喊，所有主机都收到。典型应用是局域网里的**时间服务器**——它广播时间，让网内所有主机的时钟保持一致。时间是很多功能的前提，所以这类同步很重要。

### 单工、半双工、全双工

| 模式 | 能力 | 例子 |
|---|---|---|
| 单工 | 只能单向发送 | 广播电台：电台发，你只能听 |
| 半双工 | 两个方向都能传，但**不能同时** | 对讲机 |
| 全双工 | 两个方向**同时**收发 | 电话、TCP 连接 |

对讲机是半双工：你按下说话键就把信道占了，对方只能听；你说完放开，对方才能说。所以通话结尾习惯说一句 "over" ——它的作用就是宣告"我说完了，信道交给你"。如果不说，对方会以为你只是停顿，两边一起沉默。

TCP 是全双工的，可以边说边听，而且数据是**按顺序**的：每个字节以字节流的形式存在，有先后次序。发送顺序和接收顺序一致，不会出现发 "ABC" 收到 "CBA"，所以它是可靠的。

## 十二、套接字接口：和 open 像，但打开之前要先连上

前一章讲系统级 I/O 时说，Unix 管理所有硬件都通过**文件**。网络也一样走文件这套模型，只是**打开用的不是 `open`，而是 `socket`**。

原因有两个：`open` 是"把文件整个打开"，而网络要先选协议族、再建立连接；而且网络设备没有路径名。所以 `socket` 相当于"占一个插座"——向内核注册"我要上网了"，内核分配一个通信端点并返回 **fd**。

一旦拿到 fd，后面就完全一样了：`read` 从网络读进来，`write` 往网络写出去。

### 为什么服务器需要两个 fd

客户端只需要一个 fd：拿到之后 connect，连上就读写。

服务器至少需要两个：

| fd | 作用 |
|---|---|
| 监听 fd | 只负责"有没有新请求进来"，`accept` 在它上面阻塞 |
| 连接 fd | `accept` 返回的新 fd，专供这一条连接传数据 |

服务器为每个客户端建一个连接 fd（fd1、fd2……分别对应不同客户端），监听 fd 始终留着等下一个。这两者分工不同：一个听连接请求，一个传数据。

## 十三、`sockaddr` 与 `sockaddr_in`

套接字接口用一个通用结构管理地址：`struct sockaddr`。它不绑定具体协议，内部包含两部分：

- **协议族（family）**：16 位，指明是哪套协议。常见三种——TCP、UDP、原始网络；
- **地址数据**：具体协议的地址，各协议自己的格式。

用 Internet 协议时，把它"具体化"成 `struct sockaddr_in`——名字里的 `_in` 就是 internet。这个结构把各字段分清楚了：

| 字段 | 长度 | 含义 |
|---|---|---|
| `sin_family` | 16 位 | 协议族，填 `AF_INET` |
| `sin_port` | 16 位 | 端口号 |
| `sin_addr` | 32 位 | IP 地址 |
| `sin_zero` | 8 字节 | 填充，凑齐 16 字节 |

（注：课堂上讲"端口 4 位"是口误，端口是 16 位；填充 8 字节是为了让 `sockaddr_in` 与 `sockaddr` 等长，方便指针互转。）

## 十四、客户端与服务器的流程；三次握手；fork 分身

### 客户端

1. `socket()` 建端点，拿到 fd；
2. `getaddrinfo()` 把域名换成一组 IP（一个域名可能对应多个地址）；
3. 对每个地址尝试 `connect()`，成功就停，失败换下一个；
4. 连上之后 `read` / `write`，用 RIO 做健壮读写；
5. 反复请求—响应，直到关闭。

`connect()` 是**阻塞**的：连不上就一直等，不往下执行。

### 服务器

1. `socket()` 建端点；
2. `bind()` 把 IP 和端口绑上去。多网卡主机有多个公网 IP，必须指定用哪一个，所以这一步不能省；
3. `listen()` 声明开始接受连接，参数是排队长度；
4. `accept()` 从队列取一个连接，返回**新的 fd**；
5. 在新 fd 上读写，处理这个客户端的业务；
6. 回到 `accept()` 等下一个。

`accept()` 也是阻塞的：没有客户端来就一直停在那里。

### 三次握手

`accept()` 背后是 TCP 的**三次握手**：

1. 客户端发 SYN："我要连你"；
2. 服务器回 SYN+ACK："好，我同意"；
3. 客户端再回 ACK："收到，确认"。

为什么要三次？因为每个包都可能丢：

- 客户端的 SYN 丢了，服务器没收到，客户端超时重发；
- 服务器回的 SYN+ACK 丢了，客户端收不到，会认为对方不可达，重发；
- 客户端最后的 ACK 丢了，服务器不知道客户端是否收到自己的确认，也无法确认连接可用。

**必须有一次确认是"对确认的确认"**，双方才能都确定对方收到了。三次是达成这个共识的最小次数。

UDP 不做这一步：它不管包到不到，直接发。TCP 要保证可靠，所以必须先建一条有效通道。

### 为什么 accept 之后要开分身

三次握手成功后，服务器如果自己去做业务处理，就会陷在这个客户端的循环里，其他客户端再也连不进来；这个客户端一退出，也回不到上面继续接客。所以正常做法是：**主进程只负责监听，业务交给分身**。

经典写法是 `accept()` 之后 `fork()`：子进程拿着连接 fd 去服务这个客户端，父进程 `close` 掉连接 fd，回到 `accept()` 继续等。这样每个客户端一个子进程，多个客户端可以并发。

如果觉得 fork 太重（毕竟要新建一个进程），也可以开线程。线程轻一些，但要自己做隔离。

## 十五、`getaddrinfo`：不要手填地址

如果明确知道对方的 IP，可以跳过这一步。但如果对方是**通过域名提供的服务**，就必须先把域名换成 IP——因为 `connect` 要的是地址结构，不接受域名。

`getaddrinfo` 是较新的接口，用来替代老的 `gethostbyname` 和 `getservbyname`。优点是**可重入、线程安全**，而且 IPv4/IPv6 兼容，代码不用改。缺点是参数复杂。

四个参数：

1. **域名或主机名**；
2. **端口或服务名**——给数字当端口，给名字则必须是用公认的服务名（如 http）；
3. **hints**：告诉它你想要什么样的信息（协议族、套接字类型）；
4. **result**：双指针，函数在里面填好一条链表再返回。

返回值只表示成功与否；真正的数据从第四个参数取。这块内存是函数内部申请的，**用完必须释放**，否则泄漏。

返回的 `addrinfo` 是一条**链表**：一个域名有多个 IP，就有多个节点。每个节点里有 flag、family、socktype、协议、域名、地址长度、地址指针，以及指向下一个节点的指针。第一个节点还会放规范域名。

遍历打印每个节点的地址，就得到了"这个域名有哪些 IP"。

（注：课堂上形容这个函数"麻烦一次，之后复用就好"——框架是固定的，变的只有业务部分。）

## 十六、补充：骨干网的结构

骨干网由路由器把不同子网连起来，作用类似计算机里的总线——把各个单元连在一起。

从下往上：

| 层 | 说明 |
|---|---|
| 小的私有网络 | 企业内部网 |
| **POP** | Point of Presence，接入点，网络接入点 |
| **ISP** | Internet Service Provider，服务提供商（电信、移动这类） |
| **Regional net** | 地区网，比主干网小得多，接到主干上 |
| **Backbone** | 主干网 |
| **IXP** | 交换节点，不同主干网在这里互联 |

主干网与主干网之间通过 IXP 连接。比如中国的主干网和欧洲的主干网，在交换节点上对接，再与美国、非洲的网络对接。整个因特网就是这样分层连起来的。

## 十七、补充：IP 地址的分类与子网

32 位的地址按"网络号 / 主机号"的切分方式，历史上分成几类。

| 类别 | 高位特征 | 网络号位数 | 主机号位数 | 网络个数 | 每网主机数 |
|---|---|---|---|---|---|
| A | 最高位 `0` | 8（实际可用 7） | 24 | $2^7-2=126$ | $2^{24}-2$ |
| B | 最高两位 `10` | 16（实际可用 14） | 16 | $2^{14}=16384$ | $2^{16}-2=65534$ |
| C | 最高三位 `110` | 24（实际可用 21） | 8 | $2^{21}$ | $2^8-2=254$ |
| D | 最高四位 `1110` | — | — | 组播地址 | — |
| E | 最高四位 `1111` | — | — | 保留 | — |

每类都要减 2：主机号**全 0** 是网络地址，**全 1** 是广播地址，都不能分配给主机。

### 怎么算一个网段能放多少台机器

C 类默认主机号 8 位，共 $2^8=256$ 个取值，减去全 0 和全 1，**最多 254 台**。

C 类网络号可用 21 位，所以能划出 $2^{21}$ 个 C 类网络。

如果一个网络需要 56 到 256 台主机，C 类不够（上限 254），只能用 B 类或 A 类。

如果要把一个网络切成 256 个子网，就得看网络号还剩多少位：C 类只剩 21 位可用，够切；A 类只有 7 位，$2^7=128$，切不出 256 个。

### 私有地址

有几段地址是保留给内网用的，不会在公网上路由：

| 段 | 范围 |
|---|---|
| `10.0.0.0/8` | 10.x.x.x |
| `172.16.0.0/12` | 172.16–172.31 |
| `192.168.0.0/16` | 192.168.x.x |
| `127.0.0.0/8` | 回环，`127.0.0.1` 是本机 |

（注：课堂强调"每个人不一定需要直接暴露在公网上"，这正是私有地址 + NAT 存在的理由。核对教材后补充一句来源：教材 §11.3.1 只讲"IP 地址是 32 位整数"与点分十进制，**没有展开分类或子网**；A/B/C 这一套来自课件 p47 与课堂。今天实际分配地址用 **CIDR** 记法 `a.b.c.d/x`，`/x` 直接给网络号位数、前缀长度任意，**A/B/C 是历史叫法**。两者共通的只有"网络号 + 主机号"这个划分。）

## 十八、补充：安全、认证与防火墙

早期设计互联网时有个默认假设：**不需要认证，大家都是守规矩的**。后来发现完全不是这样，于是出现了 SSH、HTTPS 这类加密协议。

### 静态 IP 与动态 IP

| 方式 | 谁决定 | 适用 |
|---|---|---|
| 动态分配（DHCP） | 网络里的服务自动分配一个空闲地址 | 家用、校园网，最常见 |
| 静态指定 | 手工配置 | 服务器、打印机等需要固定位置的设备 |

静态 IP 有个前提：必须确认这个地址在你的网络里没被别人占用——谁先占用就是谁的，后者配置上去会失效。

### 防火墙：白名单与黑名单

防火墙的基本功能就两种：

- **白名单**：只让列表里的 IP 和端口通过；
- **黑名单**：列表里的 IP 和端口一律拦掉。

现实例子：公司里能打开公司网页，但淘宝、QQ 打不开，就是把这些域名对应的 IP 和端口放进了黑名单——包出不去，也进不来。

服务器也可以开防火墙只放行必要端口。有些机构不想被 ping，就把 ICMP 那一路关掉，于是你 ping 不通，以为它不在线。

（注：课堂还讲了防火墙的社会意义、信息筛选、电视购物广告的辨识等，属于课堂议论，与网络编程主线无关，本稿不录。）

## 十九、示例：网络游戏怎么同步

这是一个"请求—响应不止一次"的例子。

A 和 B 对战，两人都先连服务器、登录。服务器给 A 一个在线列表，A 选中 B，服务器转告 B，B 同意，于是建立一局对战。

之后 A 的每一次操作——移动、放技能——都先发给服务器，服务器再转给 B。发的内容是自定义的**游戏协议**：某个角色的编号，以及它的坐标 (x, y)。B 的客户端收到新坐标，就把角色渲染到新位置；位置连续变化，看起来就是走过去。

角色的形象不在网络上传——几十 G 的客户端里早就装好了模型和动画。网络上只传"哪个编号、做了什么动作"这种暗号，本地把对应动画调出来播放。

攻击要判断两件事：距离是否在攻击范围内（根据双方坐标算），以及招式有没有打中（叫**碰撞检测**）。命中就掉血，本地播一个掉血特效，同时改属性，并把结果同步给对方。

围棋这类游戏简单得多：只需传"黑或白、第几行第几列"，比如 (1,3)，对方渲染到对应位置即可。不需要动画，也不需要属性配置。

真正难的不是渲染，是**属性平衡**——不同种族强弱怎么配，让每个种族都有长处和短板，这比动画难得多。

（注：这段是课堂用来解释"长连接上的持续请求"的例子，笔记里只保留与网络相关的部分。）
