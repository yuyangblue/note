## 一、进程与线程：创建时到底复制了什么

课堂从「创建一个线程，它和进程有什么区别」讲起。原来的进程上面挂着一堆资源：打开的文件、文件描述符、各种变量和对象。`fork` 以后这些东西变成两份，父子各持一份；变量也各有一份，所以子进程的 `i++` 和父进程的 `i++` 互不相干——比如原来 `i = 3`，一边加一边减，最后两边各是 4 和 2，完全是独立的两个东西。这就是进程。

但有一类例外：字符串常量。像 `"Hello"` 这种只读数据不需要修改，优化后事实上只有一份，父子指向同一个位置。这只是因为只读，不代表进程整体共享。

线程则是另一回事。线程创建出来以后，`i` 还是同一个 `i`，打开文件、文件描述符、变量这些上层资源都是共享的。进程是**复制一部分**，线程是**共享一部分**——这是两者最本质的区别。原来的进程变成主线程，新创建的叫对等线程，线程之间没有主次之分；进程则有父子层次。

注：转写把「线程」识别成「县城／现实／限制」，「进程」识别成「精神／进城」，`fork` 识别成「hold／word／reject」，以下均按术语更正。

## 二、通信代价与创建代价

进程之间通信麻烦，要靠 IPC（inter-process communication，进程间通信）。课堂举例：前面讲过的信号就是一种，一个进程可以把信号发给另一个进程；大概有五种通信方式。线程之间简单得多——共享变量，直接读写就行。

由此引出轻重的差别：线程是轻量级的，创建时需要的资源少；进程是重量级的，创建时资源多。早期做并发一般创建进程，但一个 Web 服务器要提供成千上万次服务时，进程和线程的资源差别就很大——创建线程资源少得多，所以这类场景一般用线程处理。

注：这里说的「线程轻量」是相对进程的地址空间复制而言；线程仍需自己的栈与上下文。

## 三、并发方式混合使用与资源回收

上一节课讲过多进程、多线程和基于事件的多路复用这三种并发操作。对真实应用程序来说，一般是这几种方法**混合**使用，课程为了讲清楚才分开讲。

接着讲回收。创建进程之后，父进程要有 `wait` / `waitpid` 来给子进程「收拾餐具」，否则子进程结束后变僵尸。但等待会阻塞：父进程停在那里，什么都做不了。非阻塞的做法是加参数循环探测，但仍要反复检查。为了避开等待，可以用 `SIGCHLD` 信号处理，或者**两次 fork**：子进程再 fork 一个后立即结束，孙进程被操作系统（课堂比喻为「孤儿院」）接管，由系统回收，父进程也就不必等第二次 fork 的那个进程。

线程里对应的是 `pthread_join` 与 `pthread_detach`。如果不想等某个线程结束，就把它分离（detach），线程结束后系统自动回收，主线程继续做自己的事。

「阻塞」在这里的意思是函数执行到那里就停住；「不阻塞」是调用一下不管成不成功就继续往下走。课堂强调这个概念，因为 `waitpid` 可以阻塞也可以不阻塞。

## 四、同步问题的引出

因为这一章主要讲线程，而线程的变量是共享的，所以会出现新的问题：一个线程做 `i++`，另一个线程做 `i--`，最后到底是什么值？是先变成 4 再变 3，还是先变 2 再变 3？谁都不知道，也不该知道——调度由操作系统决定，哪个线程先执行是不确定的。

用 `sleep` 让某个线程等一秒当然能固定顺序，但一秒钟是极大的浪费，一般不用。要解决的正是：多个不同线程操作同一个数据时，怎样保证值可靠、可预测。这就需要**同步**。进程没有这个问题，因为它的变量本来就是两份；是因为 share（共享），线程才需要同步。

需要同步的既有全局变量，也有「对多个线程可见的局部变量实例」。

## 五、线程内存模型

多线程共享的是进程的上下文，更直白地说：所有线程共享这个进程的资源——代码段、数据段、堆、打开的文件等。每个线程有自己的一套：线程 ID（TID）、栈、栈指针、程序计数器（PC）、条件码和通用寄存器。

线程其实就是对一个函数内容的执行，函数里定义的变量属于这个线程自己。用同一个函数创建线程 1 和线程 2，它们各自的局部变量是独立的；超出函数范围之外的东西则是共享的。因为线程是并行执行的，各线程的 PC 肯定不一样——PC 指向哪条语句，CPU 就执行哪条。

注：与课件第 24 讲 p3「线程内存模型」一致；教材 §12.4.1 用词相同。

## 六、示例程序：哪些变量共享

课堂用一个例子（教材和课件里的 `sharing.c`）逐个变量判定：

```c
char **ptr;                 /* 全局变量 */
int main() {
    long i;  pthread_t tid;
    char *msgs[2] = {"Hello from foo", "Hello from bar"};
    ptr = msgs;
    for (i = 0; i < 2; i++)
        Pthread_create(&tid, NULL, thread, (void *)i);
    Pthread_exit(NULL);
}
void *thread(void *vargp) {
    long myid = (long)vargp;
    static int cnt = 0;
    printf("[%ld]: %s (cnt=%d)\n", myid, ptr[myid], ++cnt);
    return NULL;
}
```

判定结果：

- `ptr`、`msgs`、`cnt` 是共享的；
- `i`、`myid` 不共享；
- `cnt` 虽然是写在线程函数内部的 `static`，但静态变量在整个进程里只有一份，谁先碰到谁初始化为 0，后面再来的线程不再初始化，所有对等线程共用同一个 `cnt`。所以「写在线程函数里」并不等于线程私有。
- 局部变量每个线程栈里各有一份；全局静态变量在虚拟内存里只有一份实例。
- `msgs` 定义在主线程里，却因为全局指针 `ptr` 被间接引用而对等线程也能访问——这就是「对等线程引用主线程的栈」。

课堂还专门讲了 `cnt++` 与 `++cnt` 的区别：`cnt++` 先返回旧值再自增，`++cnt` 先自增再返回新值。课件 p4 的示例用的是 `++cnt`，所以打印出来从 1 开始；录音里口头说的是 `cnt++`，两种写法在这里只是起始打印值不同。

注：课堂对「静态变量只有一份、谁先执行谁初始化」的解释与教材 §12.4.2 一致。

## 七、badcnt.c：错误结果来自哪里

接着看教材的 `badcnt.c`：两个线程各执行一百万次 `cnt++`，主线程 `join` 后检查 `cnt != 2 * niters` 就打印 `BOOM! cnt=...`。实际运行会得到 13051 之类远小于 20000 的值，有时又会是 20000——代码里没有随机数，不确定性来自操作系统调度线程的顺序。

为什么 `cnt++` 会出问题？它看着是一条语句，汇编里是三条指令：

```asm
movq  cnt(%rip), %rdx    ; L：load，从内存读到寄存器
addq  $1, %rdx           ; U：update，在寄存器里加一
movq  %rdx, cnt(%rip)    ; S：store，写回内存
```

加上循环头部 Hi 和尾部 Ti，一次自增可写成 H-L-U-S-T 五步。课堂用这五个字母分析各种交错顺序：

- 正常顺序：线程 1 完整走完 H1 L1 U1 S1 T1，把 0 变成 1；线程 2 接着走，把 1 变成 2。
- 出错顺序：线程 1 读入 0、在寄存器里加好 1，但还没写回；线程 2 此时也读入 0，加一后写入 1；线程 1 再把自己那份 1 写回，结果两个线程都做了加一，内存里却是 1。

关键在 L、U、S 这三步必须连在一起，不能被别的线程插进来。这就是**原子操作**的概念：要么一次做完，要么不做。`cnt++` 不是原子的，`volatile` 也不解决原子性，它只保证真的读内存而不是用寄存器缓存。

注：课堂上画的 H/L/U/S/T 与课件 p10 的汇编标号一致；「13051」是屏幕上一次实际运行结果，不是固定值。

## 八、进度图与不安全区域

把两个线程各自的五步画在两条坐标轴上，就是一个**进度图**：每个点表示一个执行状态 (Inst1, Inst2)，一条合法的状态迁移序列叫一条轨迹。围绕共享变量 `cnt`，L、U、S 三步构成**临界区**：这段指令不应被交错执行。两个线程各自的临界区在进度图上叠出的矩形区域，就是**不安全区域**——轨迹一旦穿进去，结果就可能不一致。

讲解时老师强调：单个线程内部五步的顺序不变，不确定的是两个线程的五步如何交错，而交错由操作系统调度决定。进度图的作用就是把「会不会进危险区」变成图上能不能看见的问题。

注：与教材 §12.5.1、课件 p14—p17 完全对应。

## 九、信号量与 P/V 操作

解决思路是控制执行顺序。原理上能控制顺序，但写代码时控制不了线程什么时候被切走，所以要用专门的同步机制。传统方式是**信号量（semaphore）**，此外还有条件变量、监视器等。

信号量本质上是一个非负的全局整型变量，通过 P、V 两个操作管理不同线程对资源的访问：

- **P(s)**：若 s 非零，把 s 减一并立即返回；「测试并减一」是原子的。若 s 为零，线程挂起，直到 s 变非零且被 V 操作唤醒；唤醒后再完成减一。
- **V(s)**：把 s 加一，原子执行；若有线程阻塞在 s 上，恰好唤醒其中一个。

课堂用「一把锁」来解释：资源数初始化为 1，表示只允许一个线程进入。线程 1 先 P，s 从 1 变 0，拿到锁往下走；线程 2 再 P，s 变负，上锁失败，阻塞在这里。线程 1 做完临界区，V 一下 s 回到非负，线程 2 被唤醒、补做减一，才继续往下走。s 初值也可以是 N，表示最多允许 N 个线程同时访问，就像房间一次能进五个人，第六个进不去。

**为什么不用普通整型变量自己写 `if (s > 0) s--;`？** 因为读、判断、减这三步本身不是原子的，会重蹈 `cnt++` 的覆辙。P、V 由系统保证原子性，这才是必须用信号量的理由。

注：课堂上用「P 后变负表示上锁失败／等待」的传统操作系统口径讲解；课件 p19 与教材采用「信号量始终非负，s = 0 时阻塞」的定义（信号量不变式 s ≥ 0）。两种是不同实现表述，笔记以教材为准。

## 十、C 接口与 goodcnt.c

教材的 `csapp.h` 提供了一套接口：`sem_init(&s, 0, val)` 初始化（第二个参数 0 表示线程间共享），`sem_wait(&s)` 就是 P，`sem_post(&s)` 就是 V；大写包装 `P()` / `V()` 只是对前两者的封装，出错直接退出。

修复 `badcnt.c` 的做法：定义一个保护 `cnt` 的信号量 `mutex`，初值 1，在 `cnt++` 前后加 P/V：

```c
Sem_init(&mutex, 0, 1);
for (i = 0; i < niters; i++) {
    P(&mutex);
    cnt++;
    V(&mutex);
}
```

这样两个线程进临界区前先抢锁，拿到锁的线程走完 L-U-S 才释放，另一个才进来，`cnt` 的操作被串行化，结果稳定为 20000。代价是比 `badcnt.c` 慢好几个数量级。

对应到进度图，P/V 把原来的不安全区域整个包进一个「禁止区域」，任何合法轨迹都绕开它。这个区域在课件里被称为**进入区**。

课堂最后强调使用步骤：先定义信号量、再初始化、用之前 P、用完 V。要求「能看懂」这种代码就够了，不要求自己写完整程序；就像网络编程知道 `socket` → `connect` → `read/write` 的框架就行。

## 十一、生产者—消费者与缓冲

接下来是同步的高级场景。典型例子是生产者—消费者：数据从各个方向汇入一个队列，中间这个队列一般叫**中间件**，作用是缓冲——生产者和消费者的速率不一致，直接对接会丢数据或数据不完整，所以先放进去、再从里面取。课堂举了大数据处理的例子（提到阿里开发的某个计算框架），也提到各城市每天实时传来的销售记录。

往同一块区域写的时候必须上锁，否则一边写一半，另一边又进来写一半，数据就是残缺的。另一个提高并发的办法是把大块资源**切分成小块**（slot），每个生产者／消费者对不同小块操作，只对争用的那一块上锁——就像批作业把一摞卷子分成几份并行批，或者厕所的锁装在每个隔间门上而不是厕所大门上。

事件驱动的图形界面也是生产者—消费者：鼠标的左键单击、双击、右键、滚轮、移动，键盘敲击都是事件；机器很卡时点击没反应，过一会儿才有响应，说明点击事件已经排进缓冲区，只是处理得慢。多媒体场景类似：一边产生视频／音频，一边由多个 worker 渲染，中间需要缓冲；视频切成多个 slot，不同 worker 渲染不同片段，最后合并，减少总耗时。

注：「阿里开发的 one to you Q」是转写原文，未能确认具体产品名，课堂只用它举例说明「大数据处理中的队列」，不影响原理。

## 十二、sbuf 的结构与三个信号量

教材的共享缓冲区 `sbuf` 用一个结构体表示：一个 `int *buf` 指针指向存储区，`n` 表示最多多少个元素，`front` / `rear` 是环形缓冲的头尾下标，再加三个信号量：

- `mutex`（初值 1）：保护对缓冲区的访问；
- `slots`（初值 n）：记录还有几个空槽位；
- `items`（初值 0）：记录已有几个元素。

`sbuf_init` 为 `buf` 申请 n 个 int 的空间，令 `n` 等于传入容量，`front = rear = 0`，再初始化三个信号量；`sbuf_deinit` 释放空间，避免内存泄漏。`sbuf_insert` 在尾部插入并移动尾指针，`sbuf_remove` 从头部取出（不必把旧值清零，下次写入会覆盖，这是效率考虑），两者都在 `mutex` 的保护下修改头尾。生产者 P(slots)、写入、V(items)；消费者 P(items)、取出、V(slots)。二者之和恒为 n，缓冲区满／空时自动阻塞。

课堂顺带讨论了一个枝节：C 语言用结构体直接写底层模块，比 C++ 的多层类继承「轻」，老师引述了 Linus 对 C++ 效率的批评；底层驱动甚至用汇编和 C。这个讨论与并发主线无关，笔记不展开。

## 十三、读者—写者问题

另一个经典模型是读者—写者：读线程只读对象，写线程修改对象；写必须排他，读可以多个同时进行。因为读不改数据，不会造成数据不一致；写会改，所以同一时刻只能有一个写，而且写的时候不能有人读。

课堂讲的是「写者优先」版本：写线程到达时要尽快写，后来的读线程必须排在写后面。实现上用一个计数器记录当前有多少读者：第一个读者要拿到那把保护写操作的锁（P(w)），后续读者不必再拿；最后一个读者读完时释放它（V(w)），写者才有机会进入。对计数器的加减本身也要上锁。这样写者写时读者阻塞，读者在读时写者等待。

课堂还提到真实系统中的复杂情形：比如航班订座系统，以及 DMA（外部设备直接访问内存）使 CPU 缓存与内存数据可能不一致——内存里已经被设备改成 B，缓存里仍是 A，缓存命中就读到旧值。这也是操作系统难写的原因之一。后面关于国产操作系统现状与「时间戳做随机数种子可被预测」的议论与主线关联较弱，只保留结论：随机数种子要尽量混入不可预测的系统状态，时间戳单独使用是可以推算的。

注：DMA 一段只在录音中出现，教材第 12 章没有；按单一来源处理，不写成定论。

## 十四、预线程化并发服务器

把上面几样合起来就是教材的预线程化 echo 服务器：主线程（master thread）只负责 `accept`，把客户端连接 fd 插进 `sbuf`；一组 worker 线程启动时就创建好，各自从 `sbuf` 里 remove 一个 fd，处理请求，再关掉连接。worker 数量按业务负载设定，程序一启动就固定，中途不改；多媒体渲染就是典型场景。

worker 一进来先 `pthread_detach` 把自己分离，省掉主线程回收的麻烦；之后从缓冲区取 fd、做请求—响应（可能多轮），最后 `close(connfd)`。

`echo_cnt` 里使用了上次问过的 `pthread_once`：定义一个 `static pthread_once_t once = PTHREAD_ONCE_INIT`，在第一次调用时初始化保护计数字节的信号量，以后不再初始化。每读到一个请求，P 一下、把字节数累加进共享计数、打印「哪个线程从哪个客户端读了多少字节」、V 解锁，再把结果写回客户端。

注：worker 数量、分离、计数字节等细节与教材 §12.5.5 的预线程化服务器一致；课堂代码是简化版 `echo_cnt`。

## 十五、线程安全函数与四类不安全

最后收束到线程安全。自己写的代码要上锁实现线程安全，标准库里也有现成的线程安全函数可直接调用。线程不安全函数分四类：

1. **不保护共享变量**的函数；
2. **跨越多个调用保持状态**的函数（状态没被保护）；
3. **返回指向静态变量的指针**的函数；
4. **调用了非线程安全函数**的函数。

说到底都是排他资源没有被保护。第 2 类的例子是 `rand` / `srandom`：随机数其实是伪随机，用 `next = next * 1103515245 + 12345` 递推再取模得到；`next` 是静态变量，整个进程只有一份。多个线程各自用相同种子调用，得到的序列就一样。种子常用 `time(NULL)`（从 1970 年 1 月 1 日零点到现在的秒数），但时间戳可预测，也可能溢出；更稳妥的做法是混入 CPU 温度、内存使用率等系统状态。

第 3 类的例子是 `ctime`、`localtime`、`gethostbyname`、`inet_ntoa`。它们返回的是静态缓冲区地址，多个线程拿到的是同一块内存，后一次调用覆盖前一次。修法有两种：改用 `_r` 版本（如 `ctime_r`、`localtime_r`、`gethostbyaddr_r`）让调用者提供缓冲区；或者写一层「加锁—复制」包装——P(mutex)、调用老函数、`strcpy` 到调用者自己申请的内存、V(mutex)，返回私有副本；调用方用完要 `free`。注意锁必须罩到拷贝结束，且程序里所有调用点都得走这层包装。

判断线程安全也可以用「可重入」（reentrant）这个判据：函数执行到一半被中断、转去执行别的代码还能安全回来继续，就是可重入的，通常也是线程安全的。标准 C 中的 `malloc`、`free`、`strlen` 等和绝大多数系统调用是线程安全的；时间、域名、地址转换相关的几个函数（如 `localtime`、`gethostbyname`、`inet_ntoa`）和 `rand` 不是。

注：课堂讲「可重入 ⇒ 线程安全」的判据与教材 §12.7.2 口径一致，但反向不总成立，笔记不把它写成充要条件。

## 十六、死锁

上锁也可能带来新问题：竞争和死锁。典型场景是两个线程（或两个进程）都要两把锁：线程 1 拿到 A，等待 B；线程 2 拿到 B，等待 A。两个资源各一把锁，谁也不释放自己手里那把，互相等，形成死循环。进度图上，两个资源各自的加锁区间叠在一起的那块区域就是死锁区域：只持有一把锁没事，试图同时持有两把就可能卡住。

一个资源不会产生这种死锁；要有两个及以上资源、并且加锁顺序相反才会。这部分内容与教材 §12.7.5 对应。课程最后提到超线程技术与多核概念属于 CPU 部分的回顾，不在此展开。
