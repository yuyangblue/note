## 一、网络编程框架回顾

上节课把网络编程的框架搭起来了：客户端和服务器两端做的事情形状是一样的——都是先 `socket()` 创建一个端点，拿到文件描述符（fd），然后在 fd 上 `read` / `write`。

客户端这边，`socket()` 之后直接调 `connect()` 向服务器发起连接请求。连接之前服务器要做几个操作：先 `socket()`，然后 `bind()` 绑定一个端口。一台服务器上可以同时跑很多种服务——网页服务、邮件服务、文件传输服务——它们靠端口号区分。比如 80 端口一般提供 Web 服务，25 端口提供 SMTP 邮件服务。所以服务器程序启动时必须绑定一个固定端口，客户端请求过来时内核根据端口号把请求派发给对应的服务程序。

客户端 `connect()` 请求连接后，服务器这边会经过三次握手建立连接。连接建立之后，客户端和服务器各自拿到一个 fd，就可以通过 `write()` 把数据发过去、通过 `read()` 把数据读回来。

这里要特别区分服务器端的两个 fd：一个是 `socket()` 创建后用于监听连接请求的，叫**监听描述符（listenfd）**；另一个是三次握手完成后、`accept()` 返回的，叫**连接描述符（connfd）**，专门用来和这个客户端传数据。客户端那边只有一个 fd。

之后双方就在这两个 fd 上来回通信：客户端把数据写到自己的 fd 上，数据通过网络到达服务器的 connfd，服务器从 connfd 读进来，处理完再写回去，客户端再从自己的 fd 读出来。整个网络编程框架就是这个样子。

**不同应用的区别只在消息处理这一层**。框架——怎么创建 fd、怎么连接、怎么收发——都是一样的；变的是服务器拿到数据之后怎么处理。比如游戏服务器收到一个登录消息，就去数据库查账号密码对不对，对了发"允许登录"，不对发"拒绝"；下棋服务器收到"黑子下到 (3,6)"，就在屏幕上把黑子画到那个位置、把白子清掉，再把结果反馈给客户端。写网络程序，核心就是在这个"消息解析和消息处理"的地方做文章。

课堂用 echo 服务器做例子：客户端把消息发过来，服务器什么都不做，原样返回回去，用这个最简单的例子来理解网络编程的基本框架。

## 二、echo 客户端代码逐行

客户端程序的结构：

```c
int clientfd;
char *host, *port, buf[MAXLINE];
rio_t rio;

host = argv[1];    // 服务器 IP 或域名
port = argv[2];    // 端口号

clientfd = Open_clientfd(host, port);   // 自己封装的连接函数
Rio_readinitb(&rio, clientfd);

while (Fgets(buf, MAXLINE, stdin) != NULL) {
    Rio_writen(clientfd, buf, strlen(buf));
    Rio_readlineb(&rio, buf, MAXLINE);
    Fputs(buf, stdout);
}
Close(clientfd);
```

逐段解释：

- `Open_clientfd` 是我们自己写的封装函数（对应教材里的 `open_clientfd`），把域名/IP 加端口传进去，它内部完成 `getaddrinfo` + `socket` + `connect`，连接成功返回一个已经连好的 fd，失败返回 -1。实际写的时候应该加一个判断：fd 大于零才是连接成功，小于零表示失败。
- `Rio_readinitb` 是 RIO（Robust I/O，健壮 I/O）的初始化，把这个 fd 和一个 rio_t 结构绑定，后面用 RIO 的封装来读，避免短计数问题。
- 主循环里，`Fgets` 从标准输入（键盘）读一行到 buf。读多少呢？最多 MAXLINE 这么多，但实际读到的就是用户输入的那一行——用户敲了多少字符就放多少字符进去，不会写满整个 buf。
- 如果读到了内容（不等于 NULL），就 `Rio_writen` 把 buf 里的数据写到 clientfd 上发出去。发送长度是 strlen(buf)，也就是实际读到的字符数，不是 buf 的总大小。
- 发完之后就阻塞在这里等——`Rio_writen` 和 `Rio_readlineb` 都是阻塞调用：数据没发完不会往下走，对面没回数据就一直等。
- 服务器处理完把数据发回来后，`Rio_readlineb` 从 clientfd 读到一行数据放到 buf，然后 `Fputs` 打印到标准输出。
- 这样就实现了：你从键盘敲一行、回车，这行字就发到服务器，服务器（echo 服务器）原样发回来，客户端再打印出来——打什么显示什么，就是回声。

这个循环一直跑，直到用户按 Ctrl+C 发信号强制终止。最后那句 `Close(clientfd)` 理论上执行不到——因为循环退出的条件只有 EOF 或被信号杀掉——但"哪里打开就哪里关闭"是好习惯，所以写上。

## 三、echo 服务器代码逐行

服务器端有两个 fd（监听 fd 和连接 fd），主程序结构：

```c
listenfd = Open_listenfd(port);   // 封装了 socket + bind + listen

while (1) {
    connfd = Accept(listenfd, ...);   // 阻塞等待连接
    echo(connfd);                     // 处理这个客户端
    Close(connfd);                    // 这个客户端断开后关闭
}
```

`Open_listenfd` 把 `socket`、`bind`、`listen` 三步封装在一起。然后进入死循环：

- `Accept(listenfd, ...)` 阻塞在监听 fd 上等连接请求。没有客户端来的时候程序就停在这里；有客户端连上了，三次握手完成，它才返回一个新的 connfd，程序才往下走。
- 拿到 connfd 之后，代码里会先把客户端的域名和端口打出来——"谁来连我了"——这是用 `getnameinfo` 反查对端地址实现的。
- 然后调 `echo(connfd)` 处理这个客户端。

`echo` 函数和客户端的循环是对称的：

```c
void echo(int connfd) {
    rio_t rio;
    Rio_readinitb(&rio, connfd);
    while ((n = Rio_readlineb(&rio, buf, MAXLINE)) != 0) {
        printf("server received %d bytes\n", n);
        Rio_writen(connfd, buf, n);
    }
}
```

服务器总是**先读再写**——因为服务器是被动方，客户端是主动方（request），服务器是响应方（response）。客户端那边是先从键盘读、再写到网络；服务器这边是先从网络读、再写回网络。读一行，原样写一行，就是 echo。

客户端也可以用 `telnet` 命令来连：`telnet 域名 端口`，连接成功后就能互相收发消息，按 `Ctrl+]` 然后 `quit` 退出。

## 四、C/S 模式与 B/S 模式

上面这种客户端—服务器模式叫 **C/S 模式（Client/Server）**。

还有一种常见的叫 **B/S 模式（Browser/Server）**——浏览器当客户端。但要注意：**B/S 底层仍然是 C/S**，只不过客户端固定成了浏览器这个通用程序，不再为每个服务单独写一个客户端。

两者对比：

| | C/S | B/S |
|---|---|---|
| 客户端 | 自己写的应用程序 | 浏览器 |
| 渲染能力 | 强，可以做复杂 3D 游戏 | 弱，只能做简单渲染 |
| 更新 | 服务器端更新没用，客户端必须跟着更新 | 所有东西在服务器端，客户端不用更新 |
| 典型场景 | 重型游戏、专业客户端 | OA 办公系统、网页应用 |

C/S 的好处是客户端可以做很复杂的事情——大型 3D 游戏必须用 C/S，因为浏览器渲染能力有限。以前 Flash 小游戏那种简单回合制（走格子、攻击范围、血量），网页还能做；复杂游戏就不行。

C/S 的缺点是版本管理麻烦：服务器更新了，客户端版本不对就连不上。启动时客户端会检查版本号——大版本号变了说明框架都改了，必须强制更新；小版本号变了只是修小 bug，可以忽略。更新的时候可能要把整个客户端从服务器重新下载安装一遍。

B/S 的好处是所有东西都在服务器端，要更新就是厂商自己更新一下，跟用户的浏览器没关系。用户那边只需要偶尔更新浏览器本身。所以 OA 办公系统这类业务普遍用 B/S——不用维护每个用户的客户端。

## 五、HTTP 协议：超文本传输协议

B/S 模式里，Web 服务器和浏览器之间遵循一套规则，叫 **HTTP（HyperText Transfer Protocol，超文本传输协议）**。

"超文本"是什么意思？最早的网页只能看纯文字，后来慢慢加上了音频、视频、图像，再加上**超链接**——点一下就跳到另一个页面。这些合起来就是"超文本"。

HTTP 是一种**应用层协议**。网络是分层的：最上面是应用层，然后是传输层、网络层，最下面是物理层（链路层）。打个比方，就像邮局——你在武汉大学邮局寄信，信件到武昌区邮局，再到武汉市邮局，再到全国干线，到了对方城市再一层层分发下去。发的时候一层层加上地址标签，收的时候一层层拆开。

课堂特别强调了两种分层模型：

- **TCP/IP 四层模型**：应用层、传输层、网络层、链路层（物理层）——这是实际用的；
- **OSI 七层模型**：概念上分得更细，每一层功能更单一、内聚更高——这是理论模型。

做题的时候要看清题目给的是哪套分层。

不管哪套模型，最上面都是应用层。HTTP 是应用层协议，应用层还有别的：FTP（文件传输）、SMTP（发邮件）、POP3（收邮件）。游戏开发商自己也会定义应用层协议（"命令 1 代表移动，命令 2 代表攻击"），那是私有协议；HTTP 是国际公开标准。

HTTP 目前发展到 1.1 版本（1999 年发布）。

## 六、HTTP 的内容类型

HTTP 传输的内容不只是纯文本，常见的 MIME 类型：

- **纯文本（text/plain）**：没有编码的普通文本；
- **HTML**：用标签来描述内容结构——`<html>`、`<body>` 这些标签；
- **JSON**：键值对形式的数据，现在已经成为网络数据传输的事实标准（虽然没有正式定为国际标准）；
- **XML**：也是标签式描述，但标签可以自定义。HTML 其实是 XML 的一个子集——HTML 的标签名是固定的（`<p>`、`<img>`），XML 里标签名你自己随便定义。

JSON 为什么后来居上？因为它比 XML 轻：XML 每个内容都要成对的开闭标签（`<name>张三</name>`），传过去的字节里大部分是标签开销，有效信息占比小；JSON 只用 `"name":"张三"`，传输效率高。

除了文本，HTTP 还能传：GIF / PNG 图片、音频、视频（二进制流）。

## 七、静态网页与动态网页

网页内容分两大类：

- **静态网页**：以 `.html` / `.htm` 结尾，页面放在服务器上是不变的——图片、音频、视频也是静态资源。客户端来请求，服务器直接把文件发过去就行。
- **动态网页**：内容不是现成的，需要服务器根据请求去查数据库、做计算，生成结果再返回。比如查询统计信息、提交登录表单、上传图片让 AI 算卡路里——这些都是动态的。

动态页比静态页慢很多：静态页服务器只需要读文件发出去，一台机器能扛几万个并发；动态页要跑数据库查询和业务逻辑，可能只能扛几千个。

一个常用的优化手段是**动态页面静态化**：把那些很多人会查、但结果不常变的动态查询，定时预先生成成静态页面存着。用户来查的时候直接发静态文件，快很多。

## 八、URL：统一资源定位器

浏览器地址栏里输入的就是 **URL（Uniform Resource Locator，统一资源定位器）**，它唯一地标识互联网上的一个资源。

以 `http://www.example.com:8080/index.html` 为例：

| 部分 | 含义 | 可否省略 |
|---|---|---|
| `http://` | 协议类型（HTTPS 是加密的 HTTP） | 不能省 |
| `www.example.com` | 域名 | 不能省 |
| `:8080` | 端口号 | 如果是 80（HTTP 默认端口）可以省略 |
| `/index.html` | 服务器上的文件路径 | 如果请求的是 `/`，服务器默认返回 index.html，也可以省略 |

所以 `http://www.example.com` 和 `http://www.example.com:80/index.html` 访问的是同一个页面。

## 九、HTTP 请求方法与状态码

HTTP 请求本质上就是一条命令行式的请求。用 `curl` 命令也能发 HTTP 请求下载网页。

**请求方法**：

| 方法 | 作用 |
|---|---|
| `GET` | 获取资源 |
| `POST` | 提交数据（比如登录表单） |
| `OPTIONS` | 测试资源通不通 |
| `HEAD` | 类似 GET 但只返回头不返回内容 |
| `PUT` | 上传/更新资源 |
| `DELETE` | 删除资源 |
| `TRACE` | 跟踪请求经过的路径 |

课堂提醒：标准里方法很多，但实际项目中**建议只用 GET 和 POST**。因为很多防火墙会把 PUT、DELETE 等方法拦掉——实验室里真实遇到过：本来按 RESTful 风格设计，删除用 DELETE、更新用 PUT，结果线上服务器外面的防火墙把这些方法全拦了，客户端发不到后端。最后只能把所有操作都改成 POST。

**响应状态码**：

| 码 | 含义 |
|---|---|
| 200 | OK，请求成功 |
| 301 | 资源永久重定向 |
| 404 | Not Found，资源不存在 |
| 500 | 服务器内部错误（比如动态处理时数据库出错） |

状态码后面跟一行文字说明（"OK"、"Not Found"），其实和数字是重复的，但方便人读。

## 十、tiny Web 服务器

教材里的 tiny Web 服务器只有几百行代码，它的工作过程：

1. 解析请求行，拿到请求的文件名；
2. 拼 HTTP 响应头：`HTTP/1.1 200 OK`、`Server: tiny`、`Content-length: 文件大小`、`Content-type: text/html`；
3. 把响应头写到 connfd；
4. 打开请求的文件（用 `mmap` 把文件内容直接映射到内存，比 `read` 一个个字节读快）；
5. 把文件内容写到 connfd；
6. 关闭连接。

注意是**写两次**：第一次写 HTTP 响应头，第二次写文件内容。静态页面就是这样——文件打开直接发。

HTTP 是无状态的：发完一次请求—响应，连接就关闭了。

## 十一、CGI 与动态内容

早期动态页面用 **CGI（Common Gateway Interface，通用网关接口）**：服务器收到动态请求后，启动一个外部程序（Perl 脚本等），把请求数据传给它，程序跑完把标准输出作为响应返回。

Perl 在 2000 年前后很火，因为它处理文本能力很强，生活信息类网站大量用 Perl + CGI。现在基本不用这种方式了——现代 Web 框架（Spring、Django、Flask 这类）内部统一处理，不再区分静态动态，框架自己知道哪些 URL 走业务逻辑、哪些直接发静态文件。

动态内容的本质是：**结果不是现成的，需要服务器根据请求去调用程序、查数据库、跑计算，生成结果再返回**。课堂举了两个例子：

- 拍饭菜照片上传，后端把图片送给 AI 模型识别卡路里，把结果返回——响应速度取决于网络和模型推理速度，中午 12 点半大家都吃饭上传时就会慢；
- 病理图像识别：一个病理切片图片可能一个 G，后端要切块、分别送模型推理、再拼结果，理想状态十分钟，医院实际承诺 24 小时出报告，AI 处理后还要医生审核。

## 十三、HTTP 1.1 与心跳保活

HTTP 1.0 与 1.1 最大的区别是 **Keep-Alive（持久连接）**：1.0 每个请求—响应完就关闭连接；1.1 可以在同一个 TCP 连接上连续发多个请求。

服务器会定时发探测消息问客户端"你还在吗"，客户端回应"我在"——这叫**心跳保活**。游戏服务器尤其需要这个：连接是宝贵资源，如果客户端异常掉线（网络断了、电脑死机了），服务器不知道，这个连接就一直占着。有了心跳机制，几个心跳没收到就认为客户端已经不在了，直接把连接资源释放掉。

## 十四、代理与镜像缓存

**代理（proxy）** 的作用：当你无法直接访问目标地址时，通过一个中间服务器替你访问，再把结果转回来。

一个典型场景是**南北运营商互通问题**：南方以电信为主，北方以联通/网通为主。跨运营商访问要绕路，速度慢。解决办法是在北方部署一个代理节点（或镜像站），北方用户直接访问北方节点，北方节点通过专线访问南方源站，两边都快。

代理还能**缓存内容**：把经常访问的资源缓存在代理服务器上，下次别人来要同样的内容，直接从代理发，不用回源站。

国内很多开源软件的镜像源就是这个原理——清华、中科、阿里都提供 PyPI、Docker Hub 等的国内镜像，和源站定期同步，国内用户装包时把源地址换成镜像，速度快很多。

## 十五、阻塞服务器的问题

回到 echo 服务器的代码，可以发现一个问题：`accept()` 是阻塞的，`echo()` 里的 `Rio_readlineb` 和 `Rio_writen` 也是阻塞的。

这意味着：**一个客户端连上之后，服务器就陷在这个客户端的 echo 循环里出不来**——要等这个客户端断开（read 返回 0），服务器才能回到 `accept()` 接下一个客户端。在这个客户端占用期间，其他客户端根本连不上。

所以这种迭代服务器（iterative server）同一时刻只能服务一个客户端。要真正同时服务多个客户端，必须用**并发**的方式。

## 十六、并发能力

并发的意思是同一时刻服务多个客户端。服务器的并发能力是重要指标——比如"这个系统能支持 1000 并发"，就是同一时刻能处理 1000 个客户端请求。

验收并发能力不能靠嘴说，要找专门的测试机构出报告：用测试工具模拟上万个客户端同时连接，看服务器的 CPU、内存、响应时间能不能扛住。一般系统能扛住几百并发就不错了，能扛一万并发已经是大厂水平。并发能力不光靠软件架构，也和硬件（CPU、内存、网卡）有关。

---

## 十七、方式一：基于进程的并发（fork）

最直观的并发方式：`accept()` 返回一个新连接后，`fork()` 一个子进程去处理这个客户端。

```c
while (1) {
    connfd = Accept(listenfd, ...);
    if (fork() == 0) {
        Close(listenfd);    // 子进程不需要监听 fd
        echo(connfd);        // 子进程服务这个客户端
        Close(connfd);
        exit(0);
    }
    Close(connfd);           // 父进程不需要连接 fd
}
```

要点：

- `fork()` 之后，子进程复制了父进程的地址空间，包括 listenfd 和 connfd 两份都有。
- **子进程要关掉 listenfd**——它不需要监听新连接；
- **父进程要关掉 connfd**——它不需要处理这个客户端。因为 fork 之后两个 fd 是共享的（指向同一个打开文件表项），父进程关掉不会影响子进程；不关反而会造成 fd 资源泄漏。
- 父进程关掉 connfd 后立刻回到 `accept()` 接下一个客户端。
- 每来一个客户端就 fork 一个子进程，代码量最少、最直观。

但这种方式现在用得少，因为**进程太重**——fork 要复制整个地址空间，资源消耗大。上万个并发就要上万个子进程，扛不住。

还有一个问题：子进程结束后要回收（waitpid），否则会变成**僵尸进程**。

---

## 十八、进程间通信（IPC）

进程之间是独立的，要通信就得靠 **IPC（Inter-Process Communication）** 机制：

| 机制 | 说明 |
|---|---|
| 信号（signal） | 一个进程给另一个发信号（比如 SIGINT） |
| 无名管道 | `pipe()` 创建，只能用于父子进程之间 |
| 命名管道（FIFO） | 文件系统里有名字，任意两个进程都能用 |
| 共享内存 | 一块内存映射到多个进程地址空间，直接读写 |
| 信号量 | 用于进程间同步、防止竞争 |

FIFO 就是 First In First Out（先进先出），像自来水管——先进来的数据先出去。命名管道是在文件系统里建一个特殊文件，一个进程往里写，另一个从里读。

## 十九、方式二：基于事件的并发（IO 多路复用）

第二种方式不创建新进程，而是**在一个进程里同时监听多个 fd**，看哪个 fd 上有事件就处理哪个。这叫 **IO 多路复用**。

核心函数有三个：

- `select()`：最早的接口；
- `poll()`：后来改进的；
- `epoll()`：Linux 上性能最好的，现在高并发服务器都用它。

### select 的原理

select 维护一个**文件描述符集合**——本质上就是一个位图（bitmap），每一位对应一个 fd：第 0 位为 1 表示 fd 0 上有事件，第 1 位为 1 表示 fd 1 上有事件，以此类推。

```
bit:  31  30  ...  4   3   2   1   0
      0    0   ... 0   0   1   0   1
                              ↑   ↑
                           fd=2 fd=0 有事件
```

服务器只关心两类事件：

1. **监听 fd（listenfd）上的连接事件**——有新客户端来连接；
2. **各个 connfd 上的读事件**——客户端发数据来了。

### select 的用法

```c
fd_set readset, copyset;
FD_ZERO(&readset);
FD_SET(listenfd, &readset);

while (1) {
    copyset = readset;   // select 会修改传入的集合，所以每次要备份
    int n = select(maxfd+1, &copyset, NULL, NULL, NULL);

    for (int i = 0; i <= maxfd; i++) {
        if (FD_ISSET(i, &copyset)) {
            if (i == listenfd) {
                // 新连接到来
                connfd = Accept(listenfd, ...);
                FD_SET(connfd, &readset);
                // 更新 maxfd
            } else {
                // 已有客户端发数据来
                n = read(i, buf, ...);
                if (n == 0) {
                    // 客户端断开
                    FD_CLR(i, &readset);
                    Close(i);
                } else {
                    // 处理数据...
                }
            }
        }
    }
}
```

要点：

- `fd_set` 用 `FD_ZERO` 清零、`FD_SET` 加入一个 fd、`FD_CLR` 移除一个 fd、`FD_ISSET` 判断某一位是否被设置。
- `select` 的第一个参数是 `maxfd + 1`——不是有多少个 fd，而是最大的 fd 值加一。因为底层是遍历 0 到 maxfd 这些位。
- **select 会修改传入的集合**：返回时它只保留有事件的那些位，没事件的清掉了。所以每次循环前要把原始集合备份一份再传给 select。
- 没有任何事件时 select 阻塞，有事件就返回"有多少个 fd 就绪"。
- 返回后从 0 到 maxfd 逐个 `FD_ISSET` 检查哪个 fd 有事件，分别处理。
- 处理完的就跳过，不用每次从头扫到底——select 返回值告诉你有几个就绪。

select 的缺点是每次都要把整个集合从用户态拷到内核态，而且返回后要线性扫描所有 fd，fd 多了性能差。所以后来才有了 poll 和 epoll——epoll 在内核里维护事件队列，不需要每次拷贝整个集合，性能好很多。

## 二十、方式三：基于线程的并发

第三种方式：`accept()` 之后创建一个线程去处理这个客户端，而不是 fork 一个进程。

### 进程 vs 线程

| | 进程 | 线程 |
|---|---|---|
| 地址空间 | 独立 | 共享同一个进程的地址空间 |
| 栈 | 独立 | 每个线程有自己独立的栈 |
| PC（程序计数器） | 独立 | 每个线程有自己的 PC |
| 堆 | 独立 | 共享 |
| 全局变量/代码 | 独立（复制） | 共享 |
| 创建开销 | 大（要复制整个地址空间） | 小 |
| 父子关系 | 有父子进程关系 | 没有父子，只有主线程和其他线程的并列关系 |
| 一个崩溃 | 其他进程不受影响 | 整个进程都死掉 |
| 通信 | 需要 IPC | 直接读共享变量就行 |
| 调度 | 内核调度 | 内核调度（同一进程内的线程） |

关键概念：

- 一个进程至少有一个线程，叫**主线程**。主线程可以创建其他线程。
- 线程之间没有父子关系——主线程创建的新线程和主线程是平等的。
- 每个线程有自己的栈和局部变量（不然函数调用会乱），但代码、数据、堆是共享的。
- 线程间通信非常简单——共享全局变量就行，不需要 IPC。
- 但也正因为共享，多个线程同时读写同一个变量就会出问题，需要**线程安全**机制（锁、信号量）。
- 创建线程的代价比创建进程小很多——进程创建/回收要约两万次 CPU 时钟周期，线程只要一半。

### 多核与并行

操作系统调度器决定哪个线程在哪个核上跑。单核 CPU 上，线程是时间片轮转（并发）；多核 CPU 上，多个线程可以同时在不同核上跑（并行）。这也是为什么 CPU 发展从"不断提高单核频率"转向"堆核心数"——单线程程序吃不到多核的好处，多线程程序才能利用多核。

---

## 二十一、pthread API

Linux 下线程库叫 **Pthreads（POSIX Threads）**，所有函数都以 `pthread_` 开头：

| 函数 | 作用 |
|---|---|
| `pthread_create` | 创建一个新线程 |
| `pthread_join` | 等待指定线程结束，回收它的资源 |
| `pthread_detach` | 分离线程，结束后由系统自动回收，不需要 join |
| `pthread_self` | 获取当前线程的线程 ID |
| `pthread_cancel` | 请求取消另一个线程 |
| `pthread_exit` | 线程退出（区别于进程退出 `exit`） |

### 创建线程

```c
pthread_t tid;

void *thread_func(void *arg) {
    // 线程要做的事
    return NULL;
}

pthread_create(&tid, NULL, thread_func, NULL);
pthread_join(tid, NULL);   // 等待线程结束
```

要点：

- 先声明一个 `pthread_t tid` 变量——这是输出参数，`pthread_create` 创建成功后把线程 ID 写进去。
- 第三个参数是**线程例程**——线程要执行的函数，函数签名是 `void *func(void *arg)`。
- 第四个参数是传给线程例程的参数，类型是 `void *`——什么都能传（整数、结构体、堆指针）。
- 线程函数返回值也是 `void *`——可以返回任意指针，主线程用 `pthread_join` 的第二个参数接收。
- 第二个参数是线程属性，一般传 NULL 用默认值。

### join 与 detach

`pthread_join(tid, NULL)` 会阻塞等待线程结束。如果不想等，就用 `pthread_detach(tid)`——告诉系统这个线程结束后自己回收资源，不用主线程 join。

```c
void *thread_func(void *arg) {
    pthread_detach(pthread_self());   // 自己把自己分离
    // ... 干活 ...
    return NULL;
}
```

在并发服务器里，工作线程一般在一开始就 `pthread_detach(pthread_self())`，这样主线程不用等它结束，处理完客户端线程自动退出、系统自动回收。

### 传参的注意事项

`pthread_create` 第四个参数是 `void *`，传 connfd 进去的时候要注意：

- 不能传栈上变量的地址——因为主线程的栈帧可能在线程还没读到之前就销毁了；
- 正确做法是在堆上 `malloc` 一个空间存 connfd，把堆指针传给线程，线程用完再 `free`。

## 二十二、基于线程的 echo 服务器

```c
while (1) {
    connfd = Accept(listenfd, ...);
    pthread_t tid;
    int *fd_ptr = malloc(sizeof(int));
    *fd_ptr = connfd;
    pthread_create(&tid, NULL, thread_echo, fd_ptr);
}

void *thread_echo(void *arg) {
    int connfd = *(int *)arg;
    free(arg);
    pthread_detach(pthread_self());
    echo(connfd);
    Close(connfd);
    return NULL;
}
```

主线程 `accept` 到新连接后，在堆上分配一个整数存 connfd，创建一个线程把这个指针传进去。线程启动后先把 `void*` 转回 `int*` 取出 connfd，然后 `free` 堆空间，detach 自己，再去 echo。

主线程立刻回到 `accept` 接下一个——这样多个客户端就能同时被多个线程服务。

## 二十三、线程安全与锁（预告）

线程之间共享数据，就会遇到**线程安全**问题：一个线程在读某个变量的时候，另一个线程正在写它，读到的就不是中间态。

解决方法是**锁**（互斥量 mutex）和**信号量**——保证同一时刻只有一个线程能访问共享资源。课堂说这部分下次课再详细讲。

线程本身是轻量级的、效率高，但共享数据带来了同步问题——这是线程相比进程的代价。进程是各自独立、互不干扰，但通信麻烦；线程通信方便，但要小心竞争。

## 二十四、三种并发方式总结

| 方式 | 原理 | 优点 | 缺点 |
|---|---|---|---|
| 多进程（fork） | 每连接一个子进程 | 简单、隔离好 | 重、开销大 |
| IO 多路复用（select/epoll） | 单进程监听所有 fd | 不需要创建进程/线程 | 编程复杂、要自己处理事件循环 |
| 多线程（pthread） | 每连接一个线程 | 轻量、共享数据方便 | 要处理线程安全问题 |

现在的高并发服务器不是单用某一种，而是**混合使用**：比如用 epoll 监听连接事件（高效），接到连接后丢给线程池处理业务（轻量）；特别复杂的业务再 fork 一个独立进程做隔离。课堂举的例子：登录操作用线程处理，开桌游戏（长时间、计算密集）就 fork 一个独立进程。
