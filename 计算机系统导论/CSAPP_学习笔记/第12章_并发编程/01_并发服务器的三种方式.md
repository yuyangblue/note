## 1. 并发为什么难

人的思维天生是顺序的——一步一步做事情。但并发程序里，多条执行流同时跑，它们之间的交叉顺序可能有无数种。时间的概念在并发里常常具有误导性：你以为"A 先 B 后"，实际系统可能让 B 先跑完。

并发程序的经典问题类别：

- **竞争（Race）**：结果取决于系统调度的任意决策。比如两个线程同时读同一个变量、同时写，最后值是不确定的。
- **死锁（Deadlock）**：两个执行流各自占着一个资源、又等对方释放，谁都动不了——像十字路口四个方向的车互相等。
- **活锁/饥饿**：没有死锁，但某个执行流总是被调度器跳过，一直得不到 CPU。

这一章先不管这些问题（后面同步章节再讲），先解决"怎么让多个客户端同时被服务"。

## 2. 迭代服务器的根本缺陷

回到迭代 echo 服务器：

```c
while (1) {
    connfd = Accept(listenfd, ...);
    echo(connfd);      // 阻塞在这里，直到这个客户端断开
    Close(connfd);
}
```

如果客户端 1 连上之后一直不发数据、也不断开（比如用户出去吃午饭了），服务器就一直阻塞在 `echo` 里的 `read` 上。这时候客户端 2 来连——注意，**客户端 2 的 `connect` 调用是会返回成功的**，因为 TCP 内核会把连接请求排到监听套接字的 backlog 队列里。但服务器进程根本没回到 `accept`，所以客户端 2 发的数据只能在内核缓冲区里等着，永远得不到回应。

解决方案：把服务器改成**并发**的——同一时刻用多条逻辑流同时为多个客户端服务。

---

## 3. 三种并发思路概览

| 思路 | 谁来调度 | 地址空间 |
|---|---|---|
| 基于进程 | 内核自动交错执行 | 每条流有自己的地址空间 |
| 基于事件 | 程序员手动交错执行 | 所有流共享同一个地址空间 |
| 基于线程 | 内核自动交错执行 | 所有线程共享同一个地址空间 |

---

## 4. 方式一：基于进程的并发

最直观的做法：`accept()` 返回一个新连接后，`fork()` 一个子进程专门去服务这个客户端，父进程立刻回去 `accept` 下一个。

### 4.1 代码骨架

```c
void sigchld_handler(int sig) {
    while (waitpid(-1, 0, WNOHANG) > 0)
        ;
}

int main(int argc, char **argv) {
    int listenfd, connfd;
    Signal(SIGCHLD, sigchld_handler);    // 注册子进程退出信号处理
    listenfd = Open_listenfd(argv[1]);

    while (1) {
        connfd = Accept(listenfd, ...);
        if (Fork() == 0) {
            Close(listenfd);     // 子进程不需要监听 fd
            echo(connfd);         // 子进程服务这个客户端
            Close(connfd);
            exit(0);
        }
        Close(connfd);            // 父进程不需要连接 fd
    }
}
```

### 4.2 为什么父子各要关一个 fd

`fork()` 之后，子进程获得父进程地址空间的完整副本——包括 listenfd 和 connfd 两份都有。内核为每个打开文件维护一个**引用计数**，`fork` 之后 connfd 的引用计数变成 2（父进程和子进程各一份）。只有当引用计数归零时，连接才真正关闭。

- **子进程必须关掉 listenfd**：它不需要监听新连接，留着是浪费 fd 资源。
- **父进程必须关掉 connfd**：它不需要服务这个客户端——服务是子进程的事。如果父进程不关，connfd 的引用计数永远是 1（父进程那份），即使子进程关了，连接也不会真正释放。

### 4.3 SIGCHLD 与僵尸进程

子进程结束后，父进程如果不去 `waitpid` 回收，子进程就变成**僵尸进程**——它已经退出了，但进程表项还留着，占着系统资源。僵尸进程多了会耗尽进程表。

解决办法：父进程注册一个 `SIGCHLD` 信号处理函数。子进程退出时内核给父进程发 SIGCHLD，处理函数里用 `waitpid(-1, 0, WNOHANG)` 回收所有已退出的子进程。`WNOHANG` 表示不阻塞——如果没有已退出的子进程就立刻返回。

### 4.4 优缺点

- **优点**：实现简单；进程之间地址空间隔离，一个客户端的 bug 不会搞垮整个服务器。
- **缺点**：进程太重——`fork` 要复制整个地址空间（虽然写时复制优化了，但仍然比线程贵得多）；创建和回收进程的开销大，上万个并发就要上万个子进程，扛不住。

## 5. 方式二：基于事件的并发（IO 多路复用）

不创建新进程，在一个进程里同时监听所有 fd——哪些 fd 上有事件（新连接来了、客户端发数据来了），就处理哪个。

### 5.1 核心思想

服务器维护一个活动连接集合（一个 connfd 数组）。主循环每次问内核："这些 fd 里哪些有数据可读？"内核返回后，逐个处理：

- 如果 listenfd 上有事件 → 新连接到来，`accept` 后把新 connfd 加入集合；
- 如果某个 connfd 上有事件 → 读数据、处理；
- 如果读返回 0 → 客户端断开，把这个 connfd 从集合里移除。

这个"问内核哪些 fd 就绪"的函数就是 `select`（或 `poll`、`epoll`）。

### 5.2 select 与 fd_set

```c
fd_set readset, copyset;
FD_ZERO(&readset);
FD_SET(listenfd, &readset);
```

`fd_set` 本质上是一个**位图（bitmap）**——每一位对应一个 fd 编号。第 0 位为 1 表示 fd 0 上关心读事件，第 5 位为 1 表示 fd 5 上关心读事件，以此类推。

操作 `fd_set` 的宏：

| 宏 | 作用 |
|---|---|
| `FD_ZERO(&set)` | 清空整个集合 |
| `FD_SET(fd, &set)` | 把 fd 加入集合 |
| `FD_CLR(fd, &set)` | 把 fd 从集合移除 |
| `FD_ISSET(fd, &set)` | 判断 fd 是否在集合里（返回后检查事件） |

### 5.3 代码骨架

```c
fd_set readset, copyset;
int maxfd = listenfd;

FD_ZERO(&readset);
FD_SET(listenfd, &readset);

while (1) {
    copyset = readset;    // select 会修改传入的集合，必须备份
    int n = select(maxfd + 1, &copyset, NULL, NULL, NULL);

    for (int i = 0; i <= maxfd; i++) {
        if (!FD_ISSET(i, &copyset)) continue;

        if (i == listenfd) {
            // 新连接到来
            int connfd = Accept(listenfd, ...);
            FD_SET(connfd, &readset);
            if (connfd > maxfd) maxfd = connfd;
        } else {
            // 已有客户端发数据来
            int n = read(i, buf, MAXLINE);
            if (n == 0) {
                // 客户端断开
                FD_CLR(i, &readset);
                Close(i);
            } else {
                // 处理数据...
            }
        }
    }
}
```

几个关键细节：

- `select` 的第一个参数是 `maxfd + 1`——不是 fd 的数量，而是最大 fd 值加一。因为底层是从 0 到 maxfd 逐个检查位。
- **`select` 会修改传入的 `fd_set`**：返回时它只保留有事件的那些位，没事件的清掉了。所以每次循环前要把原始集合备份一份（`copyset = readset`），传给 select 的是备份。
- 最后一个参数是超时——传 `NULL` 表示永久阻塞，直到有事件到来。

### 5.4 select 的局限与 epoll

select 每次调用都要把整个 fd_set 从用户态拷到内核态，返回后还要从 0 到 maxfd 线性扫描所有位找就绪的 fd。fd 多了之后，拷贝和扫描的开销都很大。

后来的改进：

- **`poll`**：用链表代替位图，没有 fd 数量上限，但仍然每次全量拷贝。
- **`epoll`**（Linux）：在内核里维护事件队列，不需要每次拷贝整个集合；只返回真正就绪的 fd。高并发服务器都用 epoll。

### 5.5 优缺点

- **优点**：只有一条控制流、一个地址空间——可以用调试器单步跟踪；没有进程或线程的创建开销；是高性能 Web 服务器的首选设计（Node.js、Nginx、Tornado 都是这个模型）。
- **缺点**：代码复杂——要自己管理事件循环、状态机；难以实现细粒度并发（比如一个 HTTP 请求只收了一半头怎么办）。

## 6. 方式三：基于线程的并发

`accept()` 之后创建一个**线程**去处理这个客户端，而不是 fork 一个进程。线程看起来和进程很像，但轻得多。

### 6.1 进程的新视角

传统视角：进程 = 进程上下文（寄存器、PC）+ 代码段 + 数据段 + 堆 + 栈。

新视角：进程 = **一组线程** + 共享的代码段、数据段、堆、文件表。每个线程有自己的栈和寄存器状态（包括 PC），但代码、数据、堆是所有线程共享的。

一个进程至少有一个线程（主线程）。主线程可以创建其他线程。线程之间没有父子关系——主线程和它创建的线程是**平等的对等线程**，只是主线程先存在而已。

### 6.2 线程 vs 进程

| | 进程 | 线程 |
|---|---|---|
| 地址空间 | 独立 | 共享同一进程的代码、数据、堆 |
| 栈 | 独立 | 每个线程有自己独立的栈 |
| PC（程序计数器） | 独立 | 每个线程有自己的 PC |
| 创建开销 | 大（复制整个地址空间） | 小（只建栈和线程上下文） |
| 父子关系 | 有树形层次 | 平等的线程池，无父子 |
| 一个崩溃 | 其他进程不受影响 | 整个进程都死 |
| 通信 | 需要 IPC（管道、共享内存等） | 直接读写共享变量 |
| 调度 | 内核调度 | 内核调度同一进程内的线程 |

关键 tradeoff：线程通信方便（共享变量就行），但也正因为共享，多个线程同时读写同一个变量就会出问题——需要同步机制。进程隔离好、不用考虑同步，但通信麻烦、创建开销大。

### 6.3 并发与并行

- **并发（concurrent）**：两条执行流在时间上重叠——单核 CPU 上，操作系统时间片轮转，一个线程跑一会儿切到另一个，看起来同时在跑。
- **并行（parallel）**：多核 CPU 上，多个线程真的在不同核上同时执行。

这也是为什么 CPU 发展从"不断提高单核频率"转向"堆核心数"——单线程程序吃不到多核的好处，多线程程序才能利用多核。

## 7. Pthreads API

Linux 下的线程库叫 **Pthreads（POSIX Threads）**，所有函数都以 `pthread_` 开头，约 60 个函数。最常用的几个：

| 函数 | 作用 |
|---|---|
| `pthread_create` | 创建一个新线程 |
| `pthread_join` | 等待指定线程结束，回收它的资源 |
| `pthread_detach` | 分离线程，结束后系统自动回收 |
| `pthread_self` | 获取当前线程的 ID |
| `pthread_exit` | 线程退出（区别于 `exit` 是进程退出） |

### 7.1 pthread_create

```c
#include <pthread.h>

void *thread_func(void *arg) {
    printf("Hello from worker thread\n");
    return NULL;
}

int main() {
    pthread_t tid;
    pthread_create(&tid, NULL, thread_func, NULL);
    pthread_join(tid, NULL);    // 等待线程结束
    return 0;
}
```

参数：

- 第一个参数 `&tid`：输出参数，创建成功后写入线程 ID；
- 第二个参数 `NULL`：线程属性，一般用默认；
- 第三个参数 `thread_func`：线程例程——线程要执行的函数，签名必须是 `void *func(void *arg)`；
- 第四个参数 `NULL`：传给线程例程的参数，类型 `void *`——什么都能传。

### 7.2 pthread_join 与 pthread_detach

`pthread_join(tid, NULL)` 会阻塞当前线程，直到 tid 指向的线程结束。这是**可汇合（joinable）**状态——线程结束后，它的资源不会自动释放，必须有人 `join` 回收。

如果不想等，就在线程一开始就调用 `pthread_detach(pthread_self())`——告诉系统这个线程结束后自己回收资源。这是**分离（detached）**状态。

```c
void *thread_func(void *arg) {
    pthread_detach(pthread_self());   // 自己把自己分离
    // ... 干活 ...
    return NULL;
}
```

并发服务器里的工作线程一般一开始就 detach——主线程不用等它结束，处理完客户端线程自动退出、系统自动回收。

### 7.3 传参的坑

`pthread_create` 第四个参数是 `void *`，传 connfd 进去的时候有一个经典陷阱：

```c
// 错误写法：传栈上变量的地址
int connfd = Accept(listenfd, ...);
pthread_create(&tid, NULL, thread_func, &connfd);
```

这是错的——因为 `connfd` 是主线程栈上的局部变量，主线程的下一轮循环可能已经覆盖了它，或者函数栈帧销毁了，工作线程读到的就不是原来的 connfd。

正确做法是在堆上分配：

```c
int *fd_ptr = malloc(sizeof(int));
*fd_ptr = connfd;
pthread_create(&tid, NULL, thread_func, fd_ptr);
```

工作线程里：

```c
void *thread_func(void *arg) {
    int connfd = *(int *)arg;
    free(arg);
    pthread_detach(pthread_self());
    echo(connfd);
    Close(connfd);
    return NULL;
}
```

## 8. 基于线程的 echo 服务器

```c
void *thread(void *vargp) {
    int connfd = *((int *)vargp);
    Pthread_detach(pthread_self());
    Free(vargp);
    echo(connfd);
    Close(connfd);
    return NULL;
}

int main(int argc, char **argv) {
    int listenfd, *connfdp;
    pthread_t tid;
    listenfd = Open_listenfd(argv[1]);
    while (1) {
        connfdp = Malloc(sizeof(int));
        *connfdp = Accept(listenfd, ...);
        Pthread_create(&tid, NULL, thread, connfdp);
    }
}
```

主线程 `accept` 到新连接后，在堆上分配一个整数存 connfd，创建一个线程把这个指针传进去。线程启动后先把 `void*` 转回 `int*` 取出 connfd，然后 `free` 堆空间、detach 自己，再去 echo。主线程立刻回到 `accept` 接下一个。

## 9. 三种方式对比

| | 基于进程 | 基于事件 | 基于线程 |
|---|---|---|---|
| 调度者 | 内核 | 程序员手动 | 内核 |
| 地址空间 | 每个客户端一个 | 共享一个 | 共享一个 |
| 创建开销 | 大（fork） | 无 | 小（pthread_create） |
| 共享数据 | 困难（需 IPC） | 容易（同地址空间） | 容易（同地址空间） |
| 非预期共享 | 不容易发生 | 容易（手动管理状态） | 容易（需同步） |
| 调试 | 各进程独立调试 | 单步跟踪最方便 | 多线程交叉难调试 |
| 典型应用 | 传统 Unix 服务器 | Nginx、Node.js | Java 服务器、现代 Web |

## 10. 线程安全与锁（预告）

线程之间共享数据，就会遇到**线程安全**问题：一个线程在读某个全局变量的时候，另一个线程正在写它，读到的可能是写了一半的中间态。

解决方法是**互斥量（mutex）**和**信号量**——保证同一时刻只有一个线程能访问共享资源。这部分内容在后面的同步章节详细讲。

线程本身轻量、效率高，但共享数据带来了同步问题——这是线程相比进程的代价。

---

## 11. 现代混合架构

真实的高并发服务器不是单用某一种，而是**混合使用**：

- 用 epoll 监听连接事件（高效地处理大量连接的到来）；
- 接到连接后丢给线程池处理业务逻辑（轻量地跑具体请求）；
- 特别复杂、需要隔离的业务再 fork 一个独立进程（防止一个模块崩溃搞垮整体）。

比如登录操作用线程池处理（快、共享缓存方便），开一局游戏这种长时间、计算密集的任务就 fork 一个独立进程（隔离、不拖慢其他客户端）。

---

## 12. 小结

- 迭代服务器一次只能服务一个客户端，真实服务器必须并发；
- 三种方式：fork 子进程（简单但重）、IO 多路复用（高效但代码复杂）、pthread 线程（轻量但要处理同步）；
- 基于进程时：父子各关各的 fd，SIGCHLD + waitpid 回收僵尸；
- 基于事件时：select 维护 fd_set 位图，注意 maxfd+1 参数和 select 会修改传入集合；
- 基于线程时：线程共享代码/数据/堆，独立栈和 PC；pthread_create 传 connfd 要 malloc 在堆上；detach 让系统自动回收。

---

> **本节重点**：
> - 三种并发方式的核心区别：谁调度、地址空间分不分开；
> - fork 后父子各关各的 fd（父关 connfd、子关 listenfd），SIGCHLD 回收僵尸；
> - select 的 fd_set 是位图，参数是 maxfd+1，传入集合会被修改必须备份；
> - pthread_create 传参不能用栈地址，要 malloc 堆空间；线程默认 joinable，要 detach；
> - **常见坑**：忘记 `pthread_detach` 会导致线程结束后内存泄漏；忘记关 fd 会导致连接资源泄漏。
