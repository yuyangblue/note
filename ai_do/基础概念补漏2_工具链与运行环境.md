## 一、交叉编译工具链长什么样

### 名字就是说明书（三段/四段命名法）

```
riscv64  -  linux  -   gnu   -  gcc
 目标架构   目标OS   用哪个C库   哪个编译器
```

完整含义：「产出 **riscv64** 架构、跑在 **linux** 上、链接 **GNU libc** 的 **gcc**」。

看名字就能判断用途：

| 名字里的字段 | 含义 | 用来编什么 |
| --- | --- | --- |
| `...-linux-gnu-...` | 跑在 Linux 上，用 glibc | 用户程序 |
| `...-linux-musl-...` | 跑在 Linux 上，用 musl（更小、更适合静态链接） | 用户程序 |
| `...-unknown-elf-...` | **不知道跑在什么系统上**（裸机），产出裸 ELF | **内核本体** |

〔常识 —— GNU 工具链命名约定 `arch-vendor-os-abi`〕

### 和平时用的 gcc 的差别

- **前端一样**：解析 C 语法、做语义检查，这部分是同一套代码
- **后端不一样**：最后把中间代码翻译成机器指令的那一段。普通 gcc 产出 x86 机器码；`riscv64-linux-gnu-gcc` 产出 RISC-V 机器码
- **库也不一样**：它链接的 libc 是 RISC-V 版本的，不能拿你 x86 系统的 libc 来用

### 官方 Docker 镜像里装了哪些（原文版本照录）

```

riscv64-linux-gcc                  10.2.0   (Buildroot 2020.08)
riscv64-unknown-elf-gcc             8.2.0   ← 裸机用，编内核
riscv64-linux-gnu-gcc              11.4.0   (Ubuntu 11.4.0-1ubuntu1~22.04)
riscv64-linux-musl-gcc             11.2.1
loongarch64-linux-gnu-gcc          13.2.0
loongarch64-linux-musl-gcc         13.2.0

cargo 1.86.0-nightly (088d49608 2025-01-10)

  stable-x86_64-unknown-linux-gnu
  nightly-2024-02-03-x86_64-unknown-linux-gnu
  nightly-2025-01-18-x86_64-unknown-linux-gnu (default)
rustup target list --installed:
  loongarch64-unknown-linux-gnu
  loongarch64-unknown-none          ← 裸机 target
  riscv64gc-unknown-none-elf        ← 裸机 target
  riscv64imac-unknown-none-elf      ← 裸机 target

```
〔源：`testsuits-for-oskernel` pre-2025 分支 README 中 Docker 容器内的命令输出〕

> Rust 的 target 命名里，**以 `none` 结尾 = 裸机（没有 OS）**，以 `linux-gnu` 结尾 = 有 OS。

### 怎么装、怎么指定目标架构

**C / gcc**
```bash
# Ubuntu 上
apt install gcc-riscv64-linux-gnu        # RISC-V
# 龙芯的源里不一定有，比赛建议直接用官方 Docker

# 用法：就是把 gcc 换成那个长名字，参数照旧
riscv64-linux-gnu-gcc -o kernel-rv main.c
```

**Rust / cargo**
```bash
rustup target add riscv64gc-unknown-none-elf   # 装 target，不是装编译器
cargo build --target riscv64gc-unknown-none-elf
# 龙芯裸机：--target loongarch64-unknown-none
```

**Windows / Mac 上别折腾**：直接用官方 Docker 镜像（比赛就是这么规定的）。
> 原文："比赛评测时的编译和运行工作均在Docker容器中运行"
> 〔源：测试集 pre-2025 分支 README〕

## 二、QEMU 是什么

官网一句话定位：**"A generic and open source machine emulator and virtualizer"**
〔源：https://www.qemu.org/〕

通俗讲：**它是一个软件，假装自己是另一台电脑**。在 x86 笔记本上敲 `qemu-system-riscv64`，它就变成一台装着 RISC-V CPU 的虚拟机器——有内存、串口、磁盘控制器、网卡。你编的 `kernel-rv` 就在这台假机器上开机。

### 和 VirtualBox / VMware 的区别

| | VirtualBox / VMware | QEMU 系统模拟 |
| --- | --- | --- |
| 能虚拟什么 | 只能**同架构**（x86 上虚拟 x86） | **异架构**（x86 上虚拟 RISC-V / 龙芯） |
| 为什么 | 可借硬件加速直接跑指令 | 每条指令都要软件翻译 |
| 速度 | 接近原生 | 慢 |

比赛为什么用它：初赛**只用 QEMU，不碰真机**，两个架构在同一台机器上都能测，不用买开发板。

## 三、Docker 是什么（读作「刀克」，不是 doctor）

一句话：**一个已经把工具全装好的、能打包复制的 Linux 小房间。**

你们需要它的三个理由：

1. **版本锁死**。凑齐 riscv 工具链 + 龙芯工具链 + QEMU 9.2.1 + 特定版本 Rust nightly，自己装半天还可能版本对不上。官方镜像里装什么就是什么。
2. **你编的和评测机编的是同一个东西**。如果你在自己电脑上用 QEMU 8.0 跑通，评测机用 9.2.1 跑不通，你连原因都找不到。
3. **Windows / Mac 也能干活**，不用在自己机器上装一堆 Linux 工具链。

测试集仓库里的用法（原文照录）：
```
0. 你的电脑上需要安装 docker
1. 运行 make docker 进入 docker 环境
2. 运行 make 构建评测样例和 SD 卡镜像文件
```
〔源：测试集 pre-2025 分支 README「构建方法」段〕

## 四、kernel-rv 是怎么被加载进去的：用的是 `-kernel` 参数

**答案：不是放磁盘镜像里，是 `-kernel`。** 官方给了完整命令（原文照录）：

```
qemu-system-riscv64 -machine virt -kernel {os_file} -m {mem} -nographic -smp {smp} -bios default \
  -drive file={fs},if=none,format=raw,id=x0 \
  -device virtio-blk-device,drive=x0,bus=virtio-mmio-bus.0 -no-reboot \
  -device virtio-net-device,netdev=net -netdev user,id=net -rtc base=utc \
  -drive file=disk.img,if=none,format=raw,id=x1 -device virtio-blk-device,drive=x1,bus=virtio-mmio-bus.1
```

龙芯版同理（把 `virt` 换成 `-drive ... virtio-blk-pci`，无 `-bios`，另有 `disk-la.img`）：
```
qemu-system-loongarch64 -kernel {os_file} -m {mem} -nographic -smp {smp} \
  -drive file={fs},if=none,format=raw,id=x0 \
  -device virtio-blk-pci,drive=x0,bus=virtio-mmio-bus.0 -no-reboot \
  -device virtio-net-pci,netdev=net0 -netdev user,id=net0,hostfwd=tcp::5555-:5555,hostfwd=udp::5555-:5555 \
  -rtc base=utc \
  -drive file=disk-la.img,if=none,format=raw,id=x1 -device virtio-blk-pci,drive=x1,bus=virtio-mmio-bus.1
```
〔源：测试集 pre-2025 分支 README「赛题评测指南」段〕

### 三样东西别搞混

| 参数 | 是什么 | 谁准备的 |
| --- | --- | --- |
| `-kernel {os_file}` | **内核本体**（kernel-rv / kernel-la） | 你 |
| `-drive file={fs}` | **官方测试磁盘**：EXT4、无分区表，根目录放 12 组测试点 + `xxxxx_testcode.sh` | 官方 |
| `-drive file=disk.img` | 你的辅助盘（如 rootfs），**可选**，没生成就不带这个参数 | 你 |

### 完整开机链路

```
QEMU 用 -kernel 把内核塞进内存 → 跳到 entry
  → 内核自己起来 → 自己找 virtio 磁盘 → 挂载
  → 扫到 xxxxx_testcode.sh → 逐个串行跑 → 打印到串口
  → 跑完主动关机 → 评测机检测 QEMU 退出后按屏幕输出打分
```

要点：
- `-nographic` = **没有图形界面**。「屏幕输出」就是串口打印的文本，所以内核不用写显卡驱动，往串口写就行。
- 测试点必须**串行**跑，不能并发；跑不完的可以跳过，但**提示信息格式仍要输出**（如 `#### OS COMP TEST GROUP START basic ####`），否则影响评分。
- 跑完要**主动关机**。

## 五、链接脚本是干嘛的，为什么内核要固定地址

### 链接脚本是什么

通常叫 `linker.ld` / `*.lds`，写给链接器 `ld` 的配置文件，回答三件事：

```
1. .text / .data / .bss 各段放在内存的哪个地址
2. 段之间怎么排列、怎么对齐
3. 程序入口符号是哪个（ENTRY）
```

### 为什么应用程序不需要它

因为 **Linux 替它做了这些决定**：

```
你敲 ./a.out
  → Linux 读 ELF 的程序头
  → 挑一块空闲内存把代码搬过去
  → 还能做地址随机化（ASLR）
  → 程序从头到尾不知道自己在哪个地址，也不该知道
```

### 为什么内核必须固定地址

因为**内核开机时下面没有任何操作系统**，没人帮它加载。唯一的加载者是 QEMU 的 `-kernel`，而它干的事很笨：

```
QEMU -kernel kernel-rv
  → 读 ELF 里写好的加载地址
  → 原样拷进内存（不做任何重定位）
  → 跳到 entry 地址
```

**所以地址必须在编译链接阶段就写死**，写死的地方就是链接脚本。

### 两个迟早会撞上的后果

1. **开了 MMU 之后更麻烦**：内核链接时用的是物理地址，开分页后 CPU 访问的是虚拟地址。所以内核里通常有个固定偏移（如把物理 `0x80200000` 映射到虚拟 `0xffffffc080200000`）。这段是开机时手写的汇编，在开 MMU 之前先跳到虚拟地址去跑。
2. **写错地址的症状极难查**：链接地址写错，表现就是 QEMU 一启动直接卡死、或跳到非法地址触发异常，**没有任何有意义的报错**。这是新手调试内核最痛苦的一类 bug。

## 六、要不要学 RISC-V / 龙芯指令集：不用系统学

### 三条理由

**一、测试点不是汇编写的。** 12 组测例（basic、busybox、lua、libctest、iozone、unixbench、iperf、libcbench、lmbench、netperf、cyclictest、LTP）都是**用 C 写的开源软件**，官方用交叉编译器编成 rv/la 二进制放进磁盘。你一个汇编字都不用写。〔源：测试集 README 测例清单〕

**二、架构相关的部分上游已经写好了。** 如果基于 starry-next / arceos 做增量，页表、中断控制器、上下文切换都在 `axhal`（硬件抽象层）里写完了，你写的是架构无关的那一层。

**三、但要准备「能读懂一点点」的程度**，两页文档就够：

```
· 认得几个寄存器：a0/a1 传参、sp 栈指针、ra 返回地址、pc 程序计数器
· panic 时会打印 pc 值和寄存器现场，能大概看懂崩在哪
· 会用 objdump -d 反汇编看几行
```

**这个程度不用啃指令集手册。**

## 七、Rust 要不要学：取决于选题，本周不用

### 判断表

| 走哪条路 | 要不要学 Rust |
| --- | --- |
| 内核赛道 + 基于 starry-next / arceos / ByteOS | **必须** |
| 内核赛道 + 基于 RT-Thread | 不用（它是 C） |
| proj3（OS 级 Agent Runtime） | 大概率 Rust，也可能是 Go/Python，看你们定 |
| **本周（第一周调研）** | **不用**，分工文件明确写「不要求读懂 Rust 全部源码」 |

官方镜像预装 `cargo 1.86.0-nightly` + `riscv64gc-unknown-none-elf` / `loongarch64-unknown-none` 等 target —— 说明**官方默认参赛队用 Rust**。

### 和 C 的区别（对写 OS 真正重要的三条）

**一、所有权 / 借用（最重要）**
编译期就证明内存不会 use-after-free、不会 double free、不会有数据竞争。这些正是 C 写内核时 bug 的最大来源。代价是借用检查器天天跟你对着干，前两周很痛苦。

**二、`unsafe` 划出了危险区**
Rust 不禁止你干危险的事，但必须显式写在 `unsafe {}` 里。于是「读写硬件寄存器」这种不得不危险的代码被单独圈出来——审查代码时只需盯 unsafe 块。

**三、Cargo 统管依赖与构建**
不用自己写一堆编译规则（但比赛仍要在外层包那个 Makefile，因为评测机只认 `make all`）。

> 一句话：**C 是「相信程序员」，Rust 是「编译期帮你盯内存」**。OS 社区往 Rust 转，是因为内核里的内存 bug 代价太高。

## 八、如果周日被问到，怎么说

**问：交叉编译是怎么回事？**
> 编译的机器和运行的机器不是同一种 CPU。在 x86 上用 `riscv64-linux-gnu-gcc` 编出 RISC-V 机器码，这叫交叉编译。名字拆开是「架构-系统-C库-编译器」，看到 `unknown-elf` 就知道是编裸机内核用的。

**问：QEMU 和 Docker 在比赛里干嘛？**
> QEMU 是模拟器，在 x86 上假装一台 RISC-V 或龙芯的机器，初赛只用 QEMU 不碰真机。Docker 是官方做好的环境镜像，把 QEMU 9.2.1 和工具链版本全锁死，保证你本地编的和评测机编的是同一个东西。

**问：内核怎么被启动的？**
> 通过 QEMU 的 `-kernel` 参数把 kernel-rv 直接加载进内存，不是放磁盘里。磁盘是另一块，装的是官方的 12 组测试点，EXT4 无分区表。内核起来后自己挂载磁盘、串行跑测试脚本、往串口打印结果、跑完主动关机，评测机按屏幕输出打分。

**问：链接脚本为什么必须有？**
> 因为内核开机时下面没有 OS，没人帮它做加载和重定位。QEMU 只会按 ELF 里写死的地址原样拷贝，所以地址必须在编译链接阶段就用链接脚本定死。应用程序不用管，是因为 Linux 会替它挑地址，还能做随机化。

**问：要不要专门学指令集和 Rust？**
> 指令集不用系统学，测试点都是 C 写的开源软件编出来的二进制，架构相关的部分上游也写好了，只需要能看懂寄存器名和 pc 值这种程度。Rust 取决定于选题——基于 starry-next/arceos 就必须学，本周调研阶段不用。
