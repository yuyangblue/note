## 一、你们的条件与判断依据

### 1.1 已知团队情况

| 条件 | 用户提供的信息 | 对选题的影响 |
| --- | --- | --- |
| 年级 | 大二 | 可以把本次比赛作为系统实验起点，适合有阶段成果的题 |
| 语言 | C、Python 只有基础语法；没有 Rust 经验 | 要为指针、结构体、内存、工程构建、调试和 Python 项目开发补课 |
| Linux | 用过桌面版 | 熟悉桌面不等于熟悉内核、进程调试、工具链或系统性能实验 |
| 教学 OS | 没做过 xv6/rCore | 尚不具备直接进入复杂内核、运行时开发的经验基线 |
| 人员 | 三人 | 可以分工，但必须留集成和交叉理解时间 |
| 时间 | 每人每周约 10 小时 | 每周约 30 人时，约十周粗算 300 人时，含学习、联调、实验和文档 |
| 开发板 | 暂无，可购买 | 可以采购不等于已解决驱动、系统镜像、资料和调试问题 |
| GPU | 一台配 5060 的 Linux 笔记本，可连接两台 4090 服务器 | 有条件验证本地 7B/8B 推理；实际显存、权限、可用时段和并发能力需实测 |

本地章程写明作品截止为 2026-12-27；从 10-19 到该日相差 69 天。按整十周估算的 300 人时只是总投入量级，不是 300 小时纯开发。建议将其中约 60～75 人时留给集成、实验复跑、文档、视频与提交，其余时间还要覆盖基础学习。

**算力改善的是模型实验条件，不能替代操作系统、并发、驱动和测量方法的学习。** 对你们而言，应优先降低同时学习的新层次数量：先在一个成熟基线上深入一项机制，再考虑更大系统。

### 1.2 这次更新了哪些结论

上一阶段尚无本届题目，只能从往届方向提出通用建议。现在题单明确：四题围绕 AI/Agent，另有一题专门开放给课程实践。因此，之前推荐的“范围明确的功能扩展、调试、观测”思路，最适合在 **proj5 的本校课程实践框架内**落地，不能当作脱离题单的自命题。

## 三、先处理三项容易误读的要求

### 3.1 逐题评分与总技术方案的关系尚未说明

本地总技术方案给功能赛的参考比例为：执行展示 30%、文档 20%、工程规范 20%、AI 说明 10%、视频 20%。截图又为 proj2、proj3、proj4 分别列了另一套评分，其中 proj2 和 proj3 的表内合计各为 100，proj4 按两大组各占 50%。

目前不能确定它们是题目内部技术分、替代性细则，还是需要再折算到总方案。**不自行覆盖任何一套，也不擅自将两套权重相乘。** 先按题目技术要求完成成果，同时保留通用文档、AI 使用记录和演示要求；在定题时向官方澄清折算口径。

### 3.2 proj1 的“优秀难度”不是一等奖承诺

原文明确四层只是题目完成难度分析，“并非最终的评奖标准”。“QEMU 能跑”“SG2002 上 TPU 推理”分别代表不同完成层次，最终仍需综合工程和优化表现。不能据此保证某层获某奖，也不能未经确认就认定仅完成基础层满足所有交付门槛。[识别稿第 2 节][TEXT]

### 3.3 proj3 和 proj4 中的“操作系统”有不同层次

proj3 强调 Agent 的系统级执行抽象与运行机制；proj4 明确基于既有 AIOS 做多智能体协作。它们不等于内核实现赛道那种从启动、内存和进程开始构造通用内核。

AIOS 上游说明其 kernel 是位于操作系统内核之上的资源抽象层，SDK 为 Cerebrum，管理模型、内存、存储和工具等资源。因此，AIOS 的“kernel”不能直接理解成 Linux 内核。[AIOS 官方仓库][WAIOS]

但这也不意味着套用一个工作流框架就能满足 proj3。proj3 的统一抽象、资源管理、上下文管理、隔离与通信均有明确任务；具体是否必须修改底层 OS 内核，截图没有说清，需要确认。[识别稿第 4 节][TEXT]

## 四、第一选择：proj5 课程实践案例

### 4.1 为什么最适合你们

这题明确允许在系统调用、进程模型与调度、虚拟存储器、文件系统中选任一方向，不要求面面俱到，并鼓励机制可观测、教学难点分析、实验工具与方案复用。[识别稿第 6 节][TEXT]

这使你们可以只学习并做好一条知识链，不必先掌握整个 OS 或同时搭建模型生态。基础 OS 实验也能提供真实的进程、内存和 I/O 行为，结果较容易验证。代价是：作品要体现自己的设计和效果，完成现成教学实验并截图提交，特色通常不足。

**资格前置条件：它要求作品来源于“本校操作系统课程实践”。** 先向本校课程教师确认项目来源、允许的基线和材料。不能因为网上有 xv6 实验，就自动认定它满足本校课程来源要求。若本校使用其他教学内核，应优先在现有课程框架上落地。

### 4.2 推荐具体方向：调度机制实现与可观测对比

**建议题名：**「基于本校教学内核的调度机制实现、执行轨迹与对比实验」。

若本校课程使用或允许采用 xv6，可细化为「xv6 单核环境下 RR 与 MLFQ 调度对比及机制可观测实验」。这是候选方案，需课程来源确认后才能定。xv6 是 MIT 提供的 C/RISC-V 教学 OS，可作为理解进程、调度和锁的学习资源。[MIT 官方入口][WXV6]

**作品应解决的问题：** 学生看过调度算法后，难以解释真实进程为什么在某一时刻运行、等待多久、如何受到时间片和优先级影响。作品同时提供真实内核中的调度机制和可复现证据，将算法描述对应到实际执行。

#### 最小完整交付范围

1. 使用课程认可的教学内核基线，先完整运行现有进程与调度实验。
2. 保留原始调度策略作为基线，在单核环境实现一种对比策略，例如多级反馈队列（MLFQ）；准确记录本校基线策略，不预设所有教学内核都是同一种 RR。
3. 明确任务状态、时间片、队列迁移、退出处理及避免长期饥饿的规则。
4. 在内核中采集必要事件：进程就绪、开始执行、被抢占、主动阻塞、退出，以及需要的队列/优先级变化。
5. 用 Python 将真实事件转换为执行轨迹、统计图与指标表。
6. 设计若干固定负载，对比响应时间、就绪等待时间、周转时间和 CPU 份额等；解释收益与代价。
7. 提供一套可重复运行的构建、负载、采集和分析方法，并形成教学说明。

**核心贡献必须包括机制实现或有深度的实验能力。** Python 图表服务于真实内核结果，不能用手工编造时间线代替系统运行。

#### 建议的负载与指标

| 负载 | 想观察的问题 | 建议指标 |
| --- | --- | --- |
| 多个长 CPU 任务 | 是否公平分配 CPU，是否有任务长期不运行 | 运行份额、最大等待、完成时间 |
| 长任务与短任务混合 | 短任务是否更快获得服务 | 首次响应、周转时间 |
| CPU 计算与主动休眠任务混合 | 就绪/阻塞转换怎样影响调度 | 就绪等待、唤醒后的响应 |
| 长时间混合负载 | 提升交互性是否牺牲长任务，提升规则是否有效 | 最大等待、吞吐、优先级轨迹 |

指标定义要精确。例如首次响应为“首次运行时刻减就绪时刻”，周转为“退出时刻减创建/到达时刻”，等待统计只累计处于就绪状态但未运行的时间。单位依内核计时能力确定，不以低精度 tick 冒充纳秒精度。

#### 怎样做出特色

- 让轨迹能解释一次真实选择：任务为什么被抢占、为什么进入另一个队列、何时被提升优先级。
- 构造一个能暴露问题的反例，再展示修正后的行为，例如缺少提升规则时长任务等待过久。
- 在相同资源、负载与采集方式下比较，展示至少一个对新策略不利的场景，说明适用边界。
- 事件尽量先写入有界缓冲区，测试后导出，测量记录机制本身的开销；避免大量串口打印改变调度结果。
- 用讲解和实验问题帮助其他学生复现关键机制，形成可复用课程案例。

这是可以争取的作品质量方向，不是官方额外指定功能。先确保正确运行，再做展示和更细分析。

### 4.3 备选子方向与难度边界

| 方向 | 优点 | 对你们的主要风险 | 建议 |
| --- | --- | --- | --- |
| 调度实现 + 真实事件观测 | 可见结果直接，实验较易设计 | 中断、锁、计时和状态统计要准确 | 优先验证 |
| 写时复制（COW）与页面生命周期实验 | OS 深度强，可比较内存和复制成本 | 页表、引用计数、缺页、用户态拷贝路径，容易出现隐蔽错误 | 有课程基础和导师支持再选 |
| 单一文件系统功能与异常一致性测试 | 工程性强，能体现边界测试 | 缓存、inode、并发和错误路径可能超出预期 | 只在现有课程框架很熟悉时考虑 |
| 仅展示系统调用流程 | 入门较快 | 若只有跟踪和动画，技术深度与新增价值可能不足 | 可当第一周练习，定题时需更深入问题 |

### 4.4 需要补齐的知识链

```text
C：指针、数组、结构体、内存、函数指针
    → Linux 命令行、Git、Make、GDB、QEMU
    → 用户态/内核态、系统调用、异常和时钟中断
    → 进程状态、上下文切换、锁、就绪与阻塞
    → 读懂课程基线调度器
    → 实现对比策略并验证边界
    → 事件采集、Python 分析、实验与教学说明
```

不必为本方案额外学习 Rust。学习应围绕当前实验：读到一个锁就理解它保护什么，改一个调度路径就验证其状态转换，不以看完整本书作为开始实现的前置条件。

### 4.5 第一周验证与退出条件

每人约 10 小时，团队共 30 人时，第一周只验证：

- 确认课程来源和可用基线；一个人按另一人的说明也能构建和启动。
- 跑通一个用户程序、一个系统调用和一次多进程实验。
- 每个人都能用自己的话解释进程何时进入/离开就绪状态、调度器在哪里选下一任务。
- 增加一项简单、可校验的真实运行观测，例如每进程运行 tick 或有限的切换事件，确保不破坏原功能。

**如果课程来源无法确认，proj5 的优先推荐暂不成立。** 如果基线可以运行但全员仍无法解释关键代码，应缩小候选子题，先做具体课程实验；如果已有成熟课程项目和导师帮助，则再考虑 MLFQ 等扩展。第一周不要求完整实现新调度器。

## 五、备选：proj4 多智能体协作技术

### 5.1 为什么有机会，又为什么不是更轻松

你们的 Python 基础与 GPU 资源更接近此方向，可以不用从裸机和内核入口开始。但本题有明确、可检查的硬条件，远高于“四个 Agent 聊天”：

- Linux + AIOS + 端侧 7B 或 8B 大模型。
- 使用 AIOS-Agent SDK。
- 不少于 4 **种**智能体，不能只把同一种角色复制四份。
- 至少 4 个可并行子任务，自动分配。
- 至少 3 对不同类型 Agent 具有双向交互。
- 正确处理依赖和顺序。
- 相对同一多智能体方案串行执行，总时间减少至少 20%，并正确完成任务。[识别稿第 5 节][TEXT]

AIOS 当前上游把 kernel 与 Cerebrum SDK 分开，提供本地模型后端配置，但竞赛实际允许的版本需要固定。先验证指定版本，不要在大量依赖漂移的默认分支上反复安装。[AIOS 官方说明][WAIOS]

### 5.2 你们现有算力怎样发挥作用

- 先选一台可稳定使用的 4090 服务器跑单个指定规模模型，再测四个并发请求的排队和吞吐；不要一开始就把两台服务器都纳入系统。
- 多个 Agent 可以共享一个模型服务，不等于每个 Agent 都必须各加载一份权重；共享方式是否满足题目口径仍需确认。
- 笔记本可以负责开发、控制和结果分析；其模型承载能力取决于实际显存、后端和上下文，不根据“5060”型号直接保证可用。
- 要核实服务器权限、驱动、可用时段、是否可安装依赖和稳定连接。截图要求“端侧”，是否接受通过网络访问你们控制的本地部署服务器，需官方确认。
- 不将云端商业模型 API 当作题目要求的本地 7B/8B 模型替代品。

模型参数规模不等于总内存：按十进制粗算，7B/8B 的 FP16 权重约 14/16 GB，4bit 原始权重约 3.5/4 GB，尚不含量化元数据、KV Cache、工作区和并发额外占用。这只是参数量乘位宽的估算，实际配置必须测量。

### 5.3 可优先验证的任务场景

**建议候选：受约束的软件项目故障诊断与复现验证。** 任务输入为固定的源码快照、日志、配置和测试数据，最终输出故障原因、证据定位和可执行复现包。采用可本地运行的小项目与已知故障，避免把网络搜索或不可控网站速度变成主要实验变量。

一种可讨论的角色设计：

| Agent 类型 | 独立能力/工具 | 可并行工作 |
| --- | --- | --- |
| 日志诊断 | 日志解析、调用链定位 | 提取异常与时间线 |
| 源码分析 | 本地代码检索、受限静态分析 | 找到候选根因 |
| 配置与依赖分析 | 配置核对、版本与依赖检查 | 排查环境与参数问题 |
| 测试与复现 | 执行固定测试、验证假设 | 对输入问题运行独立初始诊断 |

之后通过有内容的双向反馈形成至少三对交互，例如日志↔源码、源码↔测试、配置↔测试。双向交互需要记录假设、证据和反馈，不用空消息凑数量。可增加汇总角色，但要评估额外模型调用和工程成本。

**这只是任务候选，尚未证明满足“单智能体无法完成”。** 一个工具充分的通用 Agent 可能最终也能串行完成。必须先向题目方确认“无法完成”是否指在给定权限、知识划分、时间/资源预算下无法完成，再据此设计合理能力边界；不能人为削弱单 Agent 来制造优势。若这一口径不认可该候选，应更换场景。

### 5.4 20% 应怎样验证

设同一多智能体方案串行执行耗时为 `T_serial`，并发方案为 `T_parallel`：

```text
总时间减少比例 = (T_serial - T_parallel) / T_serial
需要：T_parallel ≤ 0.8 × T_serial
等价加速比：T_serial / T_parallel ≥ 1.25
```

这里的基线是**多智能体串行执行**，不是单智能体。不要把“加速 1.2 倍”误当成“总时间减少 20%”。例如 100 秒降到 80 秒才是减少 20%；降到约 83.3 秒对应加速 1.2 倍。

建议实验保持模型、任务集、硬件、输出质量标准、采样配置和计时边界一致，记录端到端时间及分阶段耗时，多次重复。冷启动和热启动分开，不能仅给并行组预热或缓存。输出正确性由可执行测试/已知答案检查，而非模型自评。

即使四个 Agent 同时发请求，模型服务也可能将推理排队；工具工作和模型调用交错后才可能真正节省端到端时间。若主耗时无法并行，额外通信、反馈和调度会抵消收益。**先用真实模型和工具测并行空间，再花时间做完整框架。**

### 5.5 第一周验证与退出条件

1. 固定 AIOS、SDK、模型和推理后端版本，跑通最小调用。
2. 用同一模型跑四个短任务，测串行与并行的正确率、排队和耗时。
3. 验证 AIOS-Agent SDK 的任务执行和数据交互可用。
4. 说明候选任务为什么需要不同角色、哪些四项工作可以并行、三对反馈是否有实际价值。
5. 澄清端侧部署口径、单 Agent 限制定义、资源支持范围。

若安装与版本适配持续阻塞、四项主要工作无法并行，或任务主要靠强行限制单 Agent 才成立，暂缓本题。不能用固定延迟、模拟模型输出或降低结果质量来证明达标。

## 六、proj2：看起来是 B 类，实际系统门槛不低

### 6.1 它真正要做的闭环

```text
感知真实负载与资源需求
    → 决策选择/生成调度策略
    → 通过 sched_ext/scx 实际执行
    → 观测效果与异常
    → 继续调整或回退
```

只做监控页面、生成建议或调用模型回答“应该用什么调度器”，没有形成要求的运行闭环。[识别稿第 3 节][TEXT]

题目允许“选择或生成”策略，因此可能先从现有策略集合中选择，无须一开始自动生成全新 eBPF 调度器。是否必须使用 LLM，截图没有明说；“Agent”不自动等于必须是 LLM，也不表示纯规则控制器一定被接受。定题前确认。

### 6.2 一个需要尽早验证的环境风险

题目要求在 openEuler 24.03-LTS-SP3 编译、运行和测试。openEuler 官方说明该版本基于 6.6 内核；scx 上游说明 sched_ext 从上游 Linux 6.12 起支持。因此，**不能仅凭系统版本名称推断指定镜像已经具备所需调度接口**。[openEuler 官方下载说明][WOE]、[scx 官方仓库][WSCX]

这不证明 openEuler 一定不支持：发行版可能回移植特性。必须检查实际内核构建、`CONFIG_SCHED_CLASS_EXT`、BTF/BPF 配置和工具版本，或取得题目方提供的镜像/补丁。Linux 官方文档列出了相关配置及调度器加载状态接口。[Linux sched_ext 文档][WEXT]

换发行版或自行换内核是否满足指定交付环境，也应确认，不能用在其他 Linux 跑通代替本题验收。

### 6.3 对你们的知识链和投入风险

```text
Linux 进程/线程/权限和性能工具
    → CPU 调度、延迟/吞吐/公平性
    → eBPF/BTF、sched_ext 接口、scx 工程
    → workload 特征采集
    → 策略选择、稳定性、回退和防抖动
    → 在指定系统做可重复对照实验
```

真实性能改善往往比跑通更难。需要比较默认调度器、固定专家策略、自适应策略，并报告额外开销、切换频率和退化场景。没有必要承诺所有负载均优于默认。

若有熟悉 Linux 调度的导师、可直接运行的镜像和两个明确目标负载，本题可作为进阶选择；在你们当前条件下，它比 proj5 更容易将时间消耗在环境、底层概念与测量噪声上。

### 6.4 定题前要问

- 指定镜像和内核补丁在哪里？允许替换/重编内核吗？scx 用哪个版本？
- 策略选择是否足够，是否要求 LLM？可选策略是否由官方提供？
- “支持扩展”要求实现接口，还是必须完成网络/安全/cgroup 的实际扩展案例？背景的“可进一步扩展”与任务条目的“支持”应怎样验收？
- “交付环境”具体包含什么？基准负载、计时和默认策略如何固定？

## 七、proj1：不要先买板再发现问题在 OS 与驱动之间

### 7.1 任务的层次与知识链

原文给了从 QEMU CPU 推理到 RK3588 NPU、SG2002 TPU 的层次，基础层可以不依赖实体板卡。它使用**提供的统一 ACT 模型**，不是要求从零训练模型，也没有在这些截图中要求搭建完整机器人。[识别稿第 2 节][TEXT]

ACT 是模仿学习中的 Action Chunking with Transformers，处理动作序列，不应套用 LLM 的 token 生成流程理解。本次仅查阅了论文摘要作为概念核对，未验证官方统一模型具体结构。[ACT 原始论文][WACT]

```text
C/C++ 或 Rust 工程与交叉编译
    → StarryOS 启动、用户态接口与运行时依赖
    → ACT 输入/输出与算子
    → 推理库/运行时适配和正确性校验
    → QEMU CPU 路线
    → 板卡启动、驱动、NPU/TPU 工具链、资源约束和优化
```

### 7.2 为什么 GPU 和可采购板卡仍不足以消除风险

你们的 4090 可以帮助生成参考推理结果，但不能替代题目指定目标上的推理。PC Linux 跑通、开发板厂商 Linux 跑通，与 **StarryOS 上跑通**是不同的验证阶段。

RKNN 上游明确区分 PC 模型转换、板端 Runtime 和内核驱动；有 RK3588 工具链，不代表该驱动和运行库可以直接在 StarryOS 使用。必须确认现有移植与接口支持程度。[Rockchip 官方 RKNN 工程][WRKNN]

StarryOS 上游是基于 ArceOS 的实验性单体 OS，提供构建与 QEMU 路径；这只能说明有可学习的基线，不能证明本题所需算子、驱动和板卡已全部支持。[StarryOS 官方仓库][WSTARRY]

### 7.3 若仍想选，正确的短验证顺序

1. 取得统一模型、输入、输出校验方式、允许的转换/量化规则和指定版本。
2. 在现有 Linux 环境生成可信参考结果，识别模型依赖和不支持的算子。
3. 编译启动指定 StarryOS 基线，验证最小用户程序；核实 CPU 推理库是否已有移植。
4. 在 QEMU 中运行统一模型并校验输出，再考虑板卡路线。
5. 取得明确支持清单后再决定采购哪块板、如何调试驱动。

QEMU 的耗时不能直接冒充真实开发板实时延迟；应分开报告。截图没有具体实时阈值，需确认计时口径。量化与裁剪虽标为可选，仍需满足统一模型和输出要求，不能任意替换模型。

对你们的默认建议仍是暂缓：当前需要同时补 C 工程、OS、模型推理和潜在驱动适配，容易超出约 300 人时的有效开发预算。若题目方提供已可运行的模型和镜像，风险判断再更新。

## 八、proj3：当前不建议用它作为第一次系统项目

proj3 包含六个相互依赖的工作面：调度、执行抽象、故障隔离、上下文管理、真实场景和通信，且强调完整性、深入实现和机制创新。[识别稿第 4 节][TEXT]

它与 proj4 的关键区别：proj4 主要在既有 AIOS 中把具体协作任务做好；proj3 需要设计并证明支撑多 Agent 的运行机制。实际可复用现有组件的范围需要官方确认。

主要学习链：

```text
并发/异步编程与进程隔离
    → 任务图、动态依赖、生命周期与通信
    → 资源配额、可观测性、调度与容错
    → 上下文一致性、复用、压缩和隔离
    → 模型后端集成、真实负载与系统性实验
```

还需区分两种“上下文”：消息/文本历史可以由应用层管理；模型内部 KV Cache 涉及推理后端、模型版本和缓存一致性，不能把合并提示词直接称为 KV Cache 优化。截图背景提到了两者，但必做要求的深度尚需澄清。

三人约十周可以做一个小型运行时原型，但原型不自动等于满足该题全部要求。你们尚未接触教学 OS 和系统工程，选它容易形成“概念很多、实际只做工作流”的结果。建议先通过 proj5 或一个成熟的 proj4 项目积累经验。

## 九、给你们的具体推进方案

### 9.1 先按 proj5 准备，尽早处理课程来源
