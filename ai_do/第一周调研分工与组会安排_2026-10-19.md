# OS 设计赛第一周调研分工与组会安排

**周期：2026 年 10 月 19 日（周一）至 10 月 25 日（周日）。**  
**周日晚上进行线下分享与讨论。建议预留 90 分钟，具体开始时间与地点由组内确定。**  
**投入目标：每人约 10 小时，包含资料整理和组会；三人均参加、均分享。**

## 一、本周目标

本周先建立对比赛和技术方向的认识，给后续选题提供共同基础。三人都要了解 2025 年 OS 内核实现赛道在做什么，各自调研一个不同的优秀内核作品；本届五道功能挑战题分工覆盖，再补充一道 2025 年功能题作为参照。

周日组会应形成三项结果：

1. 大家能说明两条赛道的目标、主要技术工作和学习路径。
2. 能根据团队基础、兴趣、时间和资源，提出有理由的赛道与题目候选。
3. 确定下一周的小型验证任务，并形成长期准备计划的初稿。

**本周的达标标准是“能用自己的话说明白，判断有资料依据”。编译优秀作品、完成 OS 实验、深入源码或复现论文均不作为必交任务。** 不因为暂时没看懂复杂实现就否定一个方向，也不因为题名熟悉或演示漂亮就认定容易。

本安排中标出的截止时间、材料格式和时长是团队执行建议；比赛原始要求以官方文件和题目页面为准。现有[选题分析文档][ANALYSIS]只作参考，大家不需要支持其中已有的推荐顺序，可以提出不同判断。

## 四、共同模块：2025 年 OS 内核赛道要了解到什么程度

### 4.1 要回答的六个问题

| 问题 | 本周需要了解的内容 | 达标表现 |
| --- | --- | --- |
| 比赛到底要交什么？ | 参赛队提供内核工程，在规定环境运行用户程序和测试，另有文档与展示等材料 | 能区分“写应用”“实现内核”“准备完整参赛工程” |
| “题目”长什么样？ | 平台要求、构建约定、测试集、功能与性能评测，不只是一个开放题名 | 能解释为什么每年都是做 OS，具体要求仍会变化 |
| 2025 年要求什么平台和运行方式？ | 从官方历史分支核对 RISC-V、LoongArch、QEMU、测试镜像等信息，注明年份 | 能把目标架构、模拟器、操作系统内核、用户程序分别放到正确位置 |
| 通过测试需要什么能力？ | 用 2～3 个测试例子关联到进程、内存、文件、系统调用或网络 | 能说明“运行一个命令”背后为什么依赖多个 OS 模块 |
| 需要学什么？ | 语言与工具、体系结构、OS 核心模块、调试和实验 | 能画出有先后依赖的知识链，而不只罗列课程名称 |
| 我们距离起步差什么？ | 结合 C/Python 基础、Linux 使用经验和零教学内核经历 | 能提出前三项应补基础，不以“太难”或“有 AI 就行”代替分析 |

历史评测主要入口：[2025 年测试集 pre-2025 分支][TESTS]、[2025 年官方参考资料][REF2025]。测试集默认分支可能已经指向其他年份，调研时固定到 2025 年资料，并区分初赛、决赛与资料后续更新。

### 4.2 核心概念只需先建立功能认识

| 概念 | 本周讲到这个程度即可 | 后续再深入的内容 |
| --- | --- | --- |
| 用户态、内核态、系统调用 | 应用如何请求 OS 服务，为什么有权限边界 | 寄存器保存、陷入汇编和 ABI 细节 |
| 进程、线程、调度 | OS 管理执行对象，决定谁何时使用 CPU | 多核同步、抢占实现和调度算法证明 |
| 虚拟内存、页表 | 进程使用的地址如何通过映射受到管理和隔离 | 页表代码、TLB、一致性和缺页处理细节 |
| 文件系统、VFS | 如何用统一接口组织文件访问，为什么需要兼容不同存储实现 | inode 生命周期、缓存和文件系统格式细节 |
| 驱动 | OS 如何与具体设备交互 | 设备寄存器、DMA、中断控制器移植 |
| 架构、QEMU、交叉编译 | 指令集是目标，QEMU 模拟机器，交叉编译为目标生成程序 | 启动链、板级支持和工具链配置 |
| 测试与性能 | 功能是否正确和运行是否高效，是不同问题 | 优化策略、统计显著性和大型基准复现 |

至少能画出一条过程：**用户程序 → 系统调用 → 内核模块 → 必要时访问设备 → 返回结果**。可以用文件读取、创建进程等例子解释，不要求追踪真实汇编。

### 4.3 共同模块交付

每个人在自己的笔记中写出：

- 一句话解释内核赛道目标。
- 一张简图，标出平台、内核、用户程序和测试之间的关系。
- 一条学习知识链，并圈出自己最陌生的 3 个环节。
- 两条来自官方历史资料的信息，附链接和对应段落/标题。

三人可以读同一份题目资料，但先各自形成理解。组会只集中讨论分歧，不重复讲三遍相同规则。

观察角度只用于减少三人重复，不要求只看一项。三人都需对各自项目形成整体认识。

### 5.2 案例卡必须包含的八项内容

| 项目 | 需要记录什么 | 本周深度边界 |
| --- | --- | --- |
| 基本身份 | 年份、队伍/学校、奖项、源码与文档入口 | 奖项用官方名单核对，不能凭仓库名或星数认定优秀 |
| 作品目标 | 它想构造什么内核，支持什么平台和应用 | 用自己的话写 2～3 句 |
| 架构与模块 | 语言、主要层次、进程/内存/文件等模块 | 读 README、目录和设计文档的架构章节，画简图 |
| 主要能力 | 选出 3～5 项代表功能 | 能解释功能意义，不把所有系统调用逐个抄下来 |
| 一项代表机制 | 选 HAL、写时复制、缓存、异步调度等任一项 | 讲清“问题—做法—作用—代价/疑问”，不要求理解所有实现细节 |
| 依赖知识 | 为读懂/实现该机制需要哪些知识 | 区分基础必学与后续进阶 |
| 成果证据 | 作者给出的测试、实验图表、演示或设计对比 | 至少指出一项证据的来源，并说明自己有没有复现 |
| 可借鉴与困难 | 对我们有什么启发，最大两个学习门槛是什么 | 提炼方法，不能以复制整套功能作为下周目标 |

**一项机制能讲明白的标准：** 例如选择写时复制，应能说明“创建进程时立即复制全部页面可能有开销；先共享可读页面，写入时再复制相关页；需要管理映射、权限和页面归属”。本周不要求写缺页处理或理解全部引用计数代码。

### 5.3 阅读顺序与停止点

1. 先看项目简介和设计文档目录，弄清对象。
2. 看一张架构图，找到各大模块位置。
3. 选一项机制，阅读相应章节和作者给出的结果。
4. 如仍有余力，只定位一个相关源码目录或入口，记录其用途。
5. 回到团队问题：它说明内核赛在考什么，我们应先学什么？

本周做到第 3 步并能解释清楚即可。Rust 陌生语法、复杂泛型、汇编和并发细节可列入待学清单，不必逐行阅读。README 声称“支持”的功能，与自己实测通过的功能要分开写；赛后版本也不自动等于赛时完成情况。

## 六、功能挑战模块：两张题目卡要了解到什么程度

### 6.1 每道题统一回答九个问题

1. **做什么：** 用两句话说明问题和目标，避免只重复题名。
2. **交什么：** 作品是内核功能、工具、模型适配、运行时还是协作应用？运行在哪里？
3. **硬要求：** 哪些平台、数量、模型、性能指标是题目明确要求？哪些是选做或背景描述？
4. **怎么评价：** 功能、性能、创新、工程、展示各看什么？哪些权重或折算不清楚？
5. **大致怎么做：** 用 4～6 步或一张图描述可能的实现路径，并标为个人设想。
6. **要学什么：** 列出有依赖顺序的知识链，区分我们已有、需入门、需深入的内容。
7. **需要什么资源：** 硬件、系统、权限、数据、模型、导师支持，哪些已经具备，哪些待确认？
8. **难在哪里：** 写出最大的两个技术/资源风险，提出下一周可做的一个小验证。
9. **是否推荐：** 给出“优先验证 / 保留 / 暂缓”及理由，写清什么条件变化会改变判断。

每题原则上读完截图原文，再打开 1～2 个一手参考资料的 README、架构图或摘要。不要只读现有 AI 调研结论；也不要求把题目引用的所有论文全文看完。

### 6.3 B 负责：proj2 资源管控、proj4 多智能体协作

### 6.5 三人都应遵循的资料区分

- 将“官方明确要求”“项目作者陈述”“本人判断”“尚待确认”分开标注。
- A/B 标签、当前选题队伍数、论文中的最高性能，都不能直接推导获奖难度或我们能达到的效果。
- 参考资料中的 Agent 操作系统与传统 OS 内核并非同一层次，要讲清具体对象。
- 对逐题评分与赛道总技术方案的衔接，只记录问题，不自行假定折算方式。

## 七、自选学习：每人补 2～3 个相关概念

从自己负责内容中选择最影响理解的概念，用约 45 分钟完成入门。可选例子：

| 对应内容 | 可选概念 |
| --- | --- |
| 内核案例/课程实践 | 系统调用、用户态/内核态、上下文切换、虚拟内存、HAL、VFS |
| ACT | 模型推理与训练的区别、量化、推理运行时、驱动 |
| 资源管控 | workload、吞吐与延迟、eBPF、调度策略 |
| Agent 系统 | Runtime、任务 DAG、上下文、KV Cache、进程隔离、RAG |

每个概念写四行：**它是什么、解决什么问题、在所调研项目中哪里用到、自己还没理解什么。** 可以画小图；如果想写代码，只做自己能解释的轻量练习，例如观察进程或画依赖图，不影响主要调研进度。三人无需学习完全相同的概念。

AI 可以辅助解释、翻译和列出阅读问题；关键规则、数量、评分和项目成果仍要回到原始来源核对。笔记中简单记下 AI 帮助了哪些环节；分享时应能脱离 AI 生成稿解释自己的内容，不必背诵陌生术语。

## 八、交付材料与周内节点

### 8.1 每个人交一份材料即可

建议一份 Markdown/PDF/PPT 主材料，覆盖以下内容；不要求三种格式重复制作。采用笔记时建议正文约 1500～2500 字，图表和链接不计入，仅作篇幅参考。

1. **赛道概览：** 共同模块的目标、流程图与知识链，约半页。
2. **一个内核案例卡：** 基本信息、架构简图、代表机制、证据、启发与门槛，约 1 页。
3. **两张功能题卡：** 按九个统一问题组织，每张约半页至 1 页。
4. **学习记录与个人意见：** 新理解的概念、推荐候选、待确认问题、下周建议，约半页。
5. **来源：** 官方题目、仓库/设计文档等链接，并注明查看的年份或分支；引用实验结果时标注位置。

材料少而能讲清楚，优于长篇复制。模板中的尚未知项可以写“待确认”，但应说明怎样核实，不用猜测填满。

### 8.2 建议节点

| 时间 | 要做什么 |
| --- | --- |
| 周一 10-19 | 确认 A/B/C 姓名、内核案例与题目分配，检查资料能否访问 |
| 周二～周三 10-20～10-21 | 完成赛道概览、案例初读，建立题目卡框架 |
| 周三晚 | 各用三句话同步：看了什么、目前理解、遇到什么疑问；无需另开长会 |
| 周四～周六 10-22～10-24 | 补齐代表机制、功能题要求和自选概念，形成材料 |
| **周六 10-24 22:00 前（建议）** | 将初稿放到三人可共同访问的位置，方便预读 |
| 周日会前 | 每人约 15～20 分钟预读另外两人的结论，各准备至少一个问题；计入材料整理时间 |
| **周日 10-25 晚** | 线下分享、讨论选题和下一周任务，形成会议记录 |

材料命名可采用 `W1_A_姓名_调研.md` 等，存放到组内约定的位置；本安排不预设你们已经有共享仓库或在线协作文档。

## 九、周日线下组会安排

### 9.1 90 分钟议程

| 环节 | 时长 | 主要内容 |
| --- | ---: | --- |
| 开场 | 5 分钟 | 明确本次要形成候选和验证计划，不要求强行定题 |
| A 分享 + 提问 | 12 + 3 分钟 | NoAxiom、proj1/proj5、学习收获与个人判断 |
| B 分享 + 提问 | 12 + 3 分钟 | Chronix、proj2/proj4、学习收获与个人判断 |
| C 分享 + 提问 | 12 + 3 分钟 | Starry Mix、proj3/往年 proj352、学习收获与个人判断 |
| 共同校准 | 10 分钟 | 两赛道在做什么、知识链有哪些共识、哪些规则仍待核实 |
| 选题与思路讨论 | 20 分钟 | 比较兴趣、可行性、成果与风险，保留 1～2 个候选 |
| 下周与长期计划初稿 | 10 分钟 | 给候选安排验证、负责人、截止和继续/暂缓条件 |
| 合计 | **90 分钟** | 如有未解决的问题，记为待办，不无限延长会议 |

每次组会轮换主持、计时和记录职责。第一周由三人自行确定对应人选。

### 9.2 每人 12 分钟分享怎么讲

- 约 30 秒：一句话说出自己对内核赛的认识或最初误解。
- 约 4 分 30 秒：内核案例的整体结构、一项机制和对我们的启发。
- 约 5 分钟：两道功能题各约 2 分 30 秒，重点讲目标、硬要求、知识链和风险。
- 约 2 分钟：自己新学到的概念、推荐方向、最需要团队讨论的问题。

不逐页朗读材料，不演示漫长安装过程。讲不清的地方可以明确说“不确定”，由团队一起列出查证办法；被问到实现细节时，说明本周阅读边界即可。

### 9.3 会上讨论选题时统一比较这六项

| 维度 | 讨论问题 |
| --- | --- |
| 兴趣 | 三人是否愿意持续做？各自最想学什么？ |
| 基础距离 | 需要同时补几层新知识？哪个环节最容易卡住？ |
| 任务边界 | 必做要求是否明确？能否拆出较早可见的阶段成果？ |
| 资源与支持 | 硬件、模型、课程来源、权限和导师是否落实？ |
| 评价与成果 | 怎样证明完成、正确或有改进？成果是否适合展示和复用？ |
| 下周可验证性 | 用有限时间能验证哪个最大不确定性？结果怎样影响选择？ |

各自可先独立写出最想验证的两个方向及理由，再讨论，避免第一个发言的意见成为默认结论。内核赛与功能赛都保留讨论资格；本周的调研分工不代表已经承诺某个赛道。

### 9.4 会议记录必须留下什么

| 记录项 | 内容要求 |
| --- | --- |
| 共同认识 | 两赛道目标、主要门槛和需要补的基础 |
| 候选 | 1～2 个候选赛道/题目及理由；仍不确定时如实记录 |
| 暂缓方向 | 原因是兴趣、资源、基础、范围还是规则不清，而非仅写“难” |
| 待确认问题 | 问题、核实途径、负责人、预计完成时间 |
| 下周验证 | 每个验证的目标、具体任务、负责人、时间预算、交付和通过/停止条件 |
| 长期计划初稿 | 准备按“基础学习 → 小验证 → 核心实现 → 实验与交付”推进；下一次何时复盘 |

**若本周证据足够，可以提出主选；若证据不足，组会成果可以是候选加验证方案。** 不应为了周日必须拍板而跳过课程来源、运行环境等关键问题，也不宜将后续每周都变成无限扩大范围的资料搜集。

## 十、后续每周组会的固定方式

保留每周一次分享与讨论，原则上周日晚上，通常控制在 60～90 分钟；具体安排由团队协调。

每人之后按五点汇报：

1. 上周承诺了什么，实际完成什么？
2. 新学会了什么，能够用例子解释什么？
3. 有什么证据：文档理解、小实验、运行日志、代码或数据？
4. 目前最影响进度的问题是什么，需要谁协助？
5. 下周准备交出什么，验收条件是什么？

会议重心随阶段变化：第一周是认识与比较；下一阶段是基础学习和候选验证；定题后转向模块实现与集成；最后转向稳定性、实验、文档与演示。长期计划可以调整，但每次都应落到下一周的具体交付。
