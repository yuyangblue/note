# proj4 多 Agent 协作系统：开发与实验计划

**周期：2026-10-26 至 2026-12-27，共 9 个完整周阶段。**  
**团队：三人，每人每周约 10 小时；每人约 90 小时，团队约 270 人时。**  
**目标：完成符合题意的多 Agent 协作系统、可复现实验和实验报告，争取 12 月 25 日完成正式提交，12 月 26～27 日留作缓冲。**

计划编制于 2026-10-25，承接上一阶段的认识性调研。从本计划开始，工作重心转为开发、集成和验证。按已有截图要求制定，不将计划中的内部目标冒充官方评分标准。

配套资料：[本届题目识别稿][TOPIC]、[已有选题分析][ANALYSIS]、[实验报告模板][REPORT]。真实结果应在实验完成后填写，当前没有预设性能数字或成功率。

## 一、九周最终要交出什么

### 1.1 系统与题目要求逐项对应

| 题目要求 | 最终应交出的功能 | 可检查的证据 |
| --- | --- | --- |
| Linux + AIOS + 端侧 7B/8B 模型 | 在约定 Linux 环境中运行 AIOS、Cerebrum 和本地模型后端 | 环境清单、版本、启动过程、模型调用日志 |
| 使用 AIOS-Agent SDK | Agent 通过 SDK/AIOS 完成实际执行，接口适配有说明 | 代码入口、调用链、真实运行日志 |
| 不少于 4 种 Agent | 至少四类职责、工具或能力不同的 Agent | 角色定义、对应代码、输入输出与运行记录 |
| 至少 4 个可并行子任务 | 在真实任务中存在至少四项可同时推进的工作，能够自动分配给适合的 Agent | 任务图、分配规则、开始结束时间与重叠轨迹 |
| 至少 3 对不同类型 Agent 双向交互 | 三对以上有实质内容的请求—反馈—处理过程 | 消息记录、反馈造成的行动变化，不用空消息凑数量 |
| 满足顺序与依赖 | 下游等待必要结果；具备明确任务状态、超时和失败处理 | 正常案例、延迟/失败案例、依赖检查记录 |
| 正确完成复杂任务 | 输出可以由测试、真值或明确标准核验 | 任务集、校验器、正确/错误案例 |
| 相对多 Agent 串行执行，总时间减少至少 20% | 同等条件的串行基线与并发方案 | 原始数据、配对对照、计时边界和统计分析 |

来源：[proj4 任务及评分原文][TOPIC]第 5 节。20% 是题目中可见的要求；本计划不保证实现后自动达到，应尽早验证。题目对“单智能体无法完成”、端侧部署及评分折算的边界需在第一周核实。

### 1.2 交付包

1. **代码与配置：** Agent、任务分配、通信、工具、串行/并发运行模式、评测脚本、依赖与配置样例。
2. **可运行环境：** AIOS、SDK、模型/量化版本、推理后端、操作系统、驱动、硬件和启动说明；固定验证过的版本或提交号。
3. **实验材料：** 开发集/测试集清单、校验标准、原始日志与数据、生成表格和图的脚本。
4. **实验报告：** 问题、设计、实现、方法、结果、分析、局限、团队贡献及引用来源。
5. **提交材料：** README、项目/设计文档、AI 使用说明、演示视频及官方要求的其他材料。现有总技术方案要求视频分享链接放在仓库 README，提交前再次核对当届通知。

## 二、范围与实现路线

### 2.1 第一周选定一个具体场景，此后围绕同一场景推进

优先采用：输入可固定、有清晰正确性标准、至少四项主要工作可并行、三对反馈有实际价值的任务。减少依赖互联网检索或不受控网站速度，方便重复实验。

可先讨论“软件项目故障诊断与复现验证”候选：日志分析、源码分析、配置/依赖分析、测试复现四类 Agent 各有工具和职责，先并行开展初步诊断，再围绕候选原因反馈和验证。

**这只是候选架构，不代表已经满足“单智能体无法完成”的认定。** 一个工具充分的单 Agent 可能也能完成该任务。第一周应向题目方澄清是在什么能力、权限或预算条件下判断，避免故意削弱单 Agent 来制造结论。场景可据此调整，运行框架和日志/评测基础可继续开发。

到 11 月 1 日应有一页《场景与验收约定》，明确：输入、最终输出、四类角色、四项并行任务、三对双向交互、依赖、正确性标准和资源边界。不继续同时开发两个完整场景。

### 2.2 起步技术栈

- 开发语言：Python；Shell 用于必要的启动与环境操作，JSON/YAML 用于配置和数据。
- AIOS + Cerebrum SDK；Python 可先统一 3.10，具体依赖组合经过验证后锁定。
- 先用一个 7B/8B 指令模型和一个推理后端；优先沿用已跑通的 Ollama 路径，遇到实际并发瓶颈后再评估后端调整。
- 第一台 4090 服务器运行模型、AIOS 与实验任务，笔记本远程开发；第二台服务器作为备用或独立复现资源。
- 多个 Agent 可共享模型服务；共享方式、上下文和并发数量都需记录。
- 起步先提供命令行和结构化日志。可视化服务于解释运行过程，不另建庞大前端工程。

AIOS 官方将 kernel 与 Cerebrum SDK 区分，并提供本地模型后端配置。先建立最小可运行链路，再固定兼容版本，不同时堆叠多个 Agent 框架。[AIOS 官方仓库][AIOS]、[Cerebrum 官方仓库][SDK]

## 五、逐周任务与验收

### W1：10 月 26 日～11 月 1 日——场景、环境与最小链路

**共同学习：** Python 项目结构、虚拟环境、Git、SSH、HTTP/JSON；理解 Agent、SDK、AIOS、模型后端之间的调用关系。

- **A：** 建立团队代码目录与版本管理；固定候选 AIOS/SDK 版本；通过 SDK/AIOS 跑一次最小模型调用，记录入口与日志。
- **B：** 核对服务器 OS、驱动、可用显存和权限；启动一个 7B/8B 模型；提供稳定调用配置，测一个简单请求。
- **C：** 比较至多两个候选场景，准备 3 个小样例及可判断对错的标准；列出角色、并行任务和交互关系；建立报告骨架。
- **共同：** 确认场景、课程外部支持和资源；核实端侧服务器部署、单 Agent 条件、评分衔接与指定版本等规则边界。

**周日验收：** 一人提交任务，日志能证明 SDK → AIOS → 本地模型 → 结果的链路；其余两人能按说明复现调用。提交《场景与验收约定》及环境清单，未获得官方答复的项目如实标注。

**控制点：** 若安装连续消耗两个工作时段仍无进展，三人集中诊断一个版本组合，缩到官方最小示例；不要三个人分别另装不同技术栈。规则疑问不影响学习与可复用接口开发，但场景合规性不能假装已解决。

### W2：11 月 2 日～8 日——真实工具任务与统一接口

**共同学习：** 类和模块、异常处理、日志、工具参数验证；了解串行与并发的区别。

- **A：** 定义任务、Agent 和消息的最小数据结构；建立单 Agent 执行入口、状态与错误返回；把 SDK 接入封装成团队可复用接口。
- **B：** 实现一个与场景相关的真实工具，例如固定文件/日志解析、源码检索或测试执行；统一工具输入输出和失败返回。
- **C：** 构建约 6 个开发样例和校验器初版；写实验协议草稿，确定计时边界、成功标准、超时和重试预算。

**周日验收：** 一个 Agent 通过 AIOS/SDK 使用真实模型和工具，完成至少一个可核验任务。明确哪些动作由模型决策、哪些是确定性工具；不能只展示模型直接生成一段答案。

**报告：** 写问题定义、应用场景、系统组件和实验方法草稿；样例与代码对应。新增能力必须有一个能重复运行的检查案例。

### W3：11 月 9 日～15 日——四类 Agent 的串行完整基线

**共同学习：** 角色职责、上下文管理、结构化输出、任务状态和基本依赖关系。

- **A：** 集成至少四类 Agent；建立满足依赖的串行执行模式；记录状态迁移和各阶段耗时。
- **B：** 补齐角色所需工具及模型配置；明确各角色的工具、上下文和输出差异，不以改角色名称代替能力差异。
- **C：** 把校验器接入全任务，扩展开发样例至约 10 个；形成运行一次就能保存结果、正确性、耗时与版本信息的脚本。

**周日验收：** 四类 Agent 能在同一框架中串行完成一个完整任务，运行和数据链路可追踪；准备至少 3 次端到端记录，解释错误案例。这一版本是后续基线，不必已经达到高成功率。

**报告：** 填写角色/工具表、任务流程、基线定义、初步正确性问题。当前最重要的是可靠完成整条链，不增加角色数量或第二个模型。

### W4：11 月 16 日～22 日——依赖调度、自动分配和实际并行

**共同学习：** `async/await`、有界并发、任务图、超时与等待；分清 Agent 层并发和模型后端实际吞吐。

- **A：** 实现依据任务类型/能力等规则的自动分配、依赖就绪判断和并发执行；保留串行模式；接入反馈消息处理。
- **B：** 测模型后端在 1/2/4 个请求下的行为和资源占用，核实是否排队；改进工具并发调用和结构化返回。
- **C：** 用时间轨迹核对至少四个实际子任务的重叠；补依赖、延迟和错误输入用例；串行/并行两模式共用任务和校验器。

**周日验收：** 至少一个真实任务中，四项可并行工作自动分配并出现实际时间重叠；下游不会在缺少必要输入时运行。至少一对 Agent 的双向反馈可改变后续行动。

**报告：** 补架构图、任务图、状态/通信说明和第一张执行时间线。若只有日志声称“并行”，而实际执行被同步接口串行阻塞，应先修链路。

### W5：11 月 23 日～29 日——完整协作、正确性和首次性能判断

**共同学习：** 端到端计时、正确性与性能的关系、反馈开销、成功与失败分类。

- **A：** 完成至少三对不同类型 Agent 的双向交互；落实依赖、有限重试、超时和明确的失败状态；避免无限反馈循环。
- **B：** 统计模型排队、工具耗时和上下文增长；记录 GPU 等实际资源；在固定资源预算下调整已知配置。
- **C：** 在开发集对串行/并行模式做首轮配对实验；分别报告正确性、总时间和分阶段耗时；准备独立测试集分组方案。

**周日验收：** 对需求表逐项演示：四类 Agent、四项并行工作、自动分配、三对双向交互、依赖与正确输出均有证据；至少 5 个开发案例有对照数据。

**性能检查：** 尝试达到 `T_parallel ≤ 0.8 × T_serial`。如果尚未达到，必须指出主要瓶颈并在下周集中验证；不能只拿最快一次作为结论，也不能牺牲正确性或删掉必要反馈。

**报告：** 形成“系统设计与实现”主体、正确性检查、初步结果及瓶颈清单。到此应已有完整系统，后续不把所有核心能力留到 12 月才开发。

### W6：11 月 30 日～12 月 6 日——有限优化与核心冻结

**共同学习：** 用阶段日志判断瓶颈；区分模型、工具、通信和串行依赖耗时。

- **A：** 选一个主要运行瓶颈优化，例如避免无必要等待、减少重复调度或采用合理的并发上限；记录改动前后行为。
- **B：** 围绕真实瓶颈优化后端配置、上下文或工具路径，固定模型与资源。确需换推理后端时，先留可回退版本，并重跑两种模式。
- **C：** 固定正式实验协议、样例分组和分析脚本；独立测试集目标 20 个，最低规划 12 个案例，来自至少 3 类任务模式或工作负载。若准备不足，减少扩展实验而不降低核心要求。

**周日验收：** 核心功能回归通过，开发集结果有据可查；为正式实验标记代码、配置、模型和数据版本。12 月 6 日后原则上只修影响验收的错误和已定位瓶颈，不重写整体架构。

**未达到 20% 时：** 检查任务是否有足够真实并行空间、模型是否排队、反馈是否过多、工具是否阻塞。可以调整开发场景和实现，但需说明调整理由、保留结果，再锁定新的独立测试集；不得事后挑选正式测试结果。

**报告：** 实验方法定稿、优化动机与对照、正式实验版本表。

### W7：12 月 7 日～13 日——正式实验与失败分析

**共同学习：** 配对重复实验、结果聚合、失败样本分析和结论边界。

- **A：** 稳定集成版本，处理影响运行的错误；核对日志能够证明真实 AIOS/SDK 调用和交互，不增加新功能。
- **B：** 固定实验机器及可用 GPU，记录其他负载、后端并发和资源配置；执行自动化批量实验并保存环境信息。
- **C：** 组织主实验：独立测试案例逐个跑串行和并行，目标每种模式至少 3 次；汇总全部运行、正确性、超时、总时间和阶段耗时。

**周日验收：** 完成主要正式对照及原始数据归档；形成总表、执行时间线、正确性比较和失败分类。明确 20% 是否达到、在哪些范围达到，以及哪些案例退化。

**若正式结果不达标：** 如实记录，不填写预设结论。仍需优化时，形成新版本并完整重跑主要对照；已用于调参的案例不再当作未见测试集，并披露这一变化。

**报告：** 结果、分析与局限形成完整草稿，至少解释一个成功案例和一个失败/退化案例。

### W8：12 月 14 日～20 日——独立复现与报告完成

**共同工作：** 用“没有参与该模块的人”视角检查交付。

- **A：** 完善 README、入口、配置样例和依赖锁定；由另一成员按说明重新部署/运行，修复隐含手工步骤。
- **B：** 复核模型、环境与资源记录；在隔离环境或备用服务器验证可运行性。不同硬件数据单独报告，不混入主对照。
- **C：** 补必要边界/稳定性实验，核对图表由原始数据生成；整合报告初稿和附录，列出待修事项。

**周日验收：** 报告从问题到结论均完整，无待编造数据；至少一人能按交付说明运行一个完整案例；演示走通。主实验版本如有修复，评估并补跑受影响实验。

**报告：** 全文、引用、团队分工、AI 使用说明、复现步骤完整；逐项对照比赛交付物。

### W9：12 月 21 日～27 日——冻结、演示和正式提交

- **A：** 冻结发布版本，核对仓库、配置和启动/评测入口；处理必要修复并记录版本变更。
- **B：** 准备固定演示环境，确认模型和必要数据可用；录制运行演示，检查日志和资源说明。
- **C：** 完成最终报告、数据索引和材料核查，检查图表、实验数字、来源和 README 链接。
- **共同：** 每个人解释自己的模块、关键设计、实验与限制；检查官方提交入口和新通知；争取 12 月 25 日完成正式提交并留存提交记录。

**12 月 26～27 日：** 用于上传/链接/构建等故障处理，不计划大型新功能。最后的周日可以用简短交付核查代替长组会，不能等到晚间会议后才开始提交。

**验收：** 最终代码、报告、实验数据与视频内容一致；视频分享与仓库权限按官方要求设置，提交记录可核对。

## 六、从第二周开始固定实验方法

### 6.1 基线怎么设

| 方案 | 用途 | 对照原则 |
| --- | --- | --- |
| **同一多 Agent 系统串行执行** | 题目要求的主基线 | 相同角色、工具、模型、能力与反馈规则，只将可并行工作的执行限制为串行；依赖仍必须合法 |
| **多 Agent 并发执行** | 参赛主方案 | 使用依赖调度与有界并发，不能省略正确完成任务所需工作 |
| 单 Agent（条件允许时） | 补充分析多角色价值 | 不替代题目主基线；能力、工具、上下文及预算需说明，不故意削弱 |
| 一项消融实验（有余力时） | 解释某个机制的作用 | 如固定分配与自动分配对比；只在核心实验完成后开展 |

不把“模型自己输出答案”与“多 Agent 调用工具完成全部任务”作为唯一性能对照。

### 6.2 20% 的计算与正确性约束

```text
单次配对时间减少比例 = (T_serial - T_parallel) / T_serial
题目中可见的目标：T_parallel ≤ 0.8 × T_serial
对应加速比：T_serial / T_parallel ≥ 1.25
```

提前固定总体汇总方式，例如报告测试集总耗时比例，同时给逐案例结果、各案例重复运行的中位数和波动。多次运行配对、交错执行或随机顺序，减少服务器负载和热启动顺序影响。

正确性优先：报告全部案例成功率、超时和错误分布；性能收益不能靠少做任务或降低输出质量获得。内部目标是并行正确性不低于串行，但该目标不是截图提供的额外官方阈值。

失败运行也保留，按预先约定的超时上限、重试预算记账；不要静默删除慢运行或失败运行。可单列“两种模式均成功”的耗时比较，但必须说明它只是子集，不能代替全测试集的正确性与失败情况。

### 6.3 数据规模与重复次数

- W1：3 个小样例，只验证任务定义。
- W2：约 6 个开发样例。
- W3～W5：约 10 个开发案例及可重复对照。
- W6：规划独立测试集，最低目标 12 个案例，优先 20 个，覆盖至少 3 类任务模式/负载。
- W7：每个测试案例，每种主模式至少 3 次，最低规划为 `12 × 2 × 3 = 72` 次端到端运行；20 个案例对应 120 次。批量运行的机器等待时间另行预留，不等于同等人工工作时间。

这里的数量是团队在现有时间内的实验计划，不是官方指定样本量，也不保证统计充分性。相同基础模板或相近故障的变体应按组划分开发/测试，避免近重复泄漏；若只覆盖有限场景，在报告中明确局限。

### 6.4 环境与计时要一致

- 串行与并行使用同一模型/量化、硬件、工具、数据、采样参数和质量标准；固定上下文、输出和重试预算。
- 主对照采用相同可用资源预算。若后续使用第二台服务器，另设实验，不把资源增加的收益都归因于协作机制。
- 以协调器收到任务到输出通过校验为端到端边界；另记录模型、工具、等待、反馈与校验耗时。后台工具未结束时不提前停止计时。
- 区分冷启动与预热后的运行。两种模式采用相同预热与缓存政策，不只给并行方案预热。
- 全局端到端时间尽量由同一进程的单调时钟统计，避免跨服务器时钟不一致；各子进程用统一任务 ID 关联事件。
- 保留模型请求排队、工具并行和实际任务重叠证据。四个 Agent 同时发请求，不等于模型真正同时推理。

### 6.5 最小数据记录字段

| 数据 | 至少记录 |
| --- | --- |
| 运行身份 | `run_id`、`case_id`、模式、重复编号、代码/数据/配置版本 |
| 环境 | OS、GPU、模型/量化、AIOS/SDK、后端和并发参数 |
| 任务 | 输入摘要、依赖、分配角色、状态和重试 |
| 交互 | 发送方、接收方、消息类型、内容/内容引用、时间、导致的行动 |
| 性能 | 端到端耗时、模型/工具/等待耗时、调用次数、可获得的资源指标 |
| 正确性 | 校验结果、期望/实际输出、错误/超时原因 |

## 八、协作与每周组会

每周日线下组会继续保留，约 90 分钟：每人 10 分钟演示/数据与 5 分钟提问，共 45 分钟；集成检查 15 分钟；主要问题讨论 20 分钟；下周任务确认 10 分钟。

每人周会前更新：本周承诺与完成、运行/数据证据、最大阻塞、报告更新、下周验收。每周记录下一个里程碑，不重新无限扩展选题。

代码接口先约定任务、消息、工具与结果的数据结构。多人协作使用短分支，尽量每周中有一次小集成，不把所有合并留到周日。各自负责的改动需有相关案例验证，避免只写与实现重复的形式化测试。

每周验收由另一位成员按说明操作；讲解人能说明各步骤和失败原因。复杂问题可以共同排查，但避免只有 A 能运行整套系统。

## 九、进度风险与调整规则

| 触发情况 | 优先处理 | 仍需保留 |
| --- | --- | --- |
| W1 末最小链路未通 | 固定一个环境/版本组合，共同排查最小示例，压缩 UI 和额外框架探索 | SDK/AIOS、本地模型和可追踪调用 |
| W3 末没有完整串行案例 | 缩小任务数据与工具范围，先打通端到端，再扩案例 | 四类角色最终要求、真实工具与正确性 |
| W4 末没有真实并行 | 检查同步阻塞、工具路径、模型排队与任务依赖；停止加角色 | 四项可并行任务、合法依赖和自动分配 |
| W5～W6 低于 20% | 根据阶段数据集中优化一个主瓶颈，必要时调整开发场景并重新锁定测试集 | 真实工作量、反馈质量、同等资源与完整记录 |
| W7 数据仍不足 | 减少非必需消融、前端和第二硬件实验，优先主对照与正确性 | 原始日志、重复实验和失败统计 |
| W8 有关键修复 | 标记新版本，评估并补跑受影响数据，更新报告 | 版本与报告一致性 |
| 截止前仍有未达项 | 如实记录完成范围与限制，优先保证现有成果可运行、可核验 | 不虚构指标、不以演示脚本伪装系统能力 |

可以缩减：第二个场景、更多模型、复杂界面、多机调度、大量额外 Agent、非必需消融。不能将题目明确的四类 Agent、四项并行任务、三对双向交互、AIOS/SDK、本地模型和正确性悄悄删掉。

计划是进度与验收安排，不是性能保证。若正式结果未达到题目要求，应披露并继续在剩余时间内修正，不能在报告中预填“达到 20%”。
