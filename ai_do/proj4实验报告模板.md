## 3. 总体架构

- **分层图**：编排器 / Agent / AIOS kernel / 模型后端，四层各自边界。
- **调用链**：一次完整任务从入口到输出的真实路径，**以日志为证**，不只画示意图。
- **任务状态机**：created → ready → running → waiting_dep → done / failed / timeout，逐项说明迁移条件。
- **自动分配规则**：按什么把子任务派给哪个 Agent（能力标签/任务类型/负载），规则写死在哪里。
- **通信机制**：用 AIOS 的 memory 还是 storage，还是自建消息层；为什么这样选。
- **串行 / 并行双模式**：同一个调度器如何切换，保证两种模式跑的是同一套角色、工具、模型与反馈规则。

⚠️ 必须说明：**所有 Agent 是否都经由 `send_request` 走 kernel**。若有直连模型后端的旁路，在此披露并说明对性能结论的影响。

## 6. 实验设计

### 6.1 基线

| 方案 | 角色 | 对照原则 |
| --- | --- | --- |
| 同一多 Agent 系统串行执行 | **主基线** | 相同角色、工具、模型、能力与反馈规则，仅把可并行工作限制为串行，依赖仍合法 |
| 多 Agent 并发执行 | 主方案 | 依赖调度 + 有界并发，不省略必要工作 |
| 单 Agent（条件允许） | 补充分析 | 不替代主基线；能力/工具/上下文/预算须说明，不故意削弱 |
| 消融实验（有余力） | 解释某机制 | 只在核心实验完成后做 |

### 6.2 指标与计算

```
单次配对减少比例 = (T_serial - T_parallel) / T_serial
目标：T_parallel ≤ 0.8 × T_serial
等价加速比：T_serial / T_parallel ≥ 1.25
```

- 汇总方式（总体耗时比例 / 逐案例中位数）：**提前定，不得事后改**
- 重复次数与执行顺序（交错 / 随机化）：
- 计时边界：**协调器收到任务 → 输出通过校验**；后台工具未结束不提前停表
- 冷启动与预热政策：两种模式一致，不只给并行方案预热

### 6.3 数据规模

| 阶段 | 样例数 | 说明 |
| --- | --- | --- |
| W1 | 3 | 只验证任务定义 |
| W2 | ~6 | 开发样例 |
| W3～W5 | ~10 | 开发案例 + 可重复对照 |
| W6 | ≥12，目标 20 | 独立测试集，覆盖 ≥3 类任务模式 |
| W7 | 12 × 2 × 3 = 72 次起 | 每案例每模式 ≥3 次 |

近重复泄漏控制：相同模板或相近故障的变体按组划分开发/测试，不得跨组。

### 6.4 单次运行记录字段

| 类别 | 字段 |
| --- | --- |
| 身份 | `run_id`、`case_id`、模式、重复编号、代码/数据/配置版本 |
| 环境 | OS、GPU、模型与量化、AIOS/SDK、后端与并发参数 |
| 任务 | 输入摘要、依赖、分配角色、状态、重试次数 |
| 交互 | 发送方、接收方、消息类型、内容或引用、时间、导致的行动变化 |
| 性能 | 端到端耗时、模型/工具/等待耗时、调用次数、资源指标 |
| 正确性 | 校验结果、期望/实际输出、错误或超时原因 |

## 7. 结果与正确性

- **总表**：逐案例的串行/并行耗时、减少比例、是否正确。
- **执行时间线**：至少一个案例的四项子任务真实重叠轨迹。
- **正确性表**：全部案例成功率、超时、错误分布。失败运行保留，按约定预算记账，**不静默删除**。
- **耗时构成**：模型 / 工具 / 等待 / 反馈 / 校验各占多少。
- **子集说明**：若另列"两模式均成功"的耗时比较，须注明它只是子集，不能代替全测试集结论。

**结论表述**：20% 是否达到、在哪些案例范围达到、哪些案例退化。达不到就写达不到。
