## 二、架构：四层（决赛文档 p6-7，原文分四点）

```
┌─ 第 4 层  Starry modules ────────────────────────────┐
│  starry-core  宏内核基础：进程管理、加载 ELF、VFS 抽象   │
│  starry-api   POSIX 行为：文件描述符、系统调用、procfs/devfs │
│  starry       入口：加载初始化进程、退出时清理资源        │
├─ 第 3 层  Starry crates（不依赖具体 OS，专为宏内核设计）──┤
│  starry-process 会话/进程组/进程管理                     │
│  starry-signal  信号处理逻辑                            │
│  starry-vm      虚拟内存（用户空间）访存                 │
├─ 第 2 层  ArceOS modules（与具体 OS 相关，难剥离）──────┤
│  axalloc 内存分配 / axconfig 配置 / axdriver 驱动接口    │
│  axhal 硬件抽象层 / axmm 内存管理 / axnet TCP-IP         │
│  axruntime 系统初始化 / axsync 同步原语 / axtask 任务调度 │
│  【他们新设计的】axfs-ng 文件系统、axinput 输入设备       │
├─ 第 1 层  ArceOS crates（与 OS 无关，用户态内核态都能跑）─┤
│  axbacktrace / extern-trait / lwext4_rust                │
│  scope-local / simple-sdmmc / weak-map                   │
└──────────────────────────────────────────────────────┘
                        ↓ 建立在
        ArceOS（Rust 组件化 unikernel）+ StarryOS（宏内核）
```

**一句话理解**：ArceOS 本来是个 unikernel（整个系统一个地址空间、跑一个应用），StarryOS 把它改造成宏内核，Starry Mix 在这俩之上继续加东西。他们的做法是把能通用的东西**抽成独立组件**（第 1 层），这样别的 OS 也能用。

## 三、复用了什么 vs 新增了什么（你的专属角度，这题的答案）

### 3.1 上游给的基础（复用）

- **ArceOS**：组件化 unikernel，给了 axalloc / axconfig / axdriver / axhal / axlog / axmm / axnet / axruntime / axsync / axtask 这些模块（初赛文档 p4 列了清单）。
- **starry-next（StarryOS）**：ArceOS 之上的宏内核。starry-mix 仓库从 starry-next 的 `c5942de` 提交处分叉（初赛文档 p30）。
- **第三方**：lwext4（Ext4，C 语言）、rust-fatfs（vfat）、smoltcp（TCP/IP）、kernel_elf_parser（ELF 加载）、arceos-org/allocator（内存分配算法）。
- **调度**：ArceOS 自带的 FIFO / Round-robin / CFS 三种，后两者支持抢占（初赛文档 p19）。**调度算法不是他们做的。**
- **明确写"参考或直接使用他人工作"的只有两项**：共享内存实现、SockAddr 封装（初赛文档 p30）。其余新增代码基本独立完成。

## 五、四个代表机制候选（挑一个，按"问题→做法→作用→代价"展开）

> 排序按**对你们的好讲程度**，不是按重要性。

### 候选 A：UserPtr —— 用户地址访问（推荐指数 ★★★★★）
**位置**：`prelim.pdf` p8-9 / `final.pdf` p23-26（5.4 节）

- **问题**：Starry Mix 内核和用户共用一套页表地址空间。原来用户指针就是裸指针，导致①内核访问缺页时会直接崩溃（因为内核缺页被视为致命）；②无法按 POSIX 规范返回 `EFAULT`；③要频繁写 `unsafe`；④处理字符串切片很烦。
- **做法**：设计 `UserPtr<T>` / `UserConstPtr<T>` 封装裸指针。转引用时做三件事：检查地址对齐、检查内存权限是否允许用户读/写、把范围内没分配的页全部分配。另外加了个全局标志位 `ACCESSING_USER_MEM`——内核正在访问用户内存时，缺页处理就不拒绝来自内核的异常（用来处理 `get_as_str` 这种长度未知的情况）。
- **作用**：既满足了 POSIX 语义，又保留了"内核缺页=致命错误"这个安全假设。
- **代价/疑问**：`ACCESSING_USER_MEM` 是个全局标志位，作者自己说是为了处理不定长数据做的妥协——多核下这个标志位怎么维护？文档没说，可以列为疑问。
- **为什么推荐**：不需要懂 Rust 异步，概念是「用户给内核一个地址，内核不能直接信」，跟你们学系统调用、用户态/内核态直接对得上。

### 候选 B：weak-map —— 进程资源自动回收（推荐指数 ★★★★）
**位置**：`prelim.pdf` p21-24（4.3.2 / 4.3.3）/ `final.pdf` p29-31

- **问题**：进程组、会话这些结构，要在"所有进程都退出了"时自动回收；同时内核有时要遍历所有进程，得知道谁还活着——都要引用计数。但常规做法是父节点存子节点强引用，这样只能自动回收叶子节点，中间的进程组还得手动判断。
- **做法**：反过来——**子节点保存父节点的强引用**，再配一个 `WeakMap`（接口和 `BTreeMap` 一样，但内部存弱引用）。弱引用失效时，访问它"如同"该条目不存在。内部用操作计数器懒惰清理：累计 1000 次操作才尝试清一次。
- **作用**：利用 Rust 的所有权机制自动回收，不用手写管理代码，也避免了引用泄漏。
- **代价/疑问**：懒惰清理意味着过期条目会多存活一段时间；阈值 1000 是怎么定的没说。
- **为什么推荐**：能顺带讲清"引用计数 / 强引用 / 弱引用 / 进程组"，是 OS 正经概念。

### 候选 C：axfs-ng 文件系统重构（推荐指数 ★★★）
**位置**：`prelim.pdf` p10-18 / `final.pdf` p32-40

- **问题**：原 ArceOS 的 axfs 有三个毛病——①所有操作基于绝对路径，效率差且语义不符合 UNIX，导致 `openat`、`fstatat` 很难实现；②不提供 inode、owner、permission、软硬链接；③并发访问有问题。
- **做法**：从头写 `axfs-ng`。用 Rust 1.86 的 Trait Upcasting 把节点拆成 `NodeOps` / `FileNodeOps` / `DirNodeOps` 三个 trait（后两个继承自第一个），**把"这是文件还是文件夹"的检查从运行时搬到编译时**。又引入 `Location` 类型描述节点完整位置（因为挂载的存在，光有目录项不够）。目录项缓存（类似 Linux dentry）加速查找并保证内存里只有一份。
- **作用**：支持 Ext4、vfat、tmpfs、procfs、devfs，还能挂载子文件系统。
- **代价/疑问**：`rust-fatfs` 原本只考虑单线程，他们加了全局互斥锁才安全；procfs 这种动态文件系统必须禁用 dentry 缓存。
- **注意**：文件系统内容多，容易讲散。选它的话，就**只讲 Trait Upcasting 或只讲 dentry 缓存**其中一点。

### 候选 D：同步 + 异步混合机制（推荐指数 ★★，需要 Rust 异步基础）
**位置**：`final.pdf` p12-16（第 3 章）

- **问题**：早期全用同步等待队列（`WaitQueue`）。但 `poll` 等待 I/O 时，一个任务可能同时挂在多个唤醒源上——硬件、另一个任务、超时，都可能唤醒它。同步队列表达不了。
- **做法**：对上层仍然暴露同步 API，底层引入异步支持层。实现了轻量 Future 执行器，用 `block_on` / `block_on_interruptible` 两个函数把异步世界和同步世界接起来，把"能唤醒当前任务的回调"包装成 `Waker` 传给 `Future::poll`。
- **作用**：能复用 Rust 异步生态（event-listener、async-channel）来实现 Unix Domain Socket、匿名管道；还能优雅实现信号打断（Future 是轮询的，一次 poll 结束后可以主动检查信号）。
- **代价/疑问**：这是**决赛才新增的**，初赛文档里完全没有这一章——所以它特别适合作为"参赛增量"的证据。但你要先搞懂 Rust 的 Future / Waker，门槛最高。
- 顺带记一句他们为什么不全盘异步：Rust 异步有"传染性"，全改异步等于把整个运行时编译成一个巨大状态机，带来代码膨胀和额外开销。

## 六、可以直接抄进案例卡的几句话（换成你自己的话再用）

- **基本身份**：2025 年一等奖，清华大学 Starry Mix 队，队员郭士尧、王铮。基于 ArceOS（Rust 组件化 unikernel）和 StarryOS（其上的宏内核）继续开发。
- **作品目标**（参考，别照抄）：在已有的 Rust 教学/实验内核基础上，做出一个能跑真实 Linux 应用、支持多架构多板卡的宏内核，并且把过程中通用的部分抽成可复用组件。
- **依赖知识**（基础必学）：用户态/内核态与系统调用、虚拟内存与页表、进程/线程与调度、文件系统与 VFS、设备驱动与中断、Rust 所有权与 trait（**这是他们最大的门槛，也是你们的**）。
- **可借鉴**：①不要求从零写内核，站在 ArceOS 这种成熟底座上做增量是官方允许的（2025 参考资料明确写了"重点是参赛队自己独立完成的内核增量工作"）；②把通用逻辑抽成独立组件（axprocess、axsignal、weak-map），既利于工程也利于展示"我做了什么"。
- **最大两个门槛**（供你判断）：①**Rust 语言与类型系统**——他们的很多设计（Trait Upcasting、extern-trait、WeakMap）依赖较深的 Rust 特性，你们目前是零 Rust 基础；②**已有底座的代码规模**——ArceOS + StarryOS 本身已经很大，要在半年内读懂并做出增量，需要很强的代码阅读能力。
