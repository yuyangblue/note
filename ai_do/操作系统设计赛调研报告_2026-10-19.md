# 操作系统设计赛调研报告

调研日期：2026 年 10 月 19 日（北京时间）  
主要对象：2026 年全国大学生计算机系统能力大赛操作系统设计赛——中西部与华南区域赛  
范围：本地制度文件、2024 年与 2025 年全国赛历史资料、官方题目与开源作品。**按要求，本届具体赛题暂不纳入分析，也不提前确定题号。**

## 阅读结论

1. **先确认参赛资格，再选择赛道。** 本届区域赛的内核实现赛道面向本科、专科和高职学生；功能挑战赛道还接受硕士生。每队 1～3 人，同校组队，每队至少 1 位、至多 2 位指导教师，报名人员只能选择一个赛道。[本地章程][L1]（第 2～3 页）
2. **若你们首次参赛、没有完整教学内核经验，且希望在本届周期内交付完整作品，我优先建议考察范围明确、环境可得、能客观评测的功能挑战题。** 如果已经做过 xv6/rCore 的关键实验，队友稳定，目标是系统学习内核并持续投入，则内核实现更合适。这是基于项目依赖和交付风险的条件性判断，不是对你个人基础的推定。
3. **不要把区域赛当成全国赛同一套排名，也不要认为功能赛必然简单。** 区域赛独立组织，优秀队伍可经推荐、审核取得全国赛决赛资格，章程没有给出保送比例或名额。往届全国赛中，功能题可以深入 Linux 锁、文件系统和 GPU；内核题则要求各子系统协同工作。[本地章程][L1]（第 1 页）、[往届功能获奖项目汇总][W4]
4. **本届评分尤其看重可交付性。** 内核赛代码通过率参考占 40%，功能赛项目/代码执行展示参考占 30%；其余分别涉及文档、工程规范、AI 工具说明和视频。应从第一天积累设计、测试和决策记录。[本地技术方案][L2]（第 2 页）

### 1.5 必须交付什么

**内核实现赛道**：[本地技术方案][L2]第 2～3 页。

- 完整内核工程：全部源码、必要代码注释、辅助编译文件、建立编译环境的 Docker 文件等。
- 本地开发环境与评测构建环境应保持一致，开发语言不设限制。
- 设计与分析文档：设计思路、实现重点、问题与解决方法、AI 工具使用说明等。
- 自动测试平台上的记录与成绩。原文要求：“至少有一次完整通过功能与性能测试的记录和有效成绩”。
- 演示视频上传百度网盘，将分享链接放入仓库 README。

**关于“完整通过”的边界：** 本报告保留原文，不自行将它解释为“有任意非零分即可”，也不擅自判定必须所有测试点满分。后续拿到本届评测说明时，应确认有效提交和达标的具体定义。这是内核赛选型前值得核实的关键条件。

**功能挑战赛道**：[本地技术方案][L2]第 1～2 页。

- 从本届区域赛官网发布的题目中选择，并按题目要求实现。
- 提交完整代码、项目文档、功能/性能/创新性测试分析，以及与类似项目的比较。
- 过程文档包含设计、实现、注释、遇到的问题及解决方式、AI 工具说明。
- 演示视频上传百度网盘，链接写入 README。

建议两赛道共同维护：固定版本的环境说明、可重复执行的测试脚本、实验原始数据、已知限制、第三方依赖清单、团队分工和 AI 使用日志。这些是交付建议，不是额外编造的强制规则。

建议从现在起记录“AI 帮了什么—人工如何核对—哪些设计与实验由队员完成”。本报告属于前期调研辅助，不能代替你们的参赛设计、实现和实测结果。

## 二、结合往届赛题：两个赛道需要什么知识链、考什么、竞争如何

### 2.1 先看两条赛道的工作对象

| 维度 | OS 内核实现 | OS 功能挑战 |
| --- | --- | --- |
| 核心任务 | 构造、整合一个能够在规定平台运行测试程序的 OS | 在指定题目下完成系统、模块、工具或功能改进 |
| 知识形状 | 覆盖面广，子系统依赖强 | 先有公共系统基础，再在某一方向深入 |
| 典型调试问题 | 为什么异常返回失败？为什么进程退出影响其他进程？为什么文件读写与内存映射不一致？ | 为什么采集不到事件？为什么优化在另一负载下退化？为什么定位结果不可信？ |
| 主要成果证据 | 真实运行、测例通过、稳定性、性能、架构设计与过程记录 | 明确需求、实现增量、基线对比、功能正确性、改进效果与复现 |
| 风险来源 | 底层故障会阻塞整个系统；合并后的交互错误多 | 题目范围、外部依赖和验收口径差异很大 |
| 初次参赛的可控性 | 有教学内核经验和可复现基线时明显提高 | 能选择范围清楚、低外部依赖的题时明显提高 |

这张表是对本届技术目标和历史项目的分析，不是官方给两个赛道排的难度等级。

### 2.2 内核实现：从“能启动”到“能可靠运行用户程序”

#### 历史证据

**2024 年样本：Phoenix。** 官方收录的 2024 年一等奖项目使用 Rust、RISC-V64，支持多核，采用异步无栈协程的模块化宏内核；涉及进程管理、写时复制、虚拟文件系统和缓存等。作者记录其在决赛第一阶段通过了除部分 LTP 外的测试。这个样本说明，高水平作品早已超出“启动并输出文字”的教学第一步。[官方历史获奖列表][W5]、[Phoenix 项目][W6]

**2025 年题目：Linux 应用兼容与多架构协作。** 官方历史分支列出 basic、BusyBox、Lua、libc-test、iozone、UnixBench、iperf、libc-bench、lmbench、netperf、cyclictest、LTP 等测试组，并描述 RISC-V、LoongArch 内核构建及 EXT4 测试镜像。它考查的是运行测试程序时呈现的系统行为。[2025 年官方测试集历史分支][W3]

**2025 年优秀作品：NoAxiom。** 项目自述支持 RISC-V64、LoongArch64，使用 HAL 分离架构相关逻辑，并实现调度、VFS、信号、内存和网络等模块。这可以作为设计深度的参考，但 README 的当前状态可能包含赛后整理，不能把全部功能当成本届区域赛起步门槛。[NoAxiom 项目][W7]

**特别注意：** 上述多架构、EXT4 和测试组属于 2025 年全国赛历史证据。本地 2026 年区域赛技术方案没有在当前三页中指定同样的架构、文件系统或测例数量。后续应根据本届题目裁剪任务，不能照单全收。

#### 建议的知识依赖链

```text
C 或 Rust 系统编程 + 数据结构 + Git/Linux 工具
    ↓
编译、链接、ELF、ABI、调用约定、汇编与交叉编译
    ↓
目标架构特权级、异常/中断、定时器、启动与调试
    ↓
物理内存、页表、地址空间、缺页与用户指针检查
    ↓
任务上下文、进程/线程、调度、同步与进程生命周期
    ↓
设备驱动、块设备、VFS、文件描述符、文件系统
    ↓
按测例实现系统调用语义，接通用户程序运行环境
    ↓
回归测试 → 定位跨模块错误 → 性能分析与优化
```

实现时会迭代交叉，不是前一层完全学完才能动下一层。下表说明每层应学到什么程度。

| 层次 | 必要知识 | 可操作的掌握标志 |
| --- | --- | --- |
| 语言与工程 | C 指针/内存布局，或 Rust 所有权、生命周期、`unsafe`、`no_std`；构建系统、Git、Docker | 能读懂并修改现有系统代码；能在干净环境构建 |
| 程序如何运行 | 汇编、链接脚本、ELF 段、栈、寄存器、ABI | 能解释内核入口、用户程序入口和函数调用；能检查反汇编与符号 |
| 架构与异常 | 特权级、陷入与返回、时钟中断、地址转换 | 能单步追踪一次系统调用或时钟中断，不靠盲目插入日志 |
| 内存 | 页帧分配、堆、页表、映射权限、用户地址验证 | 能解释虚拟地址如何落到物理页；能定位权限或生命周期错误 |
| 进程与并发 | 上下文切换、调度、创建/执行/等待/退出、锁和等待队列 | 多任务可持续运行；资源释放后不会破坏别的任务 |
| 存储与 I/O | 驱动、块缓存、VFS、目录、inode、文件描述符 | 文件操作语义一致；进程退出、共享描述符等情况有定义 |
| 用户态兼容 | 按题目需要补全 ABI、errno、信号、时间、管道、线程或网络 | 不只是系统调用“有函数”，而是参数、返回值、边界条件符合用例 |
| 调试与验证 | QEMU/GDB、最小复现、日志分级、基线和回归 | 一个失败能追踪到原因；修改后知道哪些旧功能仍正确 |

其中写时复制、动态链接、多核、复杂网络等是否必做，要由本届测例决定；应了解其位置，但无需在选题前全部实现。教学入门可选 [MIT xv6][W14] 或 [rCore 教程][W15]，它们提供从基本执行环境到进程、内存、文件系统的系统学习路径。

#### 到底考核什么

我的归纳是四项：**软硬件边界的理解、跨子系统设计、兼容性细节、持续调试能力**。例如，程序创建子进程后读写文件失败，原因可能同时涉及地址空间复制、共享文件表、锁、退出回收和系统调用参数，而不是补一段文件读写代码就能解决。

算法与数据结构基础有用，但仅凭刷题能力不足以覆盖上述依赖。Rust/C 熟练也不能自动替代体系结构和 OS 语义知识。

### 2.3 功能挑战：公共基础之外，按题目建立一条纵向知识链

#### 真实历史题目给出的差异

| 历史样本 | 实际任务 | 对应知识链与考核重点（分析） |
| --- | --- | --- |
| 2024 年 proj333：龙架构 QEMU 高性能插桩工具 | 基于 QEMU 做类似 Pin 的动态插桩，适配接口并给出应用案例 | ISA/ABI → 动态二进制翻译 → 插桩接口 → 正确性和额外开销；同时涉及编译与体系结构。[题目原文][W8] |
| 2025 年 proj62：Linux 锁优先级传递 | 为相关锁机制实现优先级继承，给出相对原生锁的时延测试 | 调度/并发 → 优先级反转 → 锁等待关系 → 内核实现 → 最坏时延和回归验证。[题目原文][W9] |
| 2025 年 proj284：F2FS/EROFS 支持 large folios | 为文件系统适配 large folios；题目区分只读压缩文件与可读写、含 GC 的路径 | 虚拟内存 → page cache → folio 生命周期 → 文件系统读写/回收 → 正确性和成本对比。[题目原文][W10] |
| 2025 年 proj275：eBPF 追踪 AI/ML 负载 | 采集并关联 CPU/GPU 行为，用于端到端性能分析 | Linux 进程与 I/O → eBPF 探针/数据通道 → AI 运行时与 GPU 工具 → 时间线关联 → 开销和定位能力。[题目原文][W11] |
| 2025 年 proj352：基于 LLM 的 kdump 分析 | 结合故障现场、对应版本内核源码及 RAG 给出诊断建议 | 崩溃现场/调用栈 → 符号和源码匹配 → 检索 → 模型诊断 → 真实故障验证。[题目原文][W12] |

官方获奖汇总将上述 proj333 列为 2024 年一等奖项目，将 proj62、proj284、proj275、proj352 列为 2025 年一等奖项目，说明这些方向有形成高质量成果的先例；**它不能证明原题容易，也不能证明这些题号在本届区域赛可选。** [往届功能获奖项目汇总][W4]

历史题目仓库有的会沿用并修改下一年描述，有的已归档。例如 proj333 当前标为归档；阅读时应同时核对获奖年份、README 所述年份和本届可选题单，不能只看仓库仍可访问就直接报名。

#### 各方向共用的底座

```text
Linux 使用 + C/Rust 或题目要求的语言 + Git/构建/脚本
    ↓
OS 基础：进程、虚拟内存、文件系统、并发、用户态/内核态
    ↓
跑通原项目，阅读现有实现，确定“原来能做什么”
    ↓
只深入题目所需的一至两个子系统
    ↓
实现新增能力或优化 → 对照实验 → 回归与边界测试
    ↓
解释贡献、限制与失败案例，提供可复现交付
```

具体再分四类：

| 方向 | 额外需要补齐 | 更应准备的证据 | 初次参赛主要风险 |
| --- | --- | --- | --- |
| 可观测性与性能工具 | 探针、事件、时间戳、数据丢失、进程/线程关联；eBPF 题还需 map、verifier、libbpf 等 | 与已有工具/人工结果的核对、事件覆盖、额外 CPU/内存开销、定位案例 | 只做仪表盘，无法证明采集正确或有新增价值 |
| Linux 内核子系统优化 | 对应子系统源码、锁与生命周期、内核编译、调试、补丁流程 | 正确性回归、相同条件下基线、不同负载和参数下的表现 | 少量代码牵涉复杂语义；只展示平均性能，遗漏退化 |
| 移植、驱动与虚拟化 | ISA、ABI、启动链、设备树、中断、MMU/IOMMU 或虚拟化机制，按题选学 | 真实目标环境的运行证据、兼容范围、稳定性 | 板卡、固件、资料或实验权限迟迟不到位 |
| AI 辅助系统诊断 | Linux 故障分析、版本化源码、检索与数据处理、评测集构造 | 故障真值、检索命中、定位准确性、相对无检索/规则基线的收益、失败案例 | 把聊天接口当技术贡献；没有可信样本和标准答案 |

eBPF 相关能力可参考 [Linux 官方 libbpf 文档][W16]；内核开发与测试的公共资源可从 [Linux 内核官方文档][W17]进入。这里的知识链和实验建议是我的技术分析，不是要求每支功能赛队伍把四类内容都学一遍。

#### 到底考核什么

功能赛主要体现：**能否理解需求和已有系统、作出明确的技术增量、证明效果、解释适用边界。** “跑通原仓库”只能建立基线；“比原来快”也需要说明负载、硬件、版本、正确性和重复实验条件。

例如 LLM 崩溃分析题，需要证明故障现场和内核版本被正确识别、结论能定位到真实原因，不能只展示模型输出流畅。文件系统题即使修改行数少，也可能需要深入理解页缓存、压缩、回收和并发关系，难度不低于部分内核实现任务。

#### 我对竞争的判断

**内核赛：交付门槛高，头部竞争也强。** 报名规模较小不代表容易拿奖。历史一等奖作品反复出现多核、异步调度、缓存、跨架构抽象等内容，已有教学实验和持续开发经验的队伍优势明显。首参队最大的风险往往先是系统整合不起来，其次才是排名不够高。[Phoenix][W6]、[NoAxiom][W7]

**功能赛：题目间差异大，选题本身影响竞争位置。** 可以选较窄的任务降低整合面，也可能选到 Linux 核心子系统、GPU 或 Hypervisor 等很深的题。参与者知识背景更广，本届区域功能赛还包含硕士生。竞争常体现为“别人已经有工作基线和可靠实验，你是否只有演示”。但没有逐题报名与获奖数据，不能声称某个热门题必然拥挤、某个冷门题就容易获奖。

**区域赛：可把目标设为高质量交付，但不能提前判断竞争轻松。** 当前参考评分对工程规范、分析和展示给出明确权重，这为认真完成项目的初次参赛队伍提供了努力方向；与此同时，章程没有固定奖项比例，存在空缺可能。[本地章程][L1]第 5 页、[本地技术方案][L2]第 2 页。

## 三、我推荐怎么选赛道和选题

### 3.1 当前建议：先用自身条件筛赛道，再用可验证性筛题目

你的年级、学籍、Linux/C/Rust 基础、队友和可投入时间尚未提供，因此现在给出条件化建议；不伪装成已经完成个性化定题。

| 条件 | 我的倾向 |
| --- | --- |
| 队伍含硕士生 | 按本地章程优先考虑功能挑战；先确认所有成员身份合规 |
| 首参，没有完整教学 OS 经验，希望本届形成完整成果 | 优先看功能挑战中的工具、测试、可观测性或边界明确的功能扩展题 |
| 已做过 xv6/rCore 的内存、进程、文件系统实验，能解释关键实现 | 认真考虑内核赛；先验证本届评测基线和有效提交要求 |
| 有稳定内核代码基础、同方向导师和 2～3 人协作队伍 | 内核赛或深入的内核功能题都可以，以长期方向选择 |
| 熟悉某个 Linux 子系统或已有相关科研背景 | 优先选择与已有能力相邻的功能题，争取更深贡献 |
| 主要擅长前端/应用/模型调用，OS 基础薄弱 | 先补系统基础，选择能切实进入 OS 机制的题；不要只做界面或模型外壳 |

**我目前的默认推荐：功能挑战优先，具体优先级是“需求清楚、环境可得、导师可沟通、两周能建立运行与评测基线、还能做出明确增量”。** 如果你已经具备教学内核经验，这个默认顺序可以反转。

### 3.2 功能赛：优先考察的方向

以下是等待本届题单时的筛选方向，不是自命题许可。若正式题目有更大的必做范围，必须整体评估；不能自行缩小后就认为满足赛题。

#### 第一优先：有明确诊断对象的系统观测、调试或测试工具

适合：有 Linux 和基本编程基础，希望较快获得真实结果的队伍。

- 候选问题：某类程序的调度等待、系统调用耗时、I/O 阻塞、资源异常，或某个内核模块的回归定位。
- 起步实验：固定工作负载，采集一种有明确语义的事件，和已有工具/人工标记对齐，再逐步做关联或诊断。
- 贡献空间：降低额外开销、补齐盲区、定位具体瓶颈、提高复现与分析效率；依据正式题目选其中一项深入。
- 验收证据：事件是否准确、是否丢失、开销多少、是否能解释真实异常，并提供相同环境下的基线。
- 风险：现成工具很多，简单套壳缺少增量；如果是 CPU/GPU 端到端题，GPU 环境和跨层关联会显著提高难度。不能将 proj275 的完整目标误当成一个简单 CPU 追踪小工具。[历史题目示例][W11]

#### 第二优先：成熟项目中边界清楚的单模块扩展或性能改进

适合：已能读系统源码，有导师帮助识别修改边界的队伍。

- 候选问题：一条文件访问路径、一个缓存策略、一个测试框架能力、某个兼容接口或受限场景下的调度改进。
- 起步实验：先跑通未修改版本，建立稳定基线，再证明某个瓶颈或缺失能力确实存在。
- 贡献空间：改动集中，但机制解释充分，能够处理回归和失败情况。
- 风险：接口看起来很小，语义可能很大。历史 large folios 题就区分了不同文件系统路径的难度，不能以代码量估计工作量。[历史题目示例][W10]

#### 第三优先：AI 辅助内核诊断，仅在数据和评测有保障时选

适合：既能理解 Linux 故障，又有数据处理/检索经验，并能获得真实样本的队伍。

- 起步先确认：有没有可合法使用、带可靠原因标注的故障样本？内核版本和符号能否匹配？人工能否验证模型结论？
- 实验至少区分：已有分析方式、直接模型回答、加入源码检索后的结果；避免把同一故障的近重复样本同时放进开发集和评测集。
- 有效贡献可以是检索精度、版本匹配、证据定位、误报控制或流程自动化。
- 若缺少真值数据，暂缓此类题。AI 不是替代 OS 知识的捷径。[历史题目示例][W12]

#### 初次参赛时谨慎选择

- 依赖尚未落实的开发板、专有 GPU、固件、内网数据或特权环境的题。
- 同时要求学习新语言、新架构、新 OS 和新领域的题。
- “完整重做一个通用 OS”“完整 Hypervisor”“多硬件多平台全适配”等范围过大的任务，除非已有直接基础且正式题目允许合理分阶段。
- 只写“显著提升性能/实现智能化”，但没有基线、数据和验收指标的题。

这不是排斥高难题，而是依据当前约十周周期与未知基础，优先控制外部依赖和学习跨度。

### 3.3 内核赛：主要选择是基线、架构和实现范围

内核赛通常围绕共同评测目标竞争，选题不像功能赛那样主要表现为挑一个独立题号。更关键的是选择什么基础、怎么组织系统、先支持哪些必需能力。

1. **优先使用团队最熟悉的语言。** C 和 Rust 都可行，本届技术方案没有语言限制。不要同时把“学习全新语言”和“完成内核”作为必须赶完的两个大项目。
2. **先从本届要求倒推。** 架构、启动方式、镜像格式、测试入口、输出协议、资源限制、工具链版本全部确认后，再决定基线。2025 年的双架构要求只是历史例子。
3. **先证明基线可复现。** 能在干净环境构建、启动、运行真实测试和结束；知道原项目已实现什么、你们要新增什么。
4. **以稳定、可解释的完成度为第一阶段目标。** 不要为追求新颖调度器或复杂架构而反复推倒重写。若正式任务需要多架构，应尽早设计 HAL 边界，避免临近截止才补第二架构。
5. **每次扩展都回归。** 优先解决会阻塞多个测试组的公共问题，再补特定接口。性能优化需建立在正确性之上。
6. **保留参考与贡献边界。** 哪些来自教程、第三方库、往届作品，哪些是新增设计和代码，要能通过文档、提交历史和实验对应起来。[本地技术方案][L2]第 1～3 页。

建议入门前先做一个小验证：能否独立追踪一次陷入与返回，说明用户地址如何映射，修改一个系统调用并补测试，定位一个进程/内存生命周期错误。若这些主要依靠照抄或 AI 猜测完成，应先补基础，不宜直接承诺高完成度内核。

### 3.4 用一张表筛选正式赛题

先设四项淘汰条件：**资格不满足、硬件/数据拿不到、必做目标在周期内无法形成可运行版本、验收要求无法澄清。** 通过后再打分。

每项按 1～5 分评价，高分表示条件更好；总分为各项“得分 ÷ 5 × 权重”之和。它是团队决策工具，不是官方评分或获奖预测。

| 维度 | 权重 | 5 分应具备的条件 |
| --- | ---: | --- |
| 与现有知识/代码经验相邻 | 25 | 至少一位队员已经独立做过相关模块或项目 |
| 在周期内完成必做目标的可行性 | 20 | 已拆分里程碑，核心链路能较早运行，留有调试余量 |
| 评测与对照是否清楚 | 20 | 有明确输入、输出、基线、正确性标准和测量方法 |
| 开发环境与数据是否可得 | 15 | 所有关键依赖能立即使用，可重复构建 |
| 导师/社区支持 | 10 | 能确认需求和技术边界，有可用文档及沟通渠道 |
| 增量与成果表达 | 10 | 相比现有项目的改进明确，可以通过代码与实验证明 |

建议留下 2～3 个候选，各做一次短验证：跑通原项目、执行一次基准、复现一个问题、读懂准备修改的入口。比较真实进展后再定题，不只比较题名。官方历史说明也建议功能赛选题前先与题目导师沟通；本届应以区域赛公布的导师和题单为准。[oscomp 官方说明][W13]

### 3.5 约十周的准备安排

以下是投入建议，不是官方时间表。若正式赛题或团队时间不同，应据实调整。

## 四、等本届赛题加入后，最值得补充的判断

下一轮调研应将本报告从“方向建议”更新为具体题目排序，逐题回答：

3. 基线怎样测，正确性如何判断，性能是否可以重复测量？
4. 队伍的真实基础、每周可投入时间与导师支持能覆盖哪条知识链？
5. 每个候选最小可交付版本、最大风险、两周验证方法和退出条件是什么？
6. 本届区域赛内核评测的目标架构、测试集、有效成绩门槛及“完整通过”定义是什么？
