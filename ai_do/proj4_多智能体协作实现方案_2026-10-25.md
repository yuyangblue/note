## 一、题目到底卡在哪几条

官方硬条件（识别稿 5.3、5.5）：

| 编号 | 要求 | 验收含义 |
| --- | --- | --- |
| R1 | 基于 Linux + AIOS + 端侧大模型（7B 或 8B） | 环境三件套，缺一不可 |
| R2 | 用 AIOS-Agent SDK 设计多智能体协作系统 | 必须走 Cerebrum SDK，不能自己裸写一套 |
| R3 | 不少于 4 **种**智能体 | 4 份同类角色副本不算数 |
| R4 | 复杂任务可分解为不少于 4 个**可并行**子任务，并自动分配 | 要证明并行空间真实存在 |
| R5 | 不少于 3 对**不同类型**智能体之间存在**双向交互** | 有内容的来回，不是空消息 |
| R6 | 满足子任务先后顺序与依赖约束 | 要有依赖模型 |
| R7 | 相对同一多智能体方案串行，总时间减少 ≥ 20%，且任务正确 | 数值硬指标，占应用效果 50% |

评分：功能完整性 50%（任务合理性 40 分 + 多智能体实现与协作流程 60 分），应用效果 50%（20% 提速 50 分 + 正确完成 50 分）。⚠️ 这两组与赛道总技术方案（执行展示 30%、文档 20%、工程规范 20%、AI 说明 10%、视频 20%）如何折算，官方未说明，不要自行相乘。

## 二、一个必须先认清的事实：AIOS 不管协作

核对 AIOS 官方仓库与文档（2026-10-25 查阅）后的结论：

- AIOS kernel 是**操作系统内核之上的资源抽象层**，不是 Linux 内核。原文："The AIOS kernel acts as an abstraction layer over the operating system kernel, managing various resources that agents require, such as LLM, memory, storage and tool."
- kernel 管的是：LLM Core、Context Manager、Memory Manager、Storage Manager、Tool Manager、Scheduler。它接收 agent 的 syscall 并调度分派。
- **AIOS 没有提供 multi-agent 编排、agent factory 或 agent 间通信 API。** README 与 Cerebrum README 中均无此类接口；Cerebrum 的能力边界是 agent 的开发、部署、分发与发现（Development, Deployment, Distribution, Discovery）。

所以分工很清楚：

```
AIOS 负责：一次 LLM 请求/存储/工具调用怎么被调度、上下文怎么管
我们负责：谁先做、谁能并行、结果怎么交换、依赖怎么排序、最后怎么汇总
```

**「协作编排器」就是本作品的参赛增量。** 只把四个 agent 丢给 AIOS 跑起来，等于没做 R5/R6，功能完整性里的 60 分拿不到。

## 三、环境与安装（一手命令）

Python 限制：**仅支持 3.10 与 3.11**，别的版本装不上。

```bash
# 1. AIOS kernel
git clone https://github.com/agiresearch/AIOS.git
cd AIOS
python3.11 -m venv venv && source venv/bin/activate
pip install uv
uv pip install -r requirements-cuda.txt      # GPU 环境；CPU 用 requirements.txt

# 2. AIOS SDK（Cerebrum）——装了 kernel 默认会装，但建议源码安装以便改
git clone https://github.com/agiresearch/Cerebrum.git
cd Cerebrum && uv pip install -e .
python -c "import cerebrum; from cerebrum.client import Cerebrum; print(Cerebrum)"

# 3. 本地模型服务（4090 服务器）
vllm serve Qwen2.5-7B-Instruct --port 8091   # vLLM 仅支持 Linux + GPU
# 或 ollama serve + ollama pull qwen2.5:7b（CPU/GPU 均可）
```

配置两个文件：

`aios/config/config.yaml`（kernel 侧）：

```yaml
llms:
  models:
    - name: "qwen2.5-7b-instruct"
      backend: "vllm"
      hostname: "http://localhost:8091/v1"
```

Cerebrum 侧的配置须填**与 kernel 一致**的 host 和 port，否则 agent 连不上内核。

启动：

```bash
nohup python3 -m uvicorn runtime.launch:app --host 0.0.0.0 --port 8000 > uvicorn.log 2>&1 &
# 或 bash runtime/launch_kernel.sh
```

验证命令：`list-available-llms`、`list-local-agents`、`list-local-tools`。

⚠️ 竞赛允许的具体版本须固定。不要在主干分支反复重装，先把 commit hash 钉死写进 README。

## 四、Agent 怎么写

每个 agent 是一个三文件目录：

```
our_team/
└── log_analyzer/
    ├── entry.py                 # 主逻辑
    ├── config.json              # 元数据
    └── meta_requirements.txt    # 额外依赖
```

`config.json`：

```json
{
  "name": "log_analyzer",
  "description": ["从运行日志中提取异常时间线与调用链位置"],
  "tools": ["our_team/log_parser"],
  "meta": { "author": "our_team", "version": "0.0.1", "license": "CC0" },
  "build": { "entry": "entry.py", "module": "LogAnalyzer" }
}
```

`entry.py` 的三条硬性规则（官方文档明确要求）：

1. agent 类必须继承 `BaseAgent`（`cerebrum/agents/base.py`）。
2. 必须有 `run()` 方法作为主入口。
3. **所有与 kernel 的交互必须通过 `send_request`**，否则 AIOS 的调度、上下文、内存等能力对该 agent 不生效。

```python
from cerebrum.llm.apis import llm_chat
from cerebrum.memory.apis import create_memory, search_memories
from cerebrum.storage.apis import create_file, share_file
from cerebrum.tool.apis import call_tool

class LogAnalyzer(BaseAgent):
    def __init__(self, agent_name, task_input, config_):
        super().__init__(agent_name, task_input, config_)
        self.messages = []

    def run(self):
        # 工具：本地日志解析（CPU/IO 密集，可与 LLM 重叠）
        raw = call_tool("our_team/log_parser", {"path": self.task_input["log_path"]})
        # LLM：交给 AIOS kernel 调度
        resp = self.send_request(
            agent_name=self.agent_name,
            query=LLMQuery(messages=[{"role": "user", "content": f"提取异常时间线：{raw}"}])
        )
        return resp["response"]["response_message"]
```

可调用的 SDK 接口：

```python
from cerebrum.llm.apis import llm_chat, llm_chat_with_json_output, llm_chat_with_tool_call_output, llm_call_tool, llm_operate_file
from cerebrum.memory.apis import create_memory, get_memory, update_memory, delete_memory, search_memories, create_agentic_memory
from cerebrum.storage.apis import mount, create_file, create_dir, retrieve_file, rollback_file, share_file
from cerebrum.tool.apis import call_tool
```

单个 agent 调试运行：

```bash
run-agent --mode local --agent_path our_team/log_analyzer --task "..."
```

## 五、⚠️ 最大的技术陷阱

**如果 agent 绕过 kernel 直接调 vLLM/ollama，20% 就是拿不到的。**

原因：AIOS 的加速来自 kernel 把多个 agent 的 syscall 统一排队调度，而不是每个 agent 各自阻塞等待一次完整推理。直接调模型服务，你的加速只剩 Python `asyncio` 的 I/O 重叠，而且多个请求会在 vLLM 侧排队——题目"并发完成任务总时间减少 20%"很可能测不出来。

因此整个工程必须保证：

- 每个 agent 都继承 `BaseAgent` 并走 `send_request`；
- 唯一的模型出口是 kernel，agent 代码里不出现 vLLM/ollama 的直连；
- 并行由「编排器并发拉起多个 agent」+「kernel 调度多个 syscall」两层共同产生，实验报告里要能分开说清各贡献多少。

另外：agent 之间的数据交换建议走 AIOS 的 memory / storage API（`create_memory` + `search_memories`，或 `create_file` + `share_file`），这样"通信"是经过内核管理的资源，答辩时说得清；自己开 socket 或共享全局变量，就成了普通多线程程序，AIOS 价值无从体现。

## 六、协作编排器怎么设计

推荐场景：**受约束的软件项目故障诊断与复现验证**（输入固定的源码快照、日志、配置与测试数据；输出故障原因、证据定位与可执行复现包）。用可本地运行的小项目与已知故障，避免网络搜索把耗时变成不可控变量。

### 6.1 四类角色（满足 R3）

| Agent | 独立能力 | 可并行产出 |
| --- | --- | --- |
| 日志诊断 LogAnalyzer | 日志解析、调用链定位 | 异常时间线与首次出错点 |
| 源码分析 CodeInspector | 本地代码检索、受限静态分析 | 候选根因列表 + 证据位置 |
| 配置依赖 ConfigAuditor | 配置核对、版本与依赖检查 | 环境与参数问题清单 |
| 测试复现 ReproRunner | 执行固定测试、验证假设 | 可执行的复现步骤与结果 |

### 6.2 子任务 DAG（满足 R4 + R6）

```
L0  分解任务（编排器，或第 5 个 Planner 角色）
        ↓
L1  日志诊断 ‖ 源码分析 ‖ 配置依赖 ‖ 测试初诊      ← 4 个可并行子任务
        ↓（全部完成后）
L2  三对双向交互：日志↔源码、源码↔测试、配置↔测试   ← 满足 R5 的 3 对，可并发
        ↓
L3  汇总校验：合并假设、剔除被证伪项、输出诊断与复现包
```

L1 四个任务无依赖，构成 R4 要求的并行空间；L2 依赖 L1 的结果，L3 依赖 L2，构成 R6 的依赖约束。用 `asyncio.gather` + 拓扑分层实现即可，不必引入重型工作流框架。

### 6.3 双向交互要有内容（避免被判空消息）

一次合规的交互必须留下三类记录：**假设、证据、反馈后的修正**。

```
源码分析 → 日志诊断：「我怀疑是 X 函数在并发路径下的空指针，请核对 T 时刻前后有无对应日志」
日志诊断 → 源码分析：「T-2s 有 warn，T 时刻无 error，不支持崩溃假设；建议改查 Y 分支」
源码分析：修正候选根因为 Y 分支的状态未初始化
```

每次交互落盘（时间戳、发起方、响应方、假设、证据、结论），答辩时直接展示，也用于证明交互不是摆设。

## 七、20% 怎么测才站得住

```
T_serial   = 同一套多智能体方案串行执行（同样的 4 个 agent、同样的依赖与交互顺序，逐个执行）
T_parallel = 并发方案
达标条件： (T_serial - T_parallel) / T_serial ≥ 0.20
     等价： T_parallel ≤ 0.8 × T_serial，或 T_serial / T_parallel ≥ 1.25
```

⚠️ 基线是**多智能体串行**，不是单智能体。100 秒降到 80 秒才叫 20%；降到 83.3 秒只是加速 1.2 倍，不达标。

实验设计要点：

- 模型、任务集、硬件、输出质量标准、采样参数、计时起止边界全部一致；
- 冷启动与热启动分开报告，不能只给并行组预热；
- 多次重复取多次运行的结果，不只跑一次；
- 记录端到端时间**和分阶段耗时**，说明收益来自 L1 并行还是 kernel 调度；
- 正确性用可执行测试或已知答案判定，不用模型自评；
- 报告里如实给出至少一个对并发不利的场景（例如四个请求在 vLLM 侧排队），这比只报好数字更有说服力。

## 八、第一周验证与退出条件

1. 钉死 AIOS、Cerebrum、模型的 commit/版本，跑通一个最小 agent。
2. 用同一本地模型跑四个短任务，测串行与并发的实际耗时、排队情况与正确率。
3. 验证 SDK 的任务执行与数据交互可用（至少打通 memory 或 storage 一条）。
4. 说明候选任务为什么需要不同角色、哪四项真能并行、三对反馈的实际价值。
5. 向赛题方澄清：端侧部署是否接受团队可控的本地服务器、「单智能体无法完成」如何界定、20% 的计时起止、麒麟软件资源支持的申请流程。

**退出条件**：安装与版本适配持续阻塞、四项主要工作无法真正并行、或任务只能靠人为削弱单 agent 才成立 → 暂缓本题，转 proj5。

严禁用固定延迟、模拟模型输出或降低结果质量来凑 20%。
