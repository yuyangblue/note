## 三、功能题卡一：proj3（本届，约 90 分钟）

**题名**：面向多智能体的操作系统级执行时（Agent Runtime）｜英文 Multi-Agent-Oriented Operating System-Level Agent Runtime｜难度 A｜截图时选题队伍数 1
**原文来源**：`功能挑战赛题识别稿_2026-10-19.md` 第 4 节；截图 08～11。

### 3.1 题目原文要点（已转录在识别稿，回去读原文）

赛题说明点出四个「现有多 Agent 系统停留应用层框架」导致的问题：

1. 缺乏统一调度，资源竞争与执行低效；
2. 上下文（Context / KV Cache）频繁冗余拷贝，开销大；
3. 模型调用、工具调用与系统资源之间缺乏统一抽象；
4. 缺乏系统级可观测性与控制能力。

目标：把 Agent 提升为「操作系统一等公民」。

**六条赛题要求**（原文）：

- 面向多 Agent 任务的调度机制，支持任务依赖、动态生成任务及资源感知调度策略；
- 统一的 Agent 执行抽象模型，明确生命周期管理、状态转换及与 OS 资源的关系；
- Agent 执行容错机制，隔离单体 Agent 故障，避免级联故障；
- 高效的上下文管理机制，含上下文复用、压缩及隔离；
- 构建复杂多 Agent 应用场景，验证可用性与稳定性；
- Agent 之间的高效通信机制。

**平台**：基于 openEuler、openKylin、OpenHarmony 等至少一个国内主流开源 OS 开发。
**参考资料**：AIOS: LLM Agent Operating System；LangGraph / AutoGen / CrewAI 等框架；Linux 调度器（CFS）与容器资源管理机制。

**评分**：系统设计与机制创新 30%、功能完整性与实现深度 25%、性能优化效果 20%、工程实现质量 15%、实验与分析质量 10%。

## 四、功能题卡二：2025 proj352（往年，约 60 分钟）

**题名**：基于 LLM 的 kdump 分析｜所属：2025 全国大学生操作系统比赛「OS 功能设计」赛道｜难度：**高**｜分类：未归类的应用
**来源**：[oscomp/proj352-LLM-based-kdump-analysis](https://github.com/oscomp/proj352-LLM-based-kdump-analysis)（已代查，2026-10-21）
> 注意：本届网页的 proj1～proj5 是另一套编号，**不能与往年 GitHub 同编号混同**。

### 4.1 已代查的原题内容（需自己回仓库复核）

**项目描述（原文要点）**：Linux 崩溃时进入 kdump，可获取内核崩溃时的 dump stack 和故障现场，通常包括**调用栈、寄存器和内存分析**等信息，并需结合当前版本代码详细分析。本题旨在利用语言模型的知识，理解对应版本的 kernel 代码，完成自动化 dump 信息分析，给出初步故障诊断建议，简化故障定位流程。

**三个难点（原文）**：

1. 理解常规 kdump 中支撑问题分析所需要的信息量（通常由有经验的专家完成）；
2. 通过 prompt engineering 使语言模型理解故障场景和意图；
3. 通过 RAG 使语言模型精准定位故障代码。

**特征（= 必备能力）**：借助 LLM 等手段自动化常规 kdump 分析流程；构建理解 kernel 代码的 RAG 框架。
**进阶特性（= 建议，不要求必做）**：结合历史问题数据（bugzilla、maillist 等）进行问题分析。
**预期目标声明**：特征中的要求为必备能力，进阶特性为建议内容；也可提出自己的新想法，**得到导师认可后**可加入预期目标或进阶特性。
**项目导师**：张波（oscar.zhangbo@huawei.com）。
**参赛要求**：以小组为单位，最多三人，同一所高校；一人参加多个项目时只能选一个参与评奖。
