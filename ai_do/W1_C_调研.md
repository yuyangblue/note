## 第二部分：任务 1 — 2025 内核赛道概览

### 一句话：内核赛道到底要交什么 ✅

不是写一个应用程序，也不是只写一段内核代码，而是**交一个能在指定模拟器上启动、能自己挂载磁盘并跑完一批官方测试点、把结果打印到屏幕上的完整内核工程**。评分看你屏幕输出里通过了多少测试点。  
〔源：`testsuits-for-oskernel` pre-2025 分支 README「赛题评测指南」段：*"提交的项目根目录中必须包含一个 Makefile 文件……生成 ELF 格式的 kernel-rv 和 kernel-la 两个文件"*、*"您的操作系统在启动后需要主动扫描磁盘，并依次运行其中每一个测试点，将其运行结果输出到屏幕上，评测系统会根据您操作系统的屏幕输出内容进行评分"*〕

### 一条过程：用户程序 → 系统调用 → 内核模块 → 设备 → 返回 ✅（例子：读一个文件）

```
1. 用户程序调用 read(fd, buf, n)
2. CPU 执行 ecall 陷入内核态，内核按系统调用号找到 sys_read
3. 内核用 fd 找到进程的打开文件表项 → 拿到 file 对象 → 通过 VFS 找到该文件的 inode
4. VFS 向下调用具体文件系统（如 Ext4）的读接口
5. 文件系统先查页缓存；没命中就向块设备层发请求
6. 块设备驱动写设备寄存器，把请求交给磁盘（QEMU 里是 virtio-blk）
7. 磁盘完成 → 触发中断 → 中断处理程序把数据填入内核缓冲区
8. 内核把数据拷回用户态 buf，返回，恢复用户态继续执行
```

〔源：分层结构依据 Starry Mix 文档的模块划分（final.pdf 第 5、7、10 章）与分工文件 4.2 节要求的过程〕

### ⑤ 我选的一项机制 ✅（推荐 UserPtr；也可换成 weak-map）

**机制名称**：UserPtr —— 用户地址访问封装  
**位置**：`prelim.pdf` p8-9；`final.pdf` p23-26（5.4 节）

```
它要解决的问题：
  Starry Mix 的内核和用户共用一套页表地址空间，用户指针原本是裸指针，带来四个麻烦——
  ① 内核访问用户内存发生缺页时会直接崩溃（内核缺页被视为致命错误）；
  ② 无法按 POSIX 规范返回 EFAULT；
  ③ 每次访问都要写 unsafe；
  ④ 处理不定长字符串很别扭。

它的做法：
  设计 UserPtr<T> / UserConstPtr<T> 封装裸指针。要转成引用时做三件事：
  检查地址对齐、检查内存权限是否允许用户读/写、把范围内还没分配的页全部分配好。
  另设一个全局标志位 ACCESSING_USER_MEM：内核正在访问用户内存时，
  缺页处理就不拒绝来自内核的异常（用来处理 get_as_str 这种长度未知的情况）。

起到的作用：
  既满足了 POSIX 的 EFAULT 语义，又保住了"内核自己缺页 = 致命错误"这个安全假设。

代价或我还不懂的地方：
  ACCESSING_USER_MEM 是个全局标志位，作者自己说是为处理不定长数据做的妥协。
  疑问：多核并发下这个标志位怎么维护？文档没说。
```

〔源：`prelim.pdf` p8-9「2.4 用户地址访问」；`final.pdf` p23-26「5.4 用户地址访问」〕

> 其他三个候选（weak-map 自动回收 / axfs-ng 重构 / 同步异步混合）见 `StarryMix_导读_C专用.md` 第五节。

### 三个到点检查 ✅

**检查 1**：能画出「用户任务 → Agent 运行时 → 模型/工具 → OS 资源」的关系图吗？
```
用户提交一个复杂任务
   → Agent Runtime 把它拆成多个 Agent 子任务（有依赖顺序）
   → 每个子任务运行时要两样东西：模型推理（GPU/显存/KV Cache）+ 工具（进程、文件、网络）
   → Runtime 负责：谁先跑、谁能并行、给谁多少资源、谁崩了不影响别人、上下文怎么复用
   → OS 提供：进程隔离、CPU/内存配额、I/O
```
〔小暗归纳，依据识别稿 4.2-4.3 的四个问题和六条要求〕

**检查 2**：一个任务失败怎么影响其他任务？
```
举例：A 负责读日志、B 负责分析代码、C 负责跑测试，B 依赖 A 的输出。
若 A 崩溃，而 Runtime 没有隔离：B 会一直等一个永远不会来的结果，
C 也可能被卡住，最后整个任务超时失败——这就是题目说的"级联故障"。
有隔离的做法：Runtime 检测到 A 失败 → 把失败限制在 A 这个执行单元内 →
重试 A，或让 B 走降级路径（用不完整输入继续），整个系统不至于瘫痪。
```

**检查 3**：文本上下文 vs 模型 KV Cache
```
文本上下文（应用层可见）：就是消息历史、提示词里那些 token。
  可以由应用层自己管理——裁剪、摘要、合并提示词都发生在这一层。
模型 KV Cache（推理后端内部）：Transformer 推理时缓存的 Key/Value 张量，
  用于避免重复计算前缀。它跟具体模型版本、推理后端、缓存一致性绑定。
关键区别：把几段提示词拼起来，只是减少了文本层面的重复，
  ≠ KV Cache 复用。真正的 KV Cache 复用要推理后端支持（如前缀缓存）。
  不能把"合并提示词"叫做 KV Cache 优化。
```
〔源：本地《选题分析》第 8 节明确提醒了这一点；识别稿 4.2 背景提到了两者但必做深度待澄清〕

### 一手参考（帮你理解"现成框架缺什么"）✅

**AIOS**（题目参考资料第一条）

### 两个必须回答的问题 ✅

**为什么必须匹配源码版本？**
```
因为调用栈里给的是"函数名 + 偏移"，例如 qede_fill_frag_skb+0x96/0x430。
函数名在不同版本里可能改过名、改过实现，偏移 0x96 对应的源码行
只在那个具体版本里才成立。用错版本的源码去对，会把定位引到错误的行上。
另外 Linux 内核文档明确要求：分析工具必须用带调试符号的、与崩溃内核
完全对应的 vmlinux——"The dump analysis tools require a vmlinux with
debug symbols in order to read and analyze a dump file."
```
〔源：https://docs.kernel.org/admin-guide/kdump/kdump.html ；案例中的偏移示例来自 Bugzilla 2532100〕

**为什么需要"可靠的故障样本"？**
```
因为要判断系统给出的诊断对不对，必须有一个"已知正确答案"来对照。
如果样本只有 dump 而根因未知，你无法区分"模型说对了"和"模型编得像真的"。
样本还要"可靠"：dump 与源码版本对应、根因经过上游确认
（比如有明确的修复 commit），否则测出来的准确率没有意义。
```

### kdump 机制补充（帮你搞懂概念）✅

```
· kdump 是基于 kexec 的内核崩溃转储机制。系统内核启动时会预留一小段内存
  （用 crashkernel=Y@X 指定），用 kexec -p 把 dump-capture kernel（捕获内核）
  预先加载进去。
· 崩溃发生（panic()/die()/die_nmi()/SysRq-c）时不走完整硬件重启，
  而是快速切到捕获内核，于是系统内核的内存映像被保留下来。
· 在捕获内核里通过 /proc/vmcore 把内存映像导出成 ELF 格式的 vmcore 文件
  （cp /proc/vmcore <dump-file>）。
· 用 gdb vmlinux <dump-file> 或 crash 工具分析，可以拿到：
  调用栈（btt / btpid 等宏）、寄存器（含 Trapno、cr2、error_code）、内存内容。
· 前提：内核要用 CONFIG_DEBUG_INFO=Y 编译，才有带符号的 vmlinux。
```
〔源：https://docs.kernel.org/admin-guide/kdump/kdump.html ，以上各句均为该页原文或原文命令〕

### 你的额外任务：proj352 vs proj3 ✅

```
proj352（2025）在做的事：AI 是"分析工具"——
  输入一个已经发生的 OS 故障现场，让 LLM 读懂 dump + 源码，输出诊断建议。
  对象是 OS 自身的问题，AI 在外部帮忙看。

proj3（本届）在做的事：AI 是"被管理的执行主体"——
  Agent 本身是运行在系统里的任务，Runtime 要管它们的调度、资源、容错、
  上下文和通信。对象是 Agent，AI 是被管的那一方。

核心区别：
  proj352 里 OS 是"被诊断的对象"，AI 在旁边当顾问；
  proj3 里 OS 是"管理者"，AI 是被调度、被隔离、被分配资源的执行单元。
  一个是 AI for OS（用 AI 解决 OS 问题），一个是 OS for AI（为 AI 建 OS 机制）。

这说明功能挑战赛覆盖的范围是：
  不只是"做个 OS 功能"，而是覆盖"AI 与 OS 交叉"的两个方向——
  既能让 AI 帮 OS 做事，也能让 OS 去管 AI。
```

### 概念 1：Runtime（运行时）

```
它是什么：程序/任务运行时依赖的那一层支撑环境，负责调度、资源、生命周期，
         而不是实现业务逻辑本身（类比：JVM 是 Java 程序的 runtime）
解决什么问题：让上层的任务不必各自重复处理"什么时候跑、给多少资源、崩了怎么办"
在我调研的东西里哪里用到：
         proj3 要做的正是 Agent 的 Runtime；
         Starry Mix 里 axtask 负责任务调度与管理（ArceOS modules 之一）
我还没理解什么：Runtime 和"框架/库"的边界在哪——为什么 LangGraph 叫框架
         （pip 装进应用），而 proj3 要的叫 Runtime？
         差别是不是就在于有没有自己的调度和资源管理权？
```
〔源：AIOS README 的 kernel 定位句；LangGraph README 的 pip 安装与定位句；`final.pdf` p6〕

### 概念 2：KV Cache

```
它是什么：Transformer 推理时缓存的 Key/Value 张量，用来避免重复计算已处理的前缀
解决什么问题：生成第 n 个 token 时不必重算前 n-1 个，显著加速自回归生成
在我调研的东西里哪里用到：
         proj3 要求"上下文管理机制，包括上下文复用、压缩及隔离"，
         截图背景同时提到了 Context 和 KV Cache
我还没理解什么：KV Cache 具体存在哪、生命周期由谁管、多个 Agent 共享同一个模型时
         能不能共用前缀缓存——这些我都还没查证
```
〔源：识别稿 4.2 背景第 2 点原文"上下文（Context/KV Cache）频繁冗余拷贝"；本地《选题分析》第 8 节关于两种上下文的提醒〕

### 概念 3：RAG（检索增强生成）

```
它是什么：先从外部知识库检索相关片段，再把片段和问题一起送给模型生成答案
解决什么问题：模型不知道私有/最新/特定版本的内容，也不该靠"幻觉"编；
         检索提供可追溯的依据
在我调研的东西里哪里用到：
         proj352 的两个必备能力之一——"构建理解 kernel 代码的 RAG 框架"
我还没理解什么：代码怎么切分才算合理（按函数？按文件？）、
         检索出来的是代码片段还是提交历史、用什么指标判断"检索准不准"
```
〔源：proj352 原题页「特征」栏原文"构建理解kernel代码的rag框架"〕
